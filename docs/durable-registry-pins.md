# Registry pins PR1 — dormant core, real deletion HOLD

## What changes / why (C4 scope)

- **Context:** sandbox API replicas share a registry. Finite reference scans do not prevent a new acquisition between scan and DELETE; the registry cannot fence a stale HTTP request by a database epoch.
- **Container:** one existing writable PRIMARY PostgreSQL and one trusted canonical registry host. No registry, Kubernetes, cloud, SMTP, credentials, read replica, worker, lease or new dependency is added to the core.
- **Components:** `internal/registrypins` owns explicit `Ensure`, exact project-template reference parsing, durable pin receipts and exclusive repo prune intents. `pgdoc.RejectInheritedTransaction` prevents an outer rollback from undoing an apparently accepted fence. The engine is not wired to startup or existing reference writers.
- **Code boundaries:** scheduled/debug prune and project-teardown deletion now return an explicit operator HOLD for configured `on`, even with missing host/credentials. Off stays off; dry-run remains a read-only finite preview. The low-level OCI client is unchanged and its isolated client test still exercises DELETE; no production caller can reach it for real deletion in this PR.

## Protocol / invariants

1. A server selects its host from trusted Config, calls `New(primary, host)` and explicitly ensures the schema. Hosts cannot be request URLs; parsing makes no network requests. Only `host/t/<project>/<20-hex-template>:tag` or `@sha256:<64-hex>` is accepted; library and foreign-host refs are rejected. `Operation.ProjectID` must match every ref and a current ENABLED/DISABLED project row on this PRIMARY. This is an internal scope check, not user authorization.
2. `BeginPins` commits PENDING receipts BEFORE resolution/use, external dispatch and any existing project transaction. Owned AND cross-DB inherited transactions are rejected rather than joined, stripped or independently committed. Each short transaction explicitly selects READ COMMITTED before its first snapshot query, then locks canonical host namespace → current project row → pin/intent rows. Snapshot isolation defaults cannot retain a pre-lock view.
3. Stable operation UUID + project + owner + expected immutable generation are frozen; retrying the same accepted operation conflicts rather than redispatching. Each pin has its own UUID/epoch. An immutable requested alias stays separate from the current digest, so multiple aliases may bind to the same digest independently.
4. `ObserveBinding` needs independently observed UID, generation and digest ref matching the expected spec/owner nonce that the future writer stamps on the durable DB/CR binding. `ReleaseBinding` needs exact UID + observed generation + canonical digest and full receipt CAS. A delayed observation of the same UID's old generation cannot release a new generation. The core cannot verify external observations; PR2 must do so.
5. PENDING, BOUND and UNKNOWN have no expiry. Known no-effect may release only PENDING; exact observed removal/termination may release only BOUND. UNKNOWN cannot be cleared by these APIs. Async BASE remains held through positively observed exact pod termination; DEST remains owned by the current build/template binding. StartBuild success, pod absence or an apply timeout is not positive cleanup evidence.
6. `BeginPrune` is a **DB exclusion primitive, not deletion authorization**: any unreleased pin in the repo, including unresolved tag/DEST, holds it. An active intent blocks all new repo acquisitions. `MarkSending` commits before exactly one caller HTTP attempt; the core performs none. Full owner/generation/epoch/state/ref/project CAS rejects stale transitions and repeated send authorization.
7. SENDING/UNKNOWN never expire, replay or lease-takeover. `SettleKnown` accepts only a definitive response to the sole SENDING attempt, with no outstanding old request/retry; it distinguishes deleted/already_absent/not_deleted. UNKNOWN has no resend/clear API. Cancellation, HEAD absence, pod loss and lease expiry cannot fence an old registry request. Operator recovery requires a separately reviewed definitive-outcome + old-deleter-exclusion procedure; do not delete rows or fabricate known outcomes to clear HOLD.
8. Teardown configured `on` now remains incomplete with a visible HOLD; this is intentional, not a successful registry cleanup. Scheduled HOLD logs fixed reasons without secrets. Debug returns the error through its existing result envelope, not a false successful `ran` result. Dry-run evidence is never proof of real deletion.

## Tests / nonclaims

Unit tests cover strict canonical refs, unconditional typed HOLD, inherited transaction rejection, both physical entrypoint HOLDs with zero HTTP, configured-on incomplete settings and preserved dry-run/low-level client behavior. Real PostgreSQL tests use two independent pools (one defaults REPEATABLE READ), a two-waiter advisory-lock barrier in both acquisition orders, observed-generation/two-alias cleanup, UNKNOWN/stale replay/age holds, scope/current-project checks, nested TX rejection/atomicity, configured-on public HOLD and read-only PRIMARY rejection. These are local testcontainers and loopback fake HTTP only: no real registry/cloud/cluster deletion or production race-free GC acceptance is claimed.
