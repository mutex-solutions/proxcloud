# Offline public VM sanitization: native OS and the accepted Kubernetes template

[The sanitizer](<../images/vm_sanitize.py>) is an **actual offline scratch-copy transformer**, not a receipt-only helper. It never publishes anything itself. The parent that runs it owns the containment, the read-only input copy, the resource limits, the exact container/cgroup termination, the private spool, the acceptance boot and the publication gates: that parent is the `export` job of [`vm-artifact-export.yml`](<../.github/workflows/vm-artifact-export.yml>), which runs the launchers in `images/vm_export/` in a fixed order through `images/vm_export/pipeline.py`. The whole flow, its trust model and how to verify a published image are in [VM artifact export and publishing](<vm-artifact-publishing.md>).

## Deliberately fixed boundary

The native selector is `--os ubuntu-2404|ubuntu-2604|debian-12|debian-13`. A separate, mutually exclusive `--k8s-os ubuntu-2604` selector implements only the `kubernetes` variant described [below](#kubernetes-variant-k8s-os-ubuntu-2604); `--os X --variant kubernetes`, arbitrary formats, guest commands and path overrides are not supported. The script requires a non-root user whose UID and effective UID are equal and 1000 or higher (the invoking host user; no longer exactly 1000). Native input is the regular, single-link, privately collected, **immutable read-only** `/input/source.qcow2` (the Kubernetes variant instead takes `/input/source.raw` plus `/input/k8s-review.json`, see below); all modifications are to `/scratch/work/disk.qcow2`. The final standalone disk and small facts file are `/scratch/export/disk.qcow2` and `/scratch/export/clean-export-facts.json`. Work/export directories must not exist at start; retry in a new capsule. No original PVE disk/template is opened or changed by this code.

Execution is only appropriate in the **reviewed OS tools container**: trusted, pinned Debian Bookworm qemu-img/libguestfs/Python bindings/kernel/appliance; root filesystem read-only; network namespace `none`; the invoking host user (non-root, UID and GID 1000 or higher, never a system group); all capabilities dropped; no KVM, FUSE, extra devices, credentials, host sockets or writable host mounts. Read-only-bind only the exact private input and reviewed source. `/scratch` is a bounded private tmpfs. Direct libguestfs backend, disabled guest network and forced TCG are set explicitly. The Python environment and qemu-img subprocess environment are reduced to fixed constants. This program does **not** construct or independently prove those outer controls.

The current policy accepts exactly **20 GiB virtual size**, not every 20..100 GiB artifact accepted by the [public artifact contract](<public-vm-artifacts.md>). The input allocation is bounded to 24 GiB; compressed output must be strictly below 8 GiB. A 20 GiB image temporarily becomes close to fully allocated during zeroing; concurrent work/output, appliance RAM and tmpfs pages require a separately reviewed memory/cgroup budget. A 32 GiB scratch tmpfs limit alone is **not proof** a 32 GiB memory limit is sufficient. OOM, size limits, tool errors, malformed inputs, unsupported layout or failing postconditions produce no success facts. Do not relax limits or fall back to trim-only cleanup automatically.

## Processing and refusal gates

1. Inside containment, qemu-img reads QCOW2 metadata with explicit input format. Recursive metadata validation rejects backing references, external data-file references, snapshots, encryption, corruption, non-QCOW2 and other virtual sizes **before** qemu-img check or conversion. This is an image parser, so containment must already be active before this first step. Metadata/check output and tool stderr are not printed.
2. A checked input is flattened with explicit `-f qcow2 -O qcow2 -o compat=1.1,lazy_refcounts=off` into the fresh scratch work disk. The source is never added to libguestfs for writing.
3. Libguestfs inspection must find one Linux installation matching the selected Ubuntu 24.04/26.04 or Debian major 12/13. No boot, target binary, shell, service, network connection, `virt-customize`, firstboot or guestfs `command`/`sh` action runs. The expected native cloud account (`ubuntu` or `debian`) must remain present.
4. Accepted layout is one `/dev/sda`, no LVs, one ext4 root, optional ext4 `/boot`, optional vfat `/boot/efi`. Every recognized filesystem must be accounted for. An unmounted `unknown` BIOS boot partition is accepted only with GPT type `21686148-6449-6e6f-744e-656564454649`; its bootloader bytes are retained, not treated as free space. LVM, swap, unexpected devices/filesystems, extra mountpoints and unsupported metadata refuse, rather than widening cleanup silently.
5. Curated offline file operations remove cloud-init cache/seed, installer/curtin/subiquity state, root and home personal contents, SSH keys, histories, logs, apt lists/caches, temporary files, random seed, DHCP/NetworkManager leases, persistent MAC rules, build networking, account backups and build sudo drop-ins. All cloud-init drop-ins are removed; packaged `/etc/cloud/cloud.cfg` and modules remain. Cloud-init must recreate tenant identity/networking on the next cold boot; no build user-data source is retained. If customizations that must survive live in drop-ins, this version is unsuitable until explicitly reviewed.
6. Native `/etc/passwd` credential fields must be exactly shadow-backed `x` or fixed locked markers `!`, `*`, `!!`; empty fields or embedded/recoverable crypt hashes refuse before cleanup and again at final verification. Every shadow and gshadow password field is **replaced** with `!`, not prefixed to leave a recoverable password hash. All other fields and the native cloud account are retained. Builder/packer accounts, if present, remain but are password-locked and have empty homes/SSH state; matching sudo drop-ins are removed. A builder/packer rule in main sudoers refuses instead of guessing a safe policy rewrite. This is not a general-purpose Unix account migration tool.
7. Machine-id becomes empty; dbus machine-id and random seed are removed; hostname and hosts become public localhost constants. Netplan YAML, interface drop-ins, systemd-network and NetworkManager connection files are removed. Interfaces becomes loopback-only and resolver becomes a standard systemd-resolved runtime symlink. Packaged cloud-init, SSH server configuration, guest agent and bootloader remain. Boot command-line `ip=`, `ds=` or cloud-init-disabled overrides refuse rather than silently preserving build settings. A registered **snapd identity is reset to unregistered** exactly as in the [Kubernetes variant](#kubernetes-variant-k8s-os-ubuntu-2604) (same owner decision): before any write, the device-key files `private-keys-v1/*` and the serial-assertion subtree are planned for removal and `state.json` `data.auth.device` `serial`/`key-id` are dropped. A `session-macaroon`, any store user, or a key entry the wipe cannot cleanly remove (dot, hardlinked, link, directory) refuses instead: nothing is written. Final postconditions require snapd unregistered. An unseeded image (no snapd state) is untouched.
8. Postconditions re-read active password tables, identity and retained cloud account, require curated build paths absent, and scan bounded configuration files, including only GRUB text configuration (`grub.cfg` and `/etc/default/grub`, not binary fonts/modules), for the known `10.200.` lab prefix, private-key headers, SSH public-key markers and MAC literals. Selected symlink leaves are unlinked, but symlink ancestors and critical writable-file symlinks refuse; guest paths are never host paths. No raw guest bytes, usernames, addresses, password hashes or tool errors appear in success/failure logs.
9. After flush/unmount, each ext4 journal is **removed**, e2fsck is performed, all accepted filesystems are mounted and `zero_free_space` really writes their free blocks, including the freed old ext4 journal blocks. Filesystems are flushed/unmounted; new ext4 journals are created and checked; final mounted postconditions run. This is not fstrim/discard/compression masquerading as erasure.
10. After guestfs shutdown/close, explicit compressed QCOW2 conversion produces the final standalone export. Metadata/check and actual SHA256/length are rechecked. Only then does the script write the private facts file and print the same small JSON object.

### Trusted appliance journal primitive: explicit prerequisite

Bookworm Python libguestfs **does not** support `tune2fs(features=...)`. The script instead uses `g.debug("sh", ["/usr/sbin/tune2fs -O ^has_journal /dev/sdaN"])` and the matching `has_journal` restore. This is the **trusted appliance's** tool, while all target filesystems are unmounted, not a binary or shell from the target guest filesystem. Device names are strictly limited to `/dev/sda` followed by one/two decimal partition digits and cannot inject shell syntax. `tune2fs_l` must show the requested feature state; `e2fsck(device, correct=True)` must succeed. The mutually exclusive `correct=True, forceall=True` combination is intentionally not used.

Before real image use, the operator must verify the exact pinned tool image supports this debug-shell syntax, fixed appliance tool path, feature readback, journal removal/restore, actual `zero_free_space`, shutdown and no network/KVM. Use a disposable synthetic filesystem with a preservation sentinel and the same isolation controls first. Pure fake tests cannot establish this prerequisite. No unsupported-API fallback, swallowed failure or claimed successful journal reset is allowed.

## Kubernetes variant (`--k8s-os ubuntu-2604`)

Scope is exactly the Ubuntu 26.04 node template lines of the Kubernetes versions in `K8S_VERSIONS` (**1.35.10**, whose build canary passed, and **1.36.6** and **1.37.2**, added 2026-11-14 for upgrade testing; each version's build, inventory and runtime acceptance are their own gates, and the real-template facts below were recorded on 1.35.10), exported to `ghcr.io/mutex-solutions/proxcloud-vm-ubuntu-2604-k8s` (first artifact published 2026-11-12; publication does not satisfy the runtime acceptance below). The decision logic lives in the pure [copy policy](<../images/k8s_copy_policy.py>); the sanitizer only gathers bounded facts and applies the policy's recommendations.

- **Root disk only.** Input is the template's RAW root disk at `/input/source.raw`, exactly 20 GiB, regular and single-link, plus a small parent-reviewed `/input/k8s-review.json` opened with `O_NOFOLLOW`/fstat. The template's EFI vars disk and cloud-init CD/seed media are **never** inputs or outputs; a cold boot must use fresh cloud-init and, if UEFI is ever required, newly generated EFI vars.
- **Source binding.** The review must carry `source_raw_sha256`. The capsule stream-hashes the raw file (bounded, stable fstat before/after) and refuses on mismatch **before** any image parser runs. Explicit `-f raw` metadata checks precede a confined `-f raw -O qcow2` conversion into the scratch work copy; the work copy then gets the normal QCOW2 info/check. The stopped-source fact remains a parent attestation.
- **Inventory before writes.** A read-only inventory feeds `validate_inventory`, and any refusal happens before a single guest write. The root is mounted **read-only** (`mount_options("ro")`) for the whole inventory. Every rewrite (group tables, snapd `state.json`) is computed and dry-run while still read-only. Only after the policy accepts is the root unmounted and remounted read-write. Covered facts:
  - root-only msdos/ext4 layout (checked before mounting), symlinked critical paths and external fstab. curtin writes the root fstab spec as `/dev/disk/by-uuid/<uuid>` and libguestfs returns it unresolved. **Only** that exact canonical lowercase form is resolved with `findfs_uuid`, and it must resolve to the single inspected root device. by-label, by-partuuid, `UUID=`/`LABEL=`, non-canonical, unresolvable or non-root specs refuse. Every later mount (inventory, cleanup, journal reset/zeroing, final check) uses the resolved device, never the spec;
  - **swap**: `/swap.img`, `/swapfile`, **active** (uncommented) fstab swap rows and `*.swap` units in `/etc/systemd/system`;
  - accounts: only root, `builder` (uid 1000, `/home/builder`, `/bin/bash`, locked), nologin system accounts and base-passwd `sync`. **No `ubuntu` account, home or group may pre-exist**;
  - network backend, the exact `kubeadm`/`kubelet`/`kubectl` deb versions (dpkg Status exactly `install ok installed` or `hold ok installed`) and kubelet enablement;
  - **existing cluster state**: PKI, kubeconfigs, etcd, static manifests (minus only the empty `.kubelet-keep` placeholder, see below), pods/tasks/CNI state; links and dangling entries are counted;
  - credential hygiene: credentials in apt sources and repo URLs; proxy or lab addresses in `apt.conf`, `apt.conf.d`, `/etc/environment` and `containerd.service.d` drop-ins; containerd registry auth, including `hosts.toml` authorization/bearer/basic headers; kubelet registry files (`/var/lib/kubelet/config.json`, `.dockercfg`, `/.docker/config.json`, `/root/.docker/config.json`) are refused, never removed; credentials or lab addresses in `/var/lib/kubelet` outside `pki/` and `pods/`; `systemd` `credential.secret` (any entry refuses); snapd device-key entries the curated wipe can't cleanly remove (see below);
  - **identity** (presence and counts only, never values): how many supplementary groups list `builder`; snapd `state.json` presence, device `serial`/`key-id`/`session-macaroon` presence, store user count, serial-assertion entry count and wipeable device-key count.
- **Exact fact types.** GuestFS predicates (`is_file`, `is_symlink`, `exists`, `is_dir`) return int `0/1` in the real Python binding. The producer casts them to `bool`, as the policy requires, for drop-in `regular_no_symlinks`, kubelet enablement and `exists`-based counts. The policy still refuses an int in a bool field.
- **Refusal, not deletion.** Unknown, missing or mismatched facts refuse; cluster state and swap are never wiped, so the parent learns the real state.
- **cloud.cfg.d.** The native blanket `/etc/cloud/cloud.cfg.d/*` removal is replaced by exact reviewed `(name, sha256, preserve_vendor|remove_build)` decisions covering every observed entry. Preserved files are re-hashed after cleanup. Cloud-init's shipped `README` is accepted only via its own exact reviewed row. Rows (and therefore hashes) come only from the parent review file, never from source constants.
- **First-boot identity (owner decision).** The image keeps the packaged base `/etc/cloud/cloud.cfg`, whose default user is the **upstream `ubuntu`** (`users: [default]`, `lock_passwd: true`). The review key `cloud_default_user` must be exactly `"ubuntu"`, and `cloud_base_config_reviewed` attests that review. Cloud-init creates `ubuntu` at first boot and installs user-data SSH keys there, so an existing `ubuntu` account, `/home/ubuntu` or `ubuntu` group refuses. `builder` stays the exact retained `native_login` account. It must be locked (shadow marker `!`, `!!`, `*` or `!*`; the copy locks every table again). Its `~/.ssh` is removed by the COPY_WIPE and home cleanup. `cloud_default_user: "builder"` now refuses.
- **builder loses every supplementary group (owner decision).** After `validate_inventory`, the copy rewrites the `/etc/group` member field and the `/etc/gshadow` administrator and member fields. It drops exactly the name `builder` and leaves every other byte unchanged: rows, order, other members (including look-alikes such as `builder2`) and builder's own primary group row. The inventory records the count and dry-runs the rewrite while read-only; a malformed row refuses. The final check requires that `builder` appears in no member or administrator list.
  - **Strict member lists.** Every non-empty member/administrator field in both tables must fully match `[a-z_][a-z0-9_.-]*$?` items joined by single commas (ASCII). glibc `nss_files` tolerates sloppy lists, so `syslog, builder` would still grant builder `sudo` while an exact-token strip missed it. Such fields refuse: blanks, CR/tab, empty items (`a,,b`, `,builder`, `builder,`), upper case or non-ASCII.
  - **Primary group bound.** The primary gid is not rewritten, so it must already be safe. builder's passwd gid must name exactly one `/etc/group` row, that row must be named `builder`, and it must be the only `builder` row. gids compare numerically, so a zero-padded duplicate counts as shared. sudo `%group` rules and group-owned sockets (for example lxd) also match a primary gid, so gid 27 (`sudo`) or a gid shared with another group refuses. This is the policy fact `identity.builder_primary_group_own`, which must be `True`, and the final check re-verifies it.
- **sudo policy bound to reviewed bytes.** Two new review keys: `sudoers_sha256` binds `/etc/sudoers` (stock Ubuntu: `root ALL`, `%admin ALL`, `%sudo ALL`, `@includedir /etc/sudoers.d`), and `sudoers_readme_sha256` binds `/etc/sudoers.d/README`. This replaces the earlier `builder`/`packer` word-grep as the guard. Before cleanup, `/etc/sudoers.d` must be a real directory holding the reviewed README. Every other entry must be a regular, non-dot build drop-in whose name or content names `builder`/`packer`; cleanup removes those (kept from the native path). Any other drop-in refuses before any write, such as `%sudo … NOPASSWD`, a `#uid` rule or `@include`. After cleanup, `/etc/sudoers.d` must be **exactly** `{README}` with the reviewed hash, and `/etc/sudoers` must still match its hash. Because builder is in no group afterwards, the stock `%sudo`/`%admin` rules grant it nothing.
  - **sudo-rs is the active sudo on Ubuntu 26.04.** `/usr/bin/sudo` resolves through alternatives to sudo-rs (observed: sudo-rs 0.2.13 active, classic sudo 1.9.17 also installed, both apt-held). sudo-rs reads `/etc/sudoers-rs` if it exists and otherwise `/etc/sudoers`, which is the hash-bound file. So **any** `/etc/sudoers-rs` entry (file, symlink or directory) refuses.
  - **`/etc/sudo.conf`** (classic sudo plugins and `sudoers_file`) may exist, but it must have no active line (every non-blank line a comment). Its comment-only bytes are not hash-bound.
  - **userdb.** systemd userdb drop-in directories (`/etc/userdb`, `/run/userdb`, `/run/host/userdb`, `/usr/local/lib/userdb`, `/usr/lib/userdb`) must be absent or empty. A `*.user`, `*.group` or `*.membership` record there would add accounts or memberships outside the rewritten tables.

  All three guards run in the inventory (before any write) and again in the final check. Observed on the real image: `/etc/sudoers-rs` and `/etc/userdb` absent, `/etc/sudo.conf` comment-only.
- **snapd identity reset to unregistered (owner decision).** Copy-only, after `validate_inventory`:
  - wipe the device-key files `private-keys-v1/*` (each regular, single-link, non-dot) and the serial-assertion subtree `/var/lib/snapd/assertions/asserts-v0/serial` (no symlinks; every leaf single-link);
  - rewrite `/var/lib/snapd/state.json`, removing only `data.auth.device.serial`, `key-id` and `session-macaroon`. brand and model, seed state, snaps and every other key stay.

  The parse is strict: bounded to 32 MiB, UTF-8, duplicate keys, NaN/Infinity and non-canonical number text refuse, and only the observed `auth` keys (`device`, `last-id`, `users`) and device keys are allowed. Output is compact JSON that keeps key order, and it must re-parse to the original tree minus those keys. If there is nothing to drop, the file is left byte-identical. A session macaroon or any store user refuses in the policy (credentials, not regenerable machine identity). The rewrite also refuses if `state.json` changed between the read-only inventory and the write, or if its content can't be re-encoded (for example a lone `\ud800` surrogate escape). The final check requires an empty key directory, no serial subtree, no serial/key-id/session-macaroon in `state.json`, and still no store user.
  - **Not reset, by design:** the per-snap `snap-cookie` values that `state.json` keeps (and `/var/lib/snapd/cookie/` mirrors) stay **identical across clones**. They authenticate a snap's own `snapctl` calls to the local snapd over its socket; they are not device or store identity and grant nothing remotely. Regenerating them is snapd-internal, so they are left untouched. This is a known, accepted residue.
- **Curated removals.** Generic personal/network/identity cleanup plus the policy's copy-only wipes: builder/root SSH state, host keys, cloud-init state and logs, installer logs, dbus machine-id, apt auth, docker configs, snapd device-key entries and serial assertions, and reviewed prejoin token leaves.
- **Kubelet enablement is preserved, never toggled.** The upstream template is `enabled=true,state=stopped`. A masked, redirected or missing unit refuses. Enablement, packages and cluster counts must be identical before cleanup, after cleanup and after journal reset/zeroing.
- **Facts.** Success facts add `variant: kubernetes` and the reviewed `kubernetes_version`; the policy requires `kubeadm`, `kubelet` and `kubectl` at exactly that version.

A confined read-only inventory examined the real template root raw copy (VMID 100, sha256 `85f6257e…`). It used no network, dropped all capabilities, ran as UID 1000, used a read-only bind and a read-only mount, and ran no guest code. The frozen `7580c4a` code **refused** that image, failing closed as designed. These rules record what was observed and why each relaxation is safe:

Build/installer overrides are removed. Exact hashes and actions live only in the parent review file |

The template also **apt-holds** `cloud-init`, `openssh-server`, `qemu-guest-agent`, `snapd` and `kubernetes-cni` (image-builder), in addition to the three Kubernetes packages. That is the retained package policy, recorded here for consumers. **Consumers must `apt-mark unhold` these packages to receive their security updates**, then re-hold them if desired. The sanitizer does not change holds.

The probes are deliberately narrow heuristics. They are now informed by the real read-only inventory above, but this source has not been run against the template. Runtime acceptance is still required and is **not** claimed by source or tests:
1. Actual guarded inventory and review file for the stopped template.
2. Capsule tool support check (`part_get_parttype`, `part_list`, `readlink`, `findfs_uuid`, raw conversion).
3. Sanitize, then a fresh independent read-only postscan.
4. A SeaBIOS root-only cold boot with fresh cloud-init: SSH/QGA/grow, exact K8s/CRI binaries and pre-join kubelet behaviour, with no join or NodeReady claim. It must also show that `builder` is in no supplementary group (`id builder` shows only `builder`) and that `sudo -l -U builder` grants nothing under the active sudo-rs.
5. **snapd re-registration:** two independently cold-booted clones of the sanitized export must get **different** snapd serials and device keys. snapd must be healthy (`snap changes` shows no error), or must re-register without error. **Until this passes, the image is not accepted.**
6. Private publish, explicit public setting and an anonymous full three-file pull.

## Cold-boot acceptance through the PVE API

Items 4 and 5 above are automated by `images/vm_export/coldboot.py` (`python3 -m vm_export.coldboot run`), which the export workflow runs as its `coldboot` stage after the postscan. The state file is kept outside the runner's temp directory (`$HOME/.proxcloud-vm-export-coldboot/<run>` on the export runner), and the workflow's `recover` step repeats `python3 -m vm_export.coldboot cleanup` from it: always at the end of the run, and at the start of the next run for anything still not recorded clean. Item 6 is the workflow's `publish` and `verify` jobs. It uses the same least-privilege token as the template builds. There is no root, no `pvesh`, no SSH to the hypervisor and no guest-exec. The token reaches a VM only through the `pc-templates` pool ACL, so a VM outside the pool answers 403 exactly like a missing one.

What a run does, in order:

1. Reads a **sealed** `sanitize-run.json` of the requested variant and re-hashes the sealed disk (regular, single-link, not writable, at most 8 GiB).
2. Draws a random **run token** and takes two snapshots: the **protected set** (every guest the token can see, with its status and config digest) and the storage's volume list. It refuses if a test address already appears in any visible guest's `ipconfigN`/`netN`, if the import file name already exists, or if two reserved VMIDs (default `9290-9299`) aren't free. A VMID is free when no guest holds it and it owns no volume on the storage. `/cluster/nextid` is used for the first part because it also sees guests the token can't read. If the token may read it, the free space on the API node's root disk is checked too, because `pveproxy` spools the whole upload there.
3. Uploads the disk to `<storage>:import` as `pc-export-<sha12>-<run>.qcow2`, a streamed multipart upload. PVE verifies the sha256. The upload's task is polled on the node named in its task id (the API node), not on `--node`.
4. For each of two clones: writes the state file, creates a VM with only `vmid`, `pool` and the run name `pc-export-test-<sha8>-<run>-<a|b>` (tags on a create are checked on `/vms/<id>` and get 403; a name is not), waits for the create task, then writes the tags alone (`pc-export-run-<run>` is the ownership tag), then the hardware (`import-from` the uploaded volume, virtio-scsi-single, serial console, cloud-init drive, virtio NIC on the bridge and VLAN, SeaBIOS, no EFI or TPM state). It verifies 20G, resizes to 30G, and sets cloud-init user `ubuntu`, a static address and **one** ed25519 public key generated by the job. `cipassword` must be absent. Every write names the digest it read and is read back through the ownership guard.
5. Starts both clones, waits for SSH on each test address (BatchMode, a fresh `known_hosts` file per clone, the job key only) and pipes `coldboot_guest.py` to `sudo python3`. The checks are read-only: OS release, cloud-init done without errors, the default user holding exactly the job key, no usable build account, valid machine-id, guest agent, snapd active, registered again and with **no failed change in `snap changes`**, no swap, 30G disk and grown root. The native OS variant adds apt metadata for the base packages and a grown root partition. The Kubernetes variant adds the retained locked `builder`, kubelet enabled, containerd active, the exact `kubeadm`/`kubelet`/`kubectl` version and `crictl`. cloud-init's recoverable warnings are reported as a counter and do not gate. The host key the job connected to must be the one the guest reports.
6. Requires every check true on both clones **and** different machine-id, host key, snapd serial and snapd device key between them. snapd must be present on both: a guest without it proves nothing and is refused.
7. Cleans up: stop, destroy with purge, delete the uploaded file, delete the private key. Then it compares both snapshots again: every guest seen before must still be there with the same status and config digest, nothing new may remain, and the storage must list the same volumes.

**Ownership is the run's, not the artifact's.** The run token is in the VM name, in the ownership tag and in the import file name, so two runs of one sealed disk (concurrent, or a repeated `cleanup` of an earlier one) never share a name. `<state-dir>/coldboot-state.json` is written before each step it describes. Cleanup touches a VM only if that file names it **and** it has the exact run name **and** the run tag **and** it is in the pool, re-read before every mutation. Until the tag write is recorded, the exact run name with no tag at all is accepted instead: the create itself sets the name, so that VM is this run's. A reserved VMID that turns out to hold a VM with another name was never created by this run and is left alone. A template, a locked VM, a snapshot, a pending change or a disk that isn't the VM's own volume refuses. Nothing is adopted or deleted by prefix. The import file is deleted only if this run uploaded it and no visible guest references it. Any failure still runs that guarded cleanup and exits non-zero.

**Cleanup is repeatable and cannot be cancelled.** SIGTERM and SIGINT are ignored once cleanup starts. A failed read or task poll is retried, and what is still there gets a second pass. Terminal outcomes are recorded in the state file, so `python3 -m vm_export.coldboot cleanup --state-dir DIR` repeats only what is left of a cancelled run and does nothing at all for a run recorded clean. A clone that vanished without this run's destroy makes the run fail; for `cleanup` it counts as gone.

**An upload is never reported absent while its outcome is unknown.** If PVE answered with a task, cleanup waits for that task to stop before it lists the storage. If no answer was seen (a lost response, a cancel while waiting), the file is deleted when it is listed and reported `unknown` otherwise; one hour after the upload started, a still missing file counts as absent. Only a refusal by PVE itself or a body this job cut short counts as "not uploaded".

**Output.** `coldboot-result.json` holds the per-clone checks, identities as sha256 only, the cleanup facts, `protected_set.unchanged`, `storage_set.unchanged` and one fixed reason code. It never holds guest text, addresses, keys, VMIDs, the node, the pool or the storage id. The state file does hold node, pool and VMIDs (and the private key while a run is alive): it is not evidence and must not be published.

**Limits.**

- The snapshots cover only what the token can see: guests in the pool and the one storage. A test address held by a guest outside the pool or by a physical host is invisible, so the two test addresses must be reserved for this job. With no visible guest the protected-set comparison says nothing; the result records the count.
- Other jobs that work in the same pool or storage while a run is alive (a portal template update, another build) change the snapshots and fail the run with `protected_set_changed` or `storage_set_changed`. Rerun it.
- A disk that a killed import left in no config can't be removed with this token. It is reported (`volumes_remain`, `storage_set_changed`) and that VMID is not reused until an operator frees it.
- The SSH host key is trust on first use. The check proves that the record came from the peer the job talked to for the whole session, not that this peer is the clone: the guest reports its own key. Reading the key through the hypervisor would need rights this token doesn't have.
- The PVE connection is the one `images/build.py` uses, which doesn't verify the PVE certificate today; the result records `pve_tls_verified: false`.
- The fake-PVE tests in `images/tests/test_vm_export_coldboot.py` cover the guards, not a real boot: a real run of the export workflow on the lab is still the acceptance. Three PVE behaviours are assumed and not yet checked by a lab run of this code: a create may carry a name and an upload's task runs on the API node (both as the portal's Go client does it), and `GET .../pending` lists no pending change for a clone that was configured while stopped.

## Facts are not publication authority

Success emits `kind: OfflineSanitizationFacts`, selected `os`, `variant: os` (or `variant: kubernetes` with `kubernetes_version` for the Kubernetes selector), actual disk SHA256, length, virtual size and six boolean checks matching the exporter check names. These are **bounded observations under this curated policy**, not proof that every filesystem byte is secret-free and not a `CleanExportReceipt`. No source identity, run reference, request binding, host path, VMID or private infrastructure provenance is included. No facts are produced after a failing stage; a partial disk on failure must never be consumed.

The parent must stream only the fixed verified final QCOW2 bytes to a **private** spool before capsule stop, stop and prove the **exact** cgroup/container has terminated with no surviving writer, and only then verify/seal/promote those exact bytes. A reviewed parent exporter can bind the facts and sealed digest to the request in the separate receipt schema. Neither successful stdout nor an on-disk facts file authorizes public publication. This script does not stream disk bytes, stop its own capsule, promote output, connect to PVE/GHCR or alter visibility.

## Honest limitations and outstanding acceptance

This is a curated sanitizer, not an arbitrary compromised-image scanner. It does not claim secure erase of inode slack, ext4 metadata remnants, arbitrary allocated files, bootloader/EFI file contents, BIOS bootloader sectors, unpartitioned gaps/tail sectors, certificates, application databases, custom service credentials, unusual account homes or an adversarial filesystem. Journals and free-space zeroing address a concrete known historical-data issue; they do not establish absence of every possible secret. Standard root/boot/EFI files outside the cleanup/scanned set remain. A new layout, application-bearing image, unsupported OS or uncertain provenance needs a new review, not a broader command-line option.

All hashes and isolation controls require independent operator verification. Before public release, inspect the quarantined export for residual build credentials/network data and complete an isolated **full-copy cold boot** proving fresh cloud-init tenant key/password injection, regenerated host keys/machine-id, network setup, root growth, APT usability, SSH and guest agent. Source build/APT/smoke acceptance and read-only source inspection are not sanitized-export boot acceptance. No changes to existing templates/provider pins/customer VMs are implied.

[Pure fake tests](<../images/tests/test_vm_sanitize.py>) model file cleanup, password replacement, symlink refusal, OS/layout validation, scoped negative scans, metadata refusal and journal/zero ordering. They invoke no subprocess, appliance, real VM image, network or credential source. They run in normal CI and offline with process creation patched to fail. Fake methods validate only the policy shape; they do not prove installed API support, physical zeroing, filesystem health, bootability, containment or publication readiness. Parent-run synthetic/image validation, if subsequently authorized, must be recorded separately with exact tool/source identities and limits.
