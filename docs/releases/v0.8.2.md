ProxCloud v0.8.2 is a patch release on top of `v0.8.1`. It adds no large feature. It warns about a site layout that drops tenant traffic to the platform. It releases a credential that used to stay behind. It fixes what the production acceptance of `v0.8.0` found in the two consoles.

## Highlights

- **Warning for a closed tenant path.** The managed-services Check has a new row, `tenant-path`. It warns when one Proxmox node both translates tenant traffic and hosts the platform's machines. The product does not repair that layout.
- **Faster token cleanup.** The Proxmox token of a deleted tenant Kubernetes cluster is revoked minutes after the delete, on every install. It no longer waits for a provider sync, the periodic job that brings the portal's records in line with Proxmox.
- **A Ready card you can act on.** It shows the platform's addresses and says what a tenant cannot use yet. It downloads a one-hour kubeconfig of the platform cluster and prints the commands that open the two ArgoCD instances.
- **Customer console fixes.** Among them: a network's Servers and Subnets tabs, snapshot delete after a rollback, backups and the serial console. The full list is under What changed.
- **Housekeeping.** New sandbox template image pins, and dependency updates of the operator console's build.

The platform bill of materials (BOM) is the list of exact versions a managed-services platform runs. The BOM of this release is `0.8.2`. It pins what `0.8.0` and `0.8.1` pin: only the `release` line differs, and no chart, image or download changes. The release also carries the BOMs of `0.8.0` and `0.8.1`, for the platforms those releases installed.

## Upgrade

These steps upgrade from `v0.8.1`. From `v0.8.0`, also follow the [upgrade steps of v0.8.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.8.1): they still apply.

1. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first, and nothing else is run by hand. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.2/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.8.2
   ./proxcloud-up.sh upgrade v0.8.2
   ```

2. On a site with managed services, run the Check (System → Managed services) and read the new row `tenant-path`. A warning does not fail the Check and changes nothing by itself.

3. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| Managed services, and `tenant-path` warns | Read ["The path from tenants to the platform"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.2/docs/managed-services.md#the-path-from-tenants-to-the-platform) before tenants create clusters or databases. |
| An installed platform | Nothing. It stays on its BOM (0.8.0 or 0.8.1). Step 4 of the Managed services page shows the 0.8.2 BOM as a newer release that is not available to an installed platform yet. That is the intended state, and this release needs no **Apply this release**. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). |
| An install without the scheduler, where tenant clusters were deleted on `v0.8.1` | Start one provider sync after the upgrade: `POST /api/v1/admin/job/external-service/sync`. Clusters deleted before the upgrade have no release job, so their Proxmox token goes with the provider sync, as before. |
| The new platform kubeconfig | Expect a new download each time: it is valid for one hour. Each download writes its service account (`proxcloud-break-glass`, for emergency access) and that account's roles on the platform cluster again. The kubeconfig of the seed, the VM that manages the platform cluster, is unchanged. |
| Scripts against the API | No answer was taken away. `CREATE_BACKUP` on a server now answers the new archive's id. `GET_SERVERS` on a network answers a list where it was refused. |

## What changed

### Managed services

- **Check row `tenant-path`.** It reads the site layout and warns when tenant connections to the platform network would be dropped. It never fails and opens no connection, so `ok` is not proof. The [guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.2/docs/managed-services.md#the-path-from-tenants-to-the-platform) has the rule, the two supported layouts and what to do with workers that did not join.
- **Ready card: where the platform is.** It lists four addresses: the API of the seed (the VM that manages the platform cluster), the API of the platform cluster, the load balancer range and the node range. It prints the `kubectl` commands that open the two ArgoCD instances. No ArgoCD gets an address in this release.
- **Ready card: what a tenant cannot use yet.** It says "Offers no Kubernetes version yet" and "New projects do not get this provider". Each has a link to where it is put right. Nothing is published or attached for you.
- **Download platform kubeconfig.** The kubeconfig works for one hour and each download is audited as `BREAK_GLASS` (emergency access). It reads the cluster without its Secrets, forwards a port in `argocd` and reads ArgoCD's initial admin password. Through ArgoCD its holder can still change the cluster. See ["After the install"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.2/docs/managed-services.md#after-the-install).
- **Port-forward with the platform kubeconfig.** It is no longer refused on its first request. An installed platform cluster gets the corrected rule with the next download of the kubeconfig. The seed kubeconfig was not affected.

### Kubernetes

- **Token release after a cluster delete.** A delete, and a project teardown, now queue a job that runs with or without the scheduler. It revokes the cluster's Proxmox token and releases its addresses once the delete cascade is over and the cluster's machines are gone. After 24 hours it gives up and the provider sync does the release. See ["Deletion and orphan finalization"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.2/docs/managed-k8s.md#deletion-and-orphan-finalization).
- **A worker that has not joined.** After 15 minutes the customer console tells the tenant to contact the operator. It also says how to replace the machine once the cause is repaired: reduce the count by one and raise it again. A group of one is raised first.
- **Create form defaults.** The Kubernetes create form starts on the lowest version offered, with high availability off. It used to preselect the newest version and three control planes.

### Customer console

- **Network tabs.** A network's Servers tab lists the servers with a NIC on it. Its Subnets tab shows the subnet on a site without the scheduled sync.
- **Snapshots.** A snapshot delete right after a rollback asks Proxmox up to three times for the VM's config lock before it answers `409`.
- **Backups.** `CREATE_BACKUP` answers the new archive's id, and the console asks before it starts a backup.
- **Roles and Rebuild.** The role form shows a name the server accepts and states the rule. Rebuild offers the project's own images, like Create.
- **Hidden pages.** A page the menu hides (volume snapshots, S3 access keys) no longer opens by its URL.
- **Shares.** The Create share dialog warns when the file server is inside a network the site keeps tenant networks out of.
- **Serial console.** A session ends on the page when its server was stopped or restarted. The console opens on the Serial tab when the server's display is its serial port, as on cloud images.

The API side of these fixes is described in the [cloud integration guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.2/docs/cloud-integration.md).

### Sandbox and build

- **Sandbox template images.** The twelve `sandbox-*` images are pinned by tag and digest to their builds of 2026-11-16. The pin file is in no image of the portal.
- **Operator console build.** `@tailwindcss/vite` 4.3.5 and `@vitejs/plugin-react` 6.3.0.

## Verified on a lab

Run on 2026-11-18 on one lab Proxmox VE cluster, over the platform that the published images of `v0.8.0` had installed. The portal was upgraded with `./proxcloud-up.sh upgrade` to the build `dev-03bc9f3` of `main`. That build is this release without the sandbox image pins, the port-forward fix, the changelog and the release commit.

- **The platform kept working.** `status.bom` stayed the 0.8.0 one, the 14 Applications were Synced and Healthy, the plan had 0 changes, and the Check passed with 20 rows.
- **The `tenant-path` row, in two cases.** `ok` for a VLAN default zone, and a warning for a `simple` default zone. The warning did not fail the Check. The row reads the configuration: no path was measured.
- **The token release job, for a plain delete.** With the scheduler off and no provider sync, the job revoked the token and its seven ACL rows at its first attempt. That was 2 minutes 53 seconds after the delete.
- **The Ready card's data and the platform kubeconfig**, at the API and with `kubectl` 1.35.10. The token's claims give it one hour, and the audit row held no token. Secrets, `pods/exec`, a delete and a port-forward outside `argocd` were refused. Both ArgoCD commands worked on the platform cluster and on the seed.
- **Two customer console fixes, at the API.** `GET_SERVERS` on a network answered `200` with an empty list. A new network's row held its subnet details without a sync.
- **Outside the lab.** One production site was upgraded to the released `v0.8.1` on 2026-11-18. Its installed platform stayed on its BOM: the plan had 0 changes, and the apply succeeded and set `onboot` on the platform's machines.

## Not verified

- **Anything on the published artifacts of this release.** The lab ran a build of `main` on a platform installed by `v0.8.0`. A platform installed by `v0.8.1` or by this release, an apply on this release, and an installer or Helm install of it were not run.
- **The port-forward fix.** The lab build still had the old rule. That a port-forward opens on its first request with the new rule rests on a test against a fake cluster.
- **Every customer console fix that needs a tenant server.** The lab had no capacity for one. Not run:
  - a snapshot delete after a rollback;
  - the id that `CREATE_BACKUP` answers;
  - the serial console changes;
  - the image list of Rebuild;
  - a Servers tab with a server in it.
- **Other customer console fixes.** No page of the customer console was opened on the lab. Not run:
  - the share warning;
  - the role form;
  - a hidden page opened by its URL;
  - the Subnets tab for an older network;
  - the backup confirm dialog;
  - the Kubernetes create form's defaults.
- **The `tenant-path` row beyond the two cases above.** The node-side change of the guide was run by hand on one production site only. The layout with a platform network routed by the node was run nowhere. Not run:
  - the other `ok` cases;
  - an EVPN zone;
  - the warning for a Proxmox that could not be read;
  - the row against a path that is in fact closed.
- **The release job beyond a plain delete.** Not run:
  - a cascade that hangs;
  - a failed release with the management cluster or Proxmox down;
  - a project teardown;
  - an API restart while the job is pending;
  - a leftover VM in the pool;
  - a cluster with a CSI token or an RWX dataset.
- **The Ready card in a browser.** Also not run:
  - a user with the support role;
  - the `409`, `502` and `503` answers of the kubeconfig route;
  - the line "Offers no Kubernetes version yet";
  - the token after its hour;
  - a login to either ArgoCD.
- **Texts, dependencies and images.** Not run:
  - the new text for a worker that has not joined;
  - any page of the operator console after its dependency updates;
  - the sandbox template images of the new pins.
- **Earlier releases.** Everything `v0.8.0` and `v0.8.1` say is not verified still holds, except what is listed as verified here.

## Known issues

- **A standalone volume can lose its name at create.**
  - **What happens:** a volume created without a server gets a small holder VM. When Proxmox is slow to list that VM, the create answers `200` with a row that has no `id`. The volume is missing from the tenant's list until the next provider sync, which then names it after its disk (`vm-<vmid>-disk-0`).
  - **Who is affected:** a tenant who creates a volume without a server. Seen once on a lab under load; the same code is in `v0.8.0` and `v0.8.1`.
  - **What to do:** nothing is lost but the name: the disk and its size are right. Not fixed in this release.
- **Workers do not join on some site layouts.**
  - **What happens:** tenant connections to the platform network are dropped. The control plane becomes ready and no worker joins, and tenants cannot reach managed databases.
  - **Who is affected:** a site where one Proxmox node translates tenant traffic and also runs the platform machine that owns the address. The platform network must also be reached over the site's router. A node translates tenant traffic in a `simple` tenant zone, or as an exit node of an EVPN zone. A one-node site is this case; a VLAN tenant zone is not. Found on a production site; not reproduced on a lab.
  - **What to do:** read the Check row `tenant-path`, then use one of [the two layouts that work](https://github.com/mutex-solutions/proxcloud/blob/v0.8.2/docs/managed-services.md#the-path-from-tenants-to-the-platform). One of them is a change on the node itself, by hand and lost at a reboot. A repair by the product is planned for `v0.9.0`.
- **A node group cannot be scaled to 0.**
  - **What happens:** a worker that never joined stays "not joined" after its cause is repaired, and a count below one is refused.
  - **Who is affected:** a tenant whose node group has a worker that never joined.
  - **What to do:** raise the group's count by one and reduce it again once the new worker is ready, once per dead worker. This needs quota for one more worker. Which machine a scale-down removes is Cluster API's choice. Only scale-up then scale-down was run.
- **"Needs attention" stays on such a node group.**
  - **What happens:** the flag stays until a new machine is healthy. Repairing the cause does not clear it.
  - **Who is affected:** the same tenants. On an install without the scheduler the flag appears, and goes away, only when an operator starts a provider sync.
  - **What to do:** replace the worker as above. Without the scheduler, start a provider sync afterwards.
- **Seed ISOs of servers created before `v0.8.0` are never swept.**
  - **What happens:** when such a server is deleted, its seed ISO (`pcseed-v1-<...>.iso`) stays on the seed store for good. It holds the server's user data.
  - **Who is affected:** a site with servers created before `v0.8.0`.
  - **What to do:** clean it up by hand as root on a node, once its server is deleted, with the commands below.
  - **Not verified on a lab:** the cleanup by hand, that a server created on `v0.8.0` or later is swept, and the sweep itself.

  ```sh
  pvesm list <seed store> --content iso | grep pcseed-v1-
  grep -l <file name> /etc/pve/nodes/*/qemu-server/*.conf   # prints nothing for a leftover
  pvesm free <volume>                                       # only for an ISO older than a day that no VM names
  ```
