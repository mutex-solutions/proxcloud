ProxCloud v0.11.0 is the release after `v0.10.2`. It brings highly available load balancers: a load balancer now runs on a pair of appliance VMs that share one public address, and a managed Kubernetes cluster can give its Services of type LoadBalancer a public address on such a pair. It was prepared by two release candidates and two lab drills. Its code is that of `v0.11.0-rc.2`.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this release is `0.11.0`. Against `0.10.2` it moves one thing: the cluster chart for new tenant clusters, `proxmox-kamaji-cluster` `0.1.16` → `0.1.17`. Against the candidate `0.11.0-rc.2` it moves nothing but its own name.

## Highlights

- **A load balancer is a pair.** A new balancer runs on two appliance VMs: one carries the traffic, the other waits. keepalived moves the public address when the active one fails. On the lab a dead appliance cost 2.8 to 3.5 s and a planned switch 0.7 to 0.8 s.
- **What HA means on one node.** The pair survives the failure of an appliance. It does not survive the loss of the node both run on. Both land on one node on a one-node site, on a tenant network in a `simple` zone, and where the appliance image is on one node only. The balancer's page says so. Two nodes were not run on a lab.
- **What a pair costs.** Two servers, their disks and one public address, billed as ordinary rows of the project. A tenant can still ask for one VM (`ha: false`). A balancer made before this release stays one VM.
- **Services of a managed cluster get a public address.** A load balancer controller runs next to each cluster's control plane. A Service of type LoadBalancer gets its own public address on the cluster's pair. The pair is built at the first Service and billed to the project.
- **Listeners and members follow the Services by themselves.** Ports and nodes need no action. On the lab: a port added to a live Service answered after 16.8 s, a changed node port was followed in 12.7 s, a removed port lost its firewall rule after 9.5 s and left the config after 14.4 s, a second Service had its own address after 32 s and gave it back 33.6 s after its delete, and a new worker was a member 14 s after its Node appeared.
- **Other listeners keep serving through a change.** Through those changes the first port lost 0 requests, and a long-lived connection on it survived six reloads. This holds for listener and Service changes with `externalTrafficPolicy: Cluster` and healthy nodes. Node changes lose requests for seconds: see Known issues.
- **Existing clusters keep MetalLB.** Nothing changes for a cluster made before this release until the operator enables the controller for it. Enabling adds a class and moves no MetalLB address.
- **Docker Compose can serve the gateway listener.** `proxcloud-up.sh install --cluster-gateway <address>` is the listener the controllers call. It is off by default.
- **Sandbox nodes install gVisor again.** The installer's node setup asked apt for a runsc version the suite no longer lists. It now installs the release's own package, pinned by SHA256.
- **The first candidate's two faults are fixed and shown.** Replace appliances took an address down for 458 s on `v0.11.0-rc.1`, and a stopped appliance was not started again. On `v0.11.0-rc.2` three replaces under load cost one switch of 0.7 to 0.8 s each, and a stopped appliance was started by the next sync three times of three.
- **Not in this release: UDP listeners and TLS termination.** Both are planned for the next release, "complete layer 4".

## Upgrade

These steps upgrade from `v0.10.2`. From an older release, read the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) first: their steps and cautions still apply. The figures are one lab's sample, not a promise for a site.

1. **Check the platform's BOM first.** The move is planned from the BOMs `0.10.1` and `0.10.2` and their candidates, and from the two candidates of this release. A platform on an older BOM (`0.8.0` to `0.10.0` and their candidates, all on Kubernetes 1.35.10) is refused by this build. Move it to `0.10.1` first with the `v0.10.1` build, both parts, as the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) describe.

2. **Upgrade the portal.** On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. `compose.yaml` did not change since `v0.10.2`. On the lab the upgrade between the two candidates took 27.6 s, and PostgreSQL, Keycloak and Traefik kept their containers. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.11.0
   ./proxcloud-up.sh upgrade v0.11.0
   ```

   - **A new load balancer is a pair from now on.** Each one costs two servers, their disks and one address. A tenant who wants one VM sends `ha: false`.
   - **Existing balancers are not touched.** Their config, their firewall rules and their one VM stay. There is no conversion: a pair is a new balancer, with a new address.
   - **Each sync now asks every appliance whether HAProxy serves its config**, and pushes only where it does not. A serving balancer is not pushed at the upgrade. This was shown for balancers made on a candidate; for one made on `v0.10.2` it rests on tests.

3. **Run the platform upgrade. It is record only.** Open System → Managed services and read the plan in step 4. From the BOM `0.10.2` it lists two changes and refuses nothing:

   | Change | From → to | Class |
   |---|---|---|
   | `release` | `0.10.2` → `0.11.0` | record only |
   | `tenantCharts.kubernetes` | `proxmox-kamaji-cluster` `0.1.16` → `0.1.17` | record only |

   Type `upgrade <installation name> to 0.11.0`. There is one action, with no parts.

   - **What it does.** It records the new release and writes chart `0.1.17` on the Kubernetes provider. Clusters created after it get the new chart.
   - **What it does not do.** It replaces no machine, syncs nothing and writes nothing on Proxmox. The platform cluster stays on chart `0.1.16`. No tenant cluster changes chart, and none loses MetalLB.
   - **How long.** The same two rows took 39.6 s on the lab (to the first candidate). The one-row run between the candidates took 8.5 s and restarted no VM. The run to `0.11.0` itself was read as a plan, not run.

4. **Give the site what load balancers need.** Skip this step and nothing breaks: every cluster keeps MetalLB alone, and a tenant's new balancer needs only the first three items.

   - **An untagged public bridge on every node.** A public network is a bridge name and nothing more. The appliance's NIC is plugged on it with no VLAN tag, and the bridge must exist under that name on every node an appliance can land on. Where the public range is a VLAN on a trunk, make a bridge for that VLAN on every node and name that bridge. A public network that is an SDN vnet is refused for a pair.
   - **The appliance image on every node.** `config.lbImage` of the compute provider, default `debian-13`. Where it is on one node only, both appliances land there.
   - **Packages.** A stock image gets `haproxy`, `socat`, `keepalived` and `iproute2` from apt at first boot. A site with no egress bakes them into the image, which also shortens every build.
   - **A route from the platform network to the portal host on port 8444.** The controllers run on the platform cluster and call the gateway listener. On Compose, turn the listener on with the address of this host that the platform cluster's nodes reach:

     ```sh
     ./proxcloud-up.sh install --cluster-gateway <address>
     ```

     On the lab the command took 14 to 19 s and recreated only the API container. Keep the volume `gateway`: it holds the listener's key and self-signed certificate, and database backups do not hold it. Without the route no controller reaches the gateway; its cluster page says it has not reported, and nothing else breaks. Block volumes stay off on Compose. See ["Optional features" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0/deploy/compose/README.md#optional-features).
   - **The provider settings.** On the compute provider, a public network with a gateway (`config.network.publicNetworks`). On the Kubernetes provider, `config.cluster.loadBalancer`: that public network and the flavor of the appliances. The form calls them **Load balancer public network** and **Load balancer flavor id**.
   - **Quota.** The built-in project quota is five public addresses. Raise it where a cluster needs more Services (Known issues).

5. **New clusters get the controller by themselves** when every gate holds: the portal has a gateway URL and the controller image (Compose: `--cluster-gateway`; the installer chart: `api.csiGateway`), the provider pins chart `0.1.17` (step 3), the workers are the project's own, and the project may use the public network. Such a cluster runs in default mode: a Service without a class gets a public address, and MetalLB serves only class `proxcloud.io/internal`. NGINX Gateway Fabric then takes one public address per Gateway. When a gate does not hold, the cluster is made as before, with MetalLB alone, and the API log says which gate.

6. **Optional: enable the controller on an existing cluster.** The operator's **Load balancer** dialog (provider → clusters) runs **Enable load balancer controller**, in class-only mode: only Services of class `proxcloud.io/lb` get the product's balancer, and no MetalLB address moves. It moves the cluster to the provider's chart, so run step 3 first. See ["How a cluster lands on Proxmox"](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0/docs/managed-k8s.md#9-how-a-cluster-lands-on-proxmox).

   ```text
   POST /api/v1/admin/service/{kubernetesProviderId}/k8s-clusters/{clusterId}/load-balancer
   ```

7. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.11.0-rc.1` or `0.11.0-rc.2` | The plan has one change, the release, record only. Type `upgrade <installation name> to 0.11.0`. Read, not run. |
| A load balancer pair made on `v0.11.0-rc.1` | Run a services sync right after the portal upgrade. On the lab such a pair refused every connection while its row read `ACTIVE`, and the first sync on the corrected code repaired it in 5 s. Its files stay mode 0666 until its next config change or Replace appliances. |
| A platform on the BOM `0.10.1` or `0.10.1-rc.2` | The plan has four changes: the two above and cert-manager `v1.20.2` → `v1.21.3` on the seed and on the platform cluster. Back up the cert-manager resources first, as the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) say. Read, not run. |
| A platform on the BOM `0.10.1-rc.1` with its upgrade finished | Five changes: those four and the platform cluster's chart `0.1.15` → `0.1.16`. No machine is replaced. Read, not run. |
| A platform that stands in the replacement of its machines toward `0.10.1` or one of its candidates | Press **Retry** first: it goes on to that BOM, which this build carries. Then upgrade as above. |
| A platform on an older BOM | Refused (step 1). |
| Load balancers made before this release | Nothing changes: one VM, the same config and firewall rules. |
| Tenant Kubernetes clusters made before this release | Nothing changes: they keep their chart and MetalLB until step 6. |
| A project that needs more than five Services of type LoadBalancer | Raise its `floatingIps` quota first (Known issues). |
| A site with no public network for cluster load balancers | Leave `config.cluster.loadBalancer` empty. Every cluster keeps MetalLB alone. |
| Sandbox nodes of a site installed with the Ansible installer | The node setup now installs runsc `20261116.0` from the release's own package. Not run on a lab. |
| A site installed with the Ansible installer | The app chart sets the controller image where `api.csiGateway` is set. The installer's ProxCloud pin is `v0.11.0`. Not drilled. |

## What changed

Since `v0.10.2`: seven merged pull requests with product changes (#415 to #418, #420, #424, #425).

### Load balancers

- **A pair of appliances** (#415). `ha` on create, true by default. Two VMs share one public address by VRRP over the project network, run the same HAProxy config, and the standby gets every config first. Status is `ACTIVE`, `DEGRADED` or `DOWN`, with the reason. See ["High availability"](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0/docs/cloud-integration.md#high-availability-a-pair-of-appliances).
- **Replace appliances.** A tenant action that rebuilds both appliances from the current image, the standby first, with one planned switch. It is the way to new packages and a new image.
- **Health checks, PROXY protocol v2 and allowed sources** on every balancer: per pool an HTTP or TCP check, per listener the source networks, written as firewall rules.
- **A config is recorded only when the appliance serves it** (#424). The apply reloads HAProxy and wants every bind of the file to be a listening socket. Each pass checks it again and pushes where it does not hold.
- **Stopped services and stopped appliances are started** by the pass that sees them (#424, #425). The message of a `DEGRADED` pair names the cause.
- **The services sync keeps running when an appliance is down** (#425). A stopped VM is known to have no guest agent; its project is synced. See ["What an unproved inventory holds back"](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0/docs/vm-inventory-safety.md#what-an-unproved-inventory-holds-back).
- **Two billing fixes.** An appliance whose build failed no longer stays behind, and an address owned by a balancer is no longer taken for an orphan.

### Managed Kubernetes

- **The gateway accepts a cluster's load balancer state** (#416). `PUT /lb/v1/state` on the gateway listener, with a credential per cluster. Only a hash of its secret is kept.
- **A load balancer controller per cluster** (#417). It runs on the platform cluster next to the control plane, in the image of the API. Every 10 s it sends the cluster's Services and nodes; the portal builds and updates the pair. Refusals reach the tenant as Events on the Service.
- **New clusters get it in default mode** (#418), with cluster chart `0.1.17`. Existing clusters can be enabled one by one, in class-only mode.
- **A cluster's lock lasts one minute**, an unchanged controller call starts no pass, and a refused credential is logged with its cluster and reason and audited (#425). A controller that idles costs about 19 Proxmox calls a minute on the lab; it was 132 on the first candidate.
- **The consoles show a cluster's load balancer**: its addresses, appliances and member health, read-only.

### Docker Compose

- **`--cluster-gateway <address>`** serves the gateway listener on `<address>:8444` and nowhere else, with a certificate the API makes itself. `--no-cluster-gateway` turns it off.

### Sandbox nodes

- **A new sandbox node installs gVisor again** (#420). The node setup downloads the release's own runsc package, checks its SHA256 and installs it: runsc `20261116.0`.

### Release

- **BOM `0.11.0`.** The pins of `0.11.0-rc.2`: those of `0.10.2` but the cluster chart for new tenant clusters. No chart of the product changed since its tag. This build carries the BOMs of `0.8.0` to `0.11.0-rc.2` (sixteen) as previous BOMs.
- **App chart `0.11.0`.** The installer pin and the default of `proxcloud-up.sh` name `v0.11.0`. The installer's k3s and Kubernetes pins stay at `1.35.10`.

## Verified on a lab

One lab, every appliance on one node, Ubuntu 26.04 appliances. The first drill ran on `v0.11.0-rc.1` on 2026-11-21, the second on `v0.11.0-rc.2` on 2026-11-22. Both were checked afterwards by a read-only audit. These are one lab's figures, not a promise for a site.

- **On rc.1, not run again:** pair create and its firewall rules; 15 failovers 0.7 to 3.5 s; a deleted vrrp rule restored by the sync; stop / hard reboot of an appliance refused; five Services on five addresses of one pair; refusals as Events (UDP, no node port, loadBalancerIP, quota); class internal on MetalLB; PROXY protocol v2; an allowed source range; policy Local health checks; idle TCP 330 s; foreign Nodes refused and audited; suspended project; gateway down during a delete; enable on an existing cluster; one floating IP row per address, traffic counted once.
- **Upgrade rc.1 to rc.2:** portal 27.6 s; platform run record only, 8.5 s, no VM restarted; serving balancers not pushed by the upgrade or by two syncs; an appliance rc.1 left not serving repaired by the first sync.
- **Replace appliances under 10 requests a second, three times:** one switch of 0.7 to 0.8 s each (rc.1: 458 s), 12.5 to 13.5 min, never `ACTIVE` with one appliance.
- **A new pair and a new single balancer** answer before their first `ACTIVE`; config files 644, scripts 755.
- **Stopped services:** stopped keepalived or HAProxy started by the next sync; HAProxy on another config reported and loaded again by the next sync; a config change held while apt runs on the master, applied after, 0 requests lost.
- **A stopped master, three times:** failover 2.9 to 3.4 s, started by the next sync, `ACTIVE` one sync later, the sync's other passes ran. A paused master: failover 3.0 s, `ACTIVE` one sync after the resume.
- **A cluster's controller:** port added (answers after 16.8 s), targetPort changed (0.5 s), nodePort changed (12.7 s), port removed (rule gone 9.5 s, out of the config 14.4 s), second Service on its own address (32 s) and given back (33.6 s); 0 requests lost on the first port and its long-lived connection kept through six reloads.
- **Workers 1 to 2 and 2 to 1:** the member follows 14 s after the Node (with the loss under Known issues).
- **Lock and load:** converge lock about 58 s; a change cut by an API stop is live after 190 to 209 s (rc.1: 24.7 min). Controller idle: 18.6 Proxmox calls a minute (rc.1: 132). A dead master of a cluster's pair: 3.5 s, started by the product 31 s later.
- **A refused credential:** one log line with cluster and reason, one audit row. Clean-up: no object, no quota, the Proxmox cluster as before.

- **The consoles:** no page was opened; every step went through the API.
- **A production site with a public network:** one lab, a test range on a plain bridge.

## Known issues

### Not there yet

- **No UDP listeners.** A UDP port of a Service is refused with the Event `UDPNotSupported`, and a tenant's balancer takes TCP and HTTP only. Planned for the next release, "complete layer 4".
- **No TLS termination.** A listener is plain TCP or HTTP: TLS passes through to the members. Planned for the same release.
- **Layer 4 and plain HTTP only.** There is no routing by host or path. Run an ingress controller or a Gateway behind the balancer for that.
- **One appliance pair per cluster.** All Services of a cluster share one pair, each with its own address. There is no second pair and no pair per Service.
- **IPv4 only.** An IPv6 Service is refused, with an Event.

### Requests lost

- **A worker added or removed loses requests for seconds.** A new worker is a member as soon as its Node exists, before it is Ready, and HAProxy takes a new member for healthy until two checks fail. On the lab a scale-up lost 22 of 44 requests in 4.4 s, and a scale-down 52 in 10.3 s. The same happens at every worker replacement: a machine roll, a Kubernetes upgrade of the workers. Measured once per direction. Clients should retry.
- **A member that is down gets traffic again after every reload**, until its checks fail. It hits a Service with `externalTrafficPolicy: Local` on a cluster where a node has no local endpoint, and any Service while a node is dead. On the lab such a Service lost 11 to 12 requests in 2.2 to 2.4 s at each change of another Service of the same cluster. NGINX Gateway Fabric's chart default is `Local`.
- **A switch cuts open connections.** There is no connection state sync between the appliances.
- **One node is not node HA.** Where both appliances run on one node, the loss of the node takes the address down.

### What a tenant should know

- **In-cluster clients do not pass the pair.** A pod that calls a Service's public address is answered inside the cluster (`ipMode: VIP`). It sees neither a pair outage nor the source ranges. Test a Service from outside the cluster. Only a PROXY protocol Service (`ipMode: Proxy`) goes out through the pair.
- **Five public addresses by default.** The built-in project quota is `floatingIps: 5`. In default mode every Service of type LoadBalancer and every Gateway takes one; the sixth waits with `QuotaExceeded`. Raise the project's quota or the provider's default quota.
- **A cluster's first Service shows its address before it answers.** On the lab the address was in the Service's status 3 min 12 s before anything answered on it. Tools that wait for the address (`helm --wait`, Argo CD health, external-dns) take the Service for ready too early. The Event stays `EnsuringLoadBalancer` until it serves.
- **The first Service waits for the pair.** 6 min 37 s on the lab until it answered, with packages from apt. Later Services of the cluster took about 32 s.
- **Builds and replaces take minutes.** 7 to 13.5 min on the lab: a stock image runs its own first-boot upgrade, and the platform waits for the package manager. A Replace of a pair is two builds in a row, with one switch of under a second. An image with the packages baked in shortens it; not measured.
- **No grace for an address.** A Service deleted and created again gets a new address.
- **Cluster appliances skip the server quota.** Only the addresses count against the quota (`floatingIps`).

### What an operator should know

- **What backups hold.** A Proxmox backup or snapshot of an appliance holds its disk: the HAProxy config with the listeners and the members' addresses, and the keepalived config. It holds no key and no password in this release. Do not restore an appliance from one: its config comes from the portal, and Replace appliances builds a fresh one. The portal's `backup` writes the database dump and a copy of `.env` side by side. The dump holds every balancer's row and a hash of each cluster's gateway secret. `.env` holds the key that opens the provider credentials in the dump. Whoever has both files has the portal's secrets: keep them together, off the host, and readable by you alone. Neither holds the volume `gateway`.
- **A tenant's pair is repaired by the services sync.** A stopped appliance or a stopped service on it is started at the next sync, not at once. The other appliance carries the traffic meanwhile. A single appliance has no other one: on the lab its address refused connections for 33 s, until the sync.
- **A stopped appliance of a cluster's pair is started within about 70 s** (31 s in the lab's one run).
- **A paused VM makes its project's inventory unproved** for as long as it is paused. This includes every project the operator suspends. The load balancer pass and the provider's other passes run anyway; the project's own rows are frozen, and the provider's seed sweep and sandbox sweep are held back. Not new in this release.
- **A paused appliance is not resumed by the platform**, and the row of a pair whose former master is paused says "Both appliances hold the address" instead of the cause.
- **A change cut by an API stop waits about 3 minutes.** A restart or an upgrade of the API in the middle of a cluster balancer's change left it waiting 190 to 209 s on the lab. Traffic was not touched. A Replace's mark can outlive a dead API for up to 60 minutes.
- **A config change waits while the package manager runs on an appliance.** The other appliance takes it first; the row reads `DEGRADED` until both have it.
- **An address released before a sync saw it is not billed.** Its floating IP row is made by the services sync.
- **A new cluster's first MetalLB address can take about 10 minutes.** The pool's first apply fails while MetalLB's webhook starts, and is tried again later. Not new in this release.
- **A large state is refused whole.** The gateway takes at most 64 KiB per call. A cluster with many Services (around 45 or more, with several ports or long source ranges) may pass that before the 50-Service limit; then no Service of the cluster is updated.
- **A gateway URL that is a host name** leaves the controller's egress port open to any address. Use an IPv4 address.
- **Enable during a cluster's delete** can mint the cluster's credential again. Do not enable a cluster that is being deleted.

### From v0.10.2, still true

- **A platform on a BOM before `0.10.1` cannot take this move.** It upgrades to `0.10.1` with the `v0.10.1` build first.
- **From the BOM `0.10.1` there is no way back.** The move carries cert-manager `v1.21.3`, and cert-manager documents no downgrade. Back up its resources first.
- **The installer path is not drilled.**
- **A seed backup on an NFS store can be readable by everyone.** `chmod 600` the archive and its log after each backup.
- **Cilium is still outside its own support matrix on 1.36.** This release does not move it.
- **The tenant cluster chart's cert-manager addon stays at `v1.20.2`.** It is off by default.
- **Earlier releases.** The other known issues in the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) still hold.
