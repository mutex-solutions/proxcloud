ProxCloud v0.8.1 is a patch release on top of `v0.8.0`. It adds no large feature. It makes a site that runs `v0.8.0` safe to upgrade, now and later, and fixes what the first production site and the acceptance of `v0.8.0` found.

## Highlights

- **Installed platforms survive upgrades.** A managed-services platform installed by `v0.8.0` keeps working after this and every later upgrade. With `v0.8.0` alone, any later release would have refused every apply on it (`409 bom_unsupported`).
- **Tenant Kubernetes create on per-store ACL rows.** On a site whose portal user or token has ACL rows of its own on single stores, every create answered `502` while the Check was green. The Check now names the failing path, and the managed-services script repairs it.
- **An honest DHCP flag.** A tenant network answers `dhcp: false` in a zone that runs no DHCP server, and `enableDhcp: true` there is a `400`.
- **Platform machines start with their node.** Every VM of the platform gets `onboot`, and the Check has a new row `machines`.
- **Security group rules fixed.** A delete could remove another rule, a deny rule was stored as an allow rule, and an egress rule kept its CIDR in the wrong field.
- **Volume rows fixed.** A rebuilt server no longer keeps the row of its old boot disk. A volume keeps its name, id and bill item when it moves to another server.

The platform bill of materials (BOM) is the list of exact versions a managed-services platform runs. The BOM of this release is `0.8.1`. It pins what `0.8.0` pins: only the `release` line differs, and no chart, image or download changes.

## Upgrade

These steps upgrade from `v0.8.0`.

1. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first, and nothing else is run by hand. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.1/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.8.1
   ./proxcloud-up.sh upgrade v0.8.1
   ```

2. On a site with managed services, run the Check (System → Managed services).

3. Where the Check row `privileges:kubemint` fails, run the managed-services script again as root on a Proxmox node, once per portal token. The script is in step 2 of the Managed services page. On an installer site in split mode, run this instead:

   ```sh
   make upgrade
   ```

4. On an installed platform, press **Apply this release** once, at a time of your choice. It sets `onboot` on the platform's machines. Until then the Check row `machines` warns and names each VM with this command:

   ```sh
   qm set <vmid> --onboot 1
   ```

5. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A site where the portal's user or token holds an ACL row of its own on a store, a zone or a vnet | Do step 3. The row `privileges:kubemint` fails there, though it passed on `v0.8.0`, and it names the path that lacks the right. Until the script has run, tenant cluster creates answer `409`. An install or apply of the managed services stops at its first stage (`preflight_failed`). |
| An installed platform | Nothing has to be installed again. It stays on the 0.8.0 BOM, and **Apply this release** runs with that BOM. Step 4 of the Managed services page shows the 0.8.1 BOM as a newer release that is not available to an installed platform yet. That is the intended state, not an error. |
| A stopped platform machine | Start it by hand. **Apply this release** does not start it. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). |
| Scripts that call the security group actions | Send `ruleId` to `DELETE_RULE`, as `LIST_RULES` returns it. `pos` and an id of the shape `<group>-<position>` answer `400` or `409`. `ADD_RULE` answers `400` for a field it cannot store (`remoteGroupId`, `action`, `log`, `priority`). |
| Egress rules written before this release | They are listed with remote "any". Delete each and add it again. |
| Scripts that create networks | Do not send `enableDhcp: true` in an EVPN zone or in a `simple` zone without a DHCP server: it is a `400`. Existing rows are corrected by the next provider sync. |
| A log collector on the API log | Change a parser that expected plain text lines for `backend request failed`. Every line of the API log is JSON now. |
| A guest with VM id 9999 on the Proxmox cluster | Read the warning `csi-vmid` in the Check and in Test connection before you destroy that guest. |

## What changed

### Managed services

- **A release carries the BOMs of earlier releases.** From this release on, a release carries the BOM of each earlier release back to `0.8.0`. An installed platform stays on the BOM that installed it: the Check, an apply and Remove run with that BOM's pins. Moving an installed platform to a newer BOM is not in this release.
- **Platform machines start with their Proxmox node.** Only the seed had `onboot`, so after a node reboot every tenant control plane and database stayed down. Every install and apply now sets `onboot` on each VM of the platform. No start order is set, tenant clusters' machines are not covered, and a stopped VM is still started by hand. See ["After a Proxmox node reboots"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.1/docs/managed-services.md#after-a-proxmox-node-reboots).
- **Check row `machines`.** It warns for a platform VM that is stopped or has no `onboot`, with the command.
- **Check row `csi-vmid`.** It warns when a guest has VM id 9999. Proxmox counts every CSI volume as a disk of VM 9999, so destroying that guest with its unreferenced disks would remove them. The row never fails. See ["VM id 9999 and the CSI volumes"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.1/docs/managed-services.md#vm-id-9999-and-the-csi-volumes).

### Kubernetes

- **Create on a site with ACL rows on single stores.** The managed-services script and installer stage 10 now write the role `ProxCloudKubeMint` next to each such row, on a store, a zone or a vnet. The Check row `privileges:kubemint` reads the paths a create writes and names the one that fails. See [the permissions guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.1/docs/proxmox-permissions.md#a-row-of-the-portals-own-on-a-store-or-a-zone).
- **A create that Proxmox refuses for a permission says so.** It answers `409` with the reason, where it answered `502 The compute backend is unavailable`. See ["Troubleshooting"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.1/docs/managed-k8s.md#5-troubleshooting).

### Networking

- **DHCP flag.** The network create now reads the zone in Proxmox. Where the zone runs no DHCP server, the network answers `dhcp: false` and no DHCP range is written. The next provider sync corrects existing rows.
- **`enableDhcp: true` is refused where no DHCP server runs.** That covers an EVPN zone, a VLAN zone and a `simple` zone without DHCP. Leave the field out or send `false`. Neither console sends it.
- **A `simple` tenant zone without DHCP.** Set `"dhcp": false` on a zone of `config.network.zones`. Tenant Kubernetes clusters and load balancers can then use its networks on a site without EVPN or VLANs. It applies to a zone that does not exist yet.

### Security groups

- **Deleting a rule is safe.** A rule was deleted by its position, so a delete from a stale page could remove a different rule. `DELETE_RULE` now takes only `ruleId`. When the id no longer names a rule the answer is `409` and nothing is deleted.
- **`ADD_RULE` refuses what it cannot store.** `remoteGroupId`, `action`, `log` and `priority` were accepted and dropped, so a deny rule was stored as an allow rule. They are a `400` now. The protocol, the ports and the remote are checked before Proxmox is called.
- **Egress rules.** An egress rule stored its remote CIDR as the rule's source; it is the destination now. A server's outbound traffic is always allowed, so an egress rule restricts nothing, and the API now says so in `result.warning`. Egress filtering is not in this release.
- **Rule table.** The console's rule table has a Direction column, and no longer shows an empty cell for "any protocol" and "any remote".

The rule actions are described in the [API guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.1/docs/api.md).

### Volumes and servers

- **Rebuild.** Rebuild, restore from backup and snapshot rollback now reconcile the project's volume rows in the same request. The volume list no longer shows the old boot disk twice, and the quota no longer counts it twice.
- **Attach to another server.** A volume keeps its name, id and bill item. An attach while a change of volume type is still copying answers `409`.
- **A server with VM id 9999.** Deleting it no longer destroys the CSI volumes.

### Operator console and logs

- **Audit of failed creates.** A cloud resource create that is refused or fails leaves an audit event with outcome `FAILURE`. The operator's Audit page shows what the caller was answered and the backend's own reason.
- **API log.** Every line is JSON, and the `backend request failed` line carries the request id of the answer (`X-Request-Id`).

### Security

- **A security group rule's remote must be a CIDR or an address.** The value was passed to Proxmox as written, so a tenant could name a cluster IP set or alias as the source of a rule.

### Release process

- **CI checks the previous BOMs too.** The weekly check and the release gate compare each carried BOM with the registries. See ["Previous BOMs"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.1/docs/ci-release.md#previous-boms).

## Verified on a lab

Run on 2026-11-18 on one lab Proxmox VE cluster. The portal ran the published images of `v0.8.0` and installed a platform from the 0.8.0 BOM in one run without a Retry (37 minutes 45 seconds). It was then upgraded with `./proxcloud-up.sh upgrade` to the build `dev-751a190` of `main`. That build is this release without its release commit and its changelog.

- **The platform kept working.** The plan had 0 changes and no blocker, the Check was green with the two new rows, and **Apply this release** succeeded in 6.6 seconds. `status.bom` was unchanged.
- **Tenant Kubernetes create on per-store ACL rows.** With a stand-in row on the boot store, the Check failed on `privileges:kubemint` and named the store and the script. The tenant's create answered `409` with the new text, and nothing was left on Proxmox.
- **The DHCP flag**, on a network of a VLAN zone and of a `simple` zone made without DHCP. Both answered `dhcp: false`, and `enableDhcp: true` was a `400` in both.
- **`onboot`**, on the four running machines of the platform that `v0.8.0` had installed. The apply set it, and the `machines` row then read ok.
- **Security group rules, at the API.** The egress warning, the `400` and `409` answers, and a delete by the current id that removed that rule only.
- **Volumes, in part.** The `csi-vmid` row read ok, and a standalone volume was created and deleted. See Known issues for what its first create showed.

## Not verified

- **Anything on the published artifacts of this release.** The lab ran a build of `main` whose BOM pins the same versions as 0.8.0. So the lab does not show an apply that keeps older pins while the release carries other ones.
- **Volume attach, detach and rebuild.** The lab had no capacity for a tenant server. The volume fixes, and the delete of a server with VM id 9999, rest on their tests alone. The warning case of `csi-vmid` was not provoked.
- **Platform machine cases.** Not run: a stopped platform machine, a machine the token cannot read, a node reboot with `onboot` in place, and an install on this release from the start.
- **The production shape of the ACL fix.** Not run: an older `ProxCloudPlatform` row on a store, a row held through a group, and the script's new lines that repair them. They ran against a fake `pveum`.
- **Other cases.** Not run: `enableDhcp: true` in an EVPN zone, a rule-list digest that is stale at Proxmox, the console pages of every change above, and an installer or Helm install of this release.
- **Earlier releases.** Everything `v0.8.0` says is not verified still holds, except what is listed as verified here.

One observation from the lab: the install clones three node VMs at the same time. That load restarted containers of another Kubernetes cluster whose VMs share the nodes' disks. All recovered. This is the behaviour of `v0.8.0` and is unchanged.

## Known issues

- **A standalone volume can lose its name at create.** When Proxmox is slow to list the volume's holder VM, the create answers `200` with a row that has no `id`. The volume is missing from the tenant's list until the next provider sync, which then names it after its disk (`vm-<vmid>-disk-0`). The disk and its size are right. Seen once on a lab under load; the same code is in `v0.8.0`. Not fixed in this release.
- **Workers do not join where one node both translates tenant traffic and hosts the platform machines.** It happens on a Proxmox node that translates tenant traffic and also runs the platform machine that owns the address. Such a node is the VM's node in a `simple` tenant zone, or an exit node of an EVPN zone. The platform network must also be reached over the site's router. A one-node site is this case; a VLAN tenant zone is not. The control plane becomes ready and no worker joins. Managed Kubernetes works on such a site only after a change on the node itself, outside the product. This release neither detects nor repairs it; `v0.8.2` adds a Check warning and the node-side steps. Found on a production site; not reproduced on a lab.
- **Seed ISOs of servers created before `v0.8.0` are never swept.** When such a server is deleted, its seed ISO (`pcseed-v1-<...>.iso`) stays on the seed store for good. It holds the server's user data. Clean it up by hand as root on a node, once its server is deleted. The cleanup itself is not verified on a lab.

  ```sh
  pvesm list <seed store> --content iso | grep pcseed-v1-
  grep -l <file name> /etc/pve/nodes/*/qemu-server/*.conf   # prints nothing for a leftover
  pvesm free <volume>                                       # only for an ISO older than a day that no VM names
  ```
