ProxCloud v0.10.2 is a patch release on top of `v0.10.1`. It moves cert-manager from `v1.20.2` to `v1.21.3` on the seed and on the platform cluster of a managed-services platform, by one upgrade run that replaces no machine. It brings cert-manager's fix for a high-severity advisory.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this release is `0.10.2`. Against `0.10.1` it moves cert-manager from `v1.20.2` to `v1.21.3` on the seed and on the platform cluster, and nothing else: the same k3s, Kubernetes version, node image, providers, other third-party charts and product charts. It pins what the candidate `0.10.2-rc.1` pins.

## Highlights

- **cert-manager `v1.20.2` → `v1.21.3`.** On the seed and on the platform cluster, by an upgrade run from the BOM `0.10.1`. cert-manager is the first third-party chart an upgrade moves.
- **A security fix.** `v1.20.2` is affected by [GHSA-8rvj-mm4h-c258](https://github.com/advisories/GHSA-8rvj-mm4h-c258) (high), fixed upstream since `v1.20.3`. `v1.21.3` has the fix.
- **A light run.** No machine is replaced, nothing is written on Proxmox, the seed's k3s is not touched and no seed backup is asked for. On the lab the run took 3 min 8 s, issued no Certificate again, and no tenant probe failed.
- **No way back.** A platform does not go back to a BOM, and cert-manager documents no downgrade. Back up the cert-manager resources first: see step 3.
- **Inside its support table again.** cert-manager 1.21 lists Kubernetes 1.33 to 1.36, so it covers the platform's 1.36.6 and the installer's 1.35.10. `v1.20.2` lists 1.32 to 1.35.
- **A new Check row `certificates`.** It warns, by name, about cert-manager Deployments that are not available and Certificates that are not Ready. It is a warning only: no run waits on it.
- **The installer path moves too.** `cert_manager_chart` is `v1.21.3`: stage 40 moves at `make upgrade`, stage 50 at the next `make install`. No drill covers this path.

## Upgrade

These steps upgrade from `v0.10.1`. From an older release, read the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) first: their steps and cautions still apply. The figures of steps 2 to 6 are one lab's sample, not a promise for a site: one drill on a lab with a seed of one VM, a platform cluster of four nodes on Kubernetes 1.36.6, one tenant cluster and one database.

1. **Check the platform's BOM first.** The move is planned from the BOM `0.10.1` (and from its candidates and from `0.10.2-rc.1`). A platform on an older BOM (`0.8.0` to `0.10.0` and their candidates, all on Kubernetes 1.35.10) is refused by this build: the move would change k3s and Kubernetes too, and a third-party chart moves only in an upgrade that changes neither. Keep the portal on `v0.10.1` and move such a platform to `0.10.1` first, both parts, as the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) describe. Then come back to step 2. One production site of one Proxmox node made that move on 2026-11-20. What it showed:

   - **Move older databases to chart 0.5.2 first.** A database made before database chart 0.5.2 has one instance and a PodDisruptionBudget that allows no eviction. The plan's part "platform" is then blocked with `drain_blocked`, which names it. Read the platform part's blocking list before you start the seed part, and bump each such database with the operator route below. On CloudNativePG 1.30.1 the bump did not restart the database, and `drain_blocked` left the plan at once. The database is still down while its machine is replaced: back it up first.

     ```text
     # {id}: the Databases provider; {clusterId}: the database's Application name (GET .../db-clusters lists them)
     POST /api/v1/admin/service/{id}/db-clusters/{clusterId}/bump-chart
     ```

   - **One-node figures of the roll.** No image import: the node image was already a published template of Template updates. Each clone took 6 to 8 s on NVMe. The platform API was away 67 s at the control plane's hand-over and never during a clone. Every tenant API server was away 104 s in the `kamaji` unit, the database 75 s in the `dbaas` unit. The whole part took 13 min 14 s.
   - **"Error deleting Node" during the hand-over is expected.** While the platform API is away at the control plane's hand-over, the run's item can read "DeletingNode: Error deleting Node, please check controller logs for errors". On the site it showed for about 50 s and cleared by itself. Do not delete that Node by hand.
   - **Make the seed backup readable by root only.** A `vzdump` of the seed to an NFS store came out mode 777, its log 644. The archive holds the seed's secrets. After each backup, as root on the node: `chmod 600 <archive> <archive's .log>`, then `ls -l` both.

2. Upgrade the portal. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. The Compose file did not change since `v0.10.1`: on the lab the upgrade took 24 s, and PostgreSQL, Keycloak and Traefik kept their containers. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.10.2
   ./proxcloud-up.sh upgrade v0.10.2
   ```

3. The platform is not changed by step 2. It stays on its BOM and keeps working. Before you move it, do these things.

   - **Back up the cert-manager resources.** Upstream's upgrade guide advises it, and there is no way back. Download the seed kubeconfig and the platform kubeconfig (System → Managed services), then run this once with each:

     ```sh
     kubectl get certificates,issuers,clusterissuers -A -o yaml > cert-manager-backup.yaml
     ```

   - **Read the Check row `certificates`.** It should be `ok`. A warning names each Deployment or Certificate that is not right. Fix a Certificate that is not Ready on its own first: the run does not wait on it, and a Certificate that is not Ready keeps the certificate its Secret holds.

4. Open System → Managed services and read the plan in step 4. From the BOM `0.10.1` (or `0.10.1-rc.2`) it lists three changes and refuses nothing:

   | Change | From → to | Class | Stage | Wave |
   |---|---|---|---|---|
   | `release` | `0.10.1` → `0.10.2` | record only | none | |
   | seed `cert-manager` | `v1.20.2` → `v1.21.3` | chart | `seed-platform` | 1 |
   | platform cluster `cert-manager` | `v1.20.2` → `v1.21.3` | chart | `workload-platform` | 1 |

5. Run the upgrade. Type `upgrade <installation name> to 0.10.2`. There is one action, with no parts.

   - **What it does.** ArgoCD syncs cert-manager to the new chart on the seed, then on the platform cluster. It applies the CRDs in place (`v1` stays the only version) and removes what the new chart no longer renders (the Role and RoleBinding `cert-manager-tokenrequest`).
   - **The three Deployments roll together.** The controller, the cainjector and the webhook each start their new pod and remove the old one only when the new one is Ready. On the lab every Deployment had a Ready pod at every look, and the new pods were Ready 20 to 53 s after their ReplicaSet (images pulled from quay.io).
   - **The wait.** The wave waits until ArgoCD reports the three Deployments rolled (Healthy against the new chart) and the sync, the chart's `startupapicheck` Job included, Succeeded. cert-manager is recorded at `v1.21.3` only after its wave passed. The Job may start before the new webhook pod is Ready: on the lab it did, on both clusters. The wait on the Deployments does not depend on it.
   - **How long.** 3 min 8 s on the lab, with no retry: 98 s for the seed, 84 s for the platform cluster, every other stage under 4.1 s.
   - **What stops serving.** Nothing on the lab: no webhook dry run was refused, and the tenant API and the database had no failed look. A seed of one VM is slow for about 30 s while it pulls the new images (answers up to 3.1 s, one client timeout of 4 s); nothing was refused.
   - **Certificates stay.** None of the 11 Certificates (5 on the seed, 6 on the platform cluster) was issued again: each kept its revision, serial and start date. The CA bundles of the webhooks did not change.
   - **What it does not do.** It replaces no machine, writes nothing on Proxmox, does not touch the seed's k3s and restarts no pod of a tenant. The webhooks of Cluster API and Kamaji keep their certificates.
   - **If the check fails.** The sync fails, and the run starts it once more. When that one fails too, the stage fails `component_unhealthy` with what the sync failed on. Fix the cause, then **Retry**. Not run on a lab.

6. Read the Check row `certificates` again. It should be `ok` on both clusters. On the lab, after the move, a new Certificate was Ready in about 1 s, and a renewal of a provider's serving certificate took 1.5 to 1.7 s, with the new CA on the webhooks within 3.4 s.

7. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.10.2-rc.1` | The plan lists one change, the release, record only. Type `upgrade <installation name> to 0.10.2`. Not run on a lab. |
| A platform on the BOM `0.10.1-rc.2` | As from `0.10.1`: the same three changes. Read, not run. |
| A platform on the BOM `0.10.1-rc.1` with its upgrade finished | The plan lists five changes and replaces no machine: the three above, the tenant chart (record only) and the cluster chart `0.1.15` → `0.1.16` (chart, stage `cluster`, wave 3). Read, not run. |
| A platform that stands in the replacement of its machines toward `0.10.1` or one of its candidates | Press **Retry** first: it goes on to that BOM, which this build carries. This release does not take its place, and the plan shows its move as refused until the replacement is finished. Then upgrade as above. |
| A platform on an older BOM | Refused (step 1). Each cert-manager row says: finish an upgrade to a release with this one's Kubernetes version (1.36.6), k3s (`v1.36.6+k3s1`) and node image, with that release's build, then start this one. That release is `v0.10.1`. |
| Tenant Kubernetes clusters and databases | Nothing moves for them. The tenant cluster chart's cert-manager addon (off by default) stays at `v1.20.2`. |
| A site installed with the Ansible installer | `cert_manager_chart` is `v1.21.3`. Stage 40 moves the management cluster's cert-manager at `make upgrade`; its wait can pass on the old Deployment, so read the Application `cert-manager` for Synced and Healthy at `v1.21.3`. Stage 50 moves the services cluster's at the next `make install`, where plugin-barman-cloud also uses it (two Certificates and an Issuer). Back up the cert-manager resources first. No drill covers this path. See [Install, "Stages"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2/docs/install.md#stages). |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |

## What changed

Since `v0.10.1`: the changes of the release candidate `v0.10.2-rc.1` (#407, #409, #410), and the texts its drill and a production site asked for.

### Managed services

- **An upgrade may move cert-manager** (#407). On the seed and on the platform cluster, cert-manager moves as a chart of the product does: only to a version whose BOM entry lists the installed one in `upgradeFrom`, as class `chart` in its wave. It moves only in an upgrade that changes no k3s, Kubernetes version or node image; next to such a change each cert-manager row is refused with a sentence that says what to do. Every other third-party chart stays refused. See ["A cert-manager move"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2/docs/managed-services.md#a-cert-manager-move).
- **The Check row `certificates`** (#407). `ok` when cert-manager's three Deployments are available on the seed and on the platform cluster and every Certificate there is Ready; a warning that names each one that is not. It never fails and no run waits on it. See [the API reference](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2/docs/api.md).
- **cert-manager `v1.21.3` pinned** (#409, #410). The chart mirror publishes it unchanged from charts.jetstack.io; the BOM pins its mirror digest on both clusters, with `upgradeFrom: ["v1.20.2"]`. See ["What this release moves"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2/docs/managed-services.md#what-this-release-moves-and-what-it-refuses).
- **The plan's text for a cert-manager row gives the lab's figures.** It no longer says "not measured", and it says what holds the wave: the three Deployments rolled and the sync Succeeded.
- **Upstream's breaking items of 1.20 → 1.21 do not touch the product.** The chart no longer renders the `cert-manager-tokenrequest` Role and RoleBinding, the `cert-manager-edit` role loses Challenge and Order writes, and three monitoring values are gone. The product sets `crds.enabled` only and uses none of them.

### Guides

- **Databases made before chart 0.5.2 block the machine roll.** The guide now says to bump them first, before the seed part, and that on CloudNativePG 1.30.1 the bump does not restart the database. See ["Upgrade to Kubernetes 1.36.6"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2/docs/managed-services.md#upgrade-to-kubernetes-1366).
- **One-node figures of the roll.** The guide gives the production site's figures next to the lab's, and that no image is imported when the node image is already a published template.
- **"Error deleting Node" during the hand-over.** The guide says it is expected and clears by itself.
- **The seed backup's file mode.** The guide says to `chmod 600` the archive and its log after each backup by hand. See ["Seed backup"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2/docs/managed-services.md#8-credentials-and-the-seed-backup).

### Security

- **[GHSA-8rvj-mm4h-c258](https://github.com/advisories/GHSA-8rvj-mm4h-c258) (high): a direct ACME Challenge resource could bypass an Issuer's DNS01 solver policy and use a ClusterIssuer's DNS credentials.** Affects cert-manager `1.20.0` to `1.20.2`; fixed since `v1.20.3`. `v1.21.3` has the fix. A platform keeps `v1.20.2` until it has run this move.

### Installer

- **`cert_manager_chart` is `v1.21.3`** (#410). Stage 40 and stage 50 follow the platform BOM's pin. See the installer row of step 7.
- **The clusterctl image keeps its cert-manager file at `v1.20.2`** until its next rebuild. clusterctl skips a cert-manager that answers, whatever its version; cert-manager is always installed first.

### Release

- **BOM `0.10.2`.** The pins of `0.10.2-rc.1`: those of `0.10.1` but cert-manager. No chart of the product changed since its tag, so no chart version moved. This build carries the BOMs of `0.8.0` to `0.10.2-rc.1` (thirteen) as previous BOMs.
- **App chart `0.10.2`.** The installer pin and the default of `proxcloud-up.sh` name `v0.10.2`. The installer's k3s and Kubernetes pins stay at `1.35.10`.

## Verified on a lab

One drill on the published images of the candidate `v0.10.2-rc.1` (2026-11-21), on one lab with a seed of one VM and a platform cluster of four nodes on Kubernetes 1.36.6, checked afterwards by a read-only audit.

- **The portal upgrade.** From `v0.10.1` to `v0.10.2-rc.1` by the script, in 24 s, with PostgreSQL, Keycloak and Traefik kept.
- **The plan from `0.10.1`.** Three rows, no parts, no seed backup asked; and the Check row `certificates`.
- **The run.** From `0.10.1` to `0.10.2-rc.1` in 3 min 8 s with no retry: 98 s for the seed, 84 s for the platform cluster.
- **cert-manager `v1.21.3` on the seed and on the platform cluster.** The CRDs moved in place (`v1` only, storedVersions `[v1]`), the tokenrequest Role and RoleBinding were removed, the three Deployments rolled with a Ready pod at every look, and the `startupapicheck` Job ran in both syncs.
- **Nothing issued again.** No Certificate was issued again (11 of 11), no webhook refused a request (cert-manager's and Cluster API's), the CA bundles did not change, and ArgoCD did not loop.
- **Tenants.** A tenant cluster at 1.36.6 and a database had no failed look. No tenant pod restarted, no machine was replaced and nothing was written on Proxmox.
- **After the move.** A new Certificate in about 1 s, a renewal in 1.5 to 1.7 s with the new CA on the webhooks within 3.4 s, and a new tenant cluster and database created and deleted.

## Not verified

- **The installer path.** Stage 40 and stage 50, new installs, and the services cluster's barman plugin with `v1.21.3`.
- **The moves from `0.10.1-rc.1` and `0.10.1-rc.2`.** Their plans were read, not run.
- **The refusal on a real platform on a BOM from `0.8.0` to `0.10.0`.** A unit test only.
- **A site that already has the `v1.21.3` images.** The `startupapicheck` Job may then test the old webhook; the wait on the Deployments still holds.
- **A failed `startupapicheck`.** The path to `component_unhealthy` and the Retry after it.
- **A seed of more than one node, and a production site of one node.** The figures are one lab's.
- **Any way back.**

## Known issues

- **There is no way back.** cert-manager documents no downgrade, and a platform does not go back to a BOM. Back up the cert-manager resources before the run (step 3).
- **Platforms on a BOM before `0.10.1` cannot take this move.** They upgrade to `0.10.1` with the `v0.10.1` build first. A database made before database chart 0.5.2 blocks that move's part "platform" until it is bumped (step 1).
- **The installer path is not drilled.** Stage 40's wait can pass before ArgoCD has synced the new version. Read the Application yourself.
- **A seed of one VM is slow for about half a minute** while it pulls the new images. Nothing was refused on the lab.
- **A seed backup on an NFS store can be readable by everyone.** On one site it came out mode 777. `chmod 600` the archive and its log after each backup (step 1).
- **Cilium is still outside its own support matrix on 1.36.** Cilium `1.18.16` lists Kubernetes 1.30 to 1.33. This release does not move it.
- **The tenant cluster chart's cert-manager addon stays at `v1.20.2`.** It is off by default; it moves with a later tenant chart version.
- **cert-manager 1.20 reaches end of life when 1.22 is released.** A platform that has not made this move stays on `v1.20.2`. 1.22 comes in a later release, from `v1.21.3`.
- **Earlier releases.** The other known issues in the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) still hold, except the one about cert-manager outside its support matrix, which this move closes for a platform that makes it.
