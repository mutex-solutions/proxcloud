ProxCloud v0.12.0-rc.2 is the second release candidate of `v0.12.0`, published as a prerelease. `v0.12.0` offers sandboxes on the managed-services platform: an operator who runs managed Kubernetes and databases from the portal can add sandboxes there, without the Ansible installer. The first candidate was drilled on a lab on 2026-11-26 and was found not fit to become `v0.12.0`: three defects, no placement reached "live", and no sandbox ever started. This candidate carries the fixes. **None of the fixes has run on a lab**: the candidate exists so that the lab can run the drill again. It is not for production. `v0.11.1` stays the current stable release and `latest`.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this candidate is `0.12.0-rc.2`. Its pins are those of `0.12.0-rc.1`: only the release name differs. Against `0.11.1` it moves two things: the platform's own cluster chart, `proxmox-kamaji-cluster` `0.1.16` → `0.1.19`, and a new component, the sandbox chart `proxcloud-sandbox` `0.1.0`, which is installed only where the settings ask for sandboxes.

## Highlights

- **Read "Read these first" under Upgrade before you upgrade.** From `v0.11.1` and from `v0.12.0-rc.1`.
- **Three defects of the first candidate are fixed.** A shared sandbox machine was cut off from its own cluster by the product's own isolation rule. After sandboxes were switched on or off, every next run stopped at its first stage until a provider sync. Outbound port 25 was open from a sandbox machine. See "Fixed since rc.1".
- **What the first drill showed, and what it did not.** The platform upgrade replaced no machine. Both placements were built and removed. From a fenced shared machine no private target answered. But no placement reached "live", and no sandbox started on a lab. See "Verified on a lab" and "Not verified".
- **The platform upgrade replaces no machine.** From the BOM `0.11.1` the plan has three rows, as in the first candidate. From the BOM `0.12.0-rc.1` it has one row, the release name.
- **The portal upgrade restarts the database once.** The Compose file now pins PostgreSQL by digest, so the container is recreated once, on the same volume.
- **Every cluster with a load balancer controller is shown as behind after the portal upgrade**, and is offered an update of that controller. Nothing is applied until someone acts.
- **Seven load balancer fixes**, five of them known issues of `v0.11.1`. Two change an answer on an existing site: a certificate signed over SHA-1 or MD5 is refused at the upload, and a node selector term without a key selects no node.
- **A project's delete is refused while the job scheduler is off** (`409`), where it answered "scheduled" and nothing deleted it.
- **Sandboxes on the managed platform, as in the first candidate.** Two placements: `shared`, a node group of the platform cluster, and `separate`, a hosted cluster of its own. `off` is where every installation starts. The provider is registered disabled, and four release gates and the job scheduler stand before "live".
- **What a shared node group gives up.** Code that escapes a sandbox is root on a machine of the platform cluster, beside every tenant's control plane and database. `shared` is the homelab choice: one operator, no outside tenants. See Known issues.
- **Serverless function code is in this build, switched off.** No BOM pin, no provider can enable it, and no function can be created. The customer console's docs show two new pages for it. Nothing to do at the upgrade.

## Upgrade

Use a lab or another non-production site. Production sites should stay on `v0.11.1` and wait for `v0.12.0`. No duration below was measured on this candidate.

### Read these first, from v0.11.1

1. **The platform upgrade has exactly three rows from the BOM `0.11.1`, and replaces no machine.** The rows: `release`, record only; the platform's own cluster chart `proxmox-kamaji-cluster` `0.1.16` → `0.1.19`, class chart; and `sandbox`, the sandbox chart, class added. From the BOM `0.11.0` there is one more, record only: the cluster chart for new tenant clusters, `0.1.17` → `0.1.19`. No machines row, no parts, no seed backup. **The run proves it itself**: before it syncs anything of the cluster chart, it lets ArgoCD compare the live cluster with chart `0.1.19` and reads the comparison. A machine template or bootstrap template that is new or would change, or a control plane that would change, stops the run with `unexpected_rollout`. Nothing was synced then, every machine runs as before, and the Application `pc-platform` is left at the new chart version without automated sync. The first candidate's drill ran this move on a lab: nothing rolled (see "Verified on a lab").
2. **The portal upgrade restarts the database once** (#485). `compose.yaml` now names PostgreSQL by digest (`postgres:17.12-alpine@sha256:f9cf3e1f0066f0eb0c48707d864f0ac5941e9ff454a072077d97a4d278d07d73`). Compose recreates a container whose image line changed, on every install, whether or not it already runs that build. The container is stopped, removed and started on the same volume: for a few seconds the API and Keycloak have no database, and they connect again by themselves. Both builds are PostgreSQL 17.12, so nothing is dumped and restored. The script takes its backup first, as always. Later upgrades leave the container alone until that line changes again. Not run with the product's stack on a lab: the first candidate's upgrade did not recreate it, because its file had the old line.
3. **Every cluster with a load balancer controller is shown as behind, and offered an update** (#485). The controller runs the portal's own image, and the image's name carries the release. After the upgrade the tenant's cluster page shows "Platform update available" with the words "the load balancer controller only: no machine is replaced". The operator's provider page counts the cluster as behind the pin, with **Update controller** on its row, and **Bump all** moves it. This happens after every later upgrade too. **Nothing is applied by the upgrade itself.** The action replaces the controller's one pod; for that moment a change to a Service of type LoadBalancer waits. No machine is replaced, no appliance is pushed and no address moves. A cluster without the controller is offered nothing.
4. **An existing platform gets nothing of sandboxes until its operator asks, and asking is possible only after the platform's upgrade.** Upgrading the portal changes no platform. On a platform that is still on the BOM of a release before `0.12.0` the page shows no Sandboxes block, and a save with the block answers `400 invalid_installation`, naming the release to upgrade to. The platform upgrade itself builds nothing of sandboxes: no pool, no ACL row, no token, no machine, no Application, no provider. For such a platform nothing more is read or written than before, and its isolation rules stay the four DROPs, byte for byte.
5. **Asking writes on Proxmox, with the portal token.** The pool `proxcloud-sbx`. With `shared`, one ACL row: the platform's Cluster API token `capmox@pve!capi` with `ProxCloudCAPI` on `/pool/proxcloud-sbx`. With `separate`, a token of its own, `capmox@pve!pc-sandbox`, minted as a tenant cluster's token is. Then the sandbox machines in that pool, the VM firewall of each of them, the pool's security groups and IP sets, and, new in this candidate, the isolation rules for the sandbox range in the cluster firewall, written by the run itself. **No new role, no new privilege and no row for root to add.** What the two root scripts must have granted: the portal token's platform role on `/pool` with propagate, `Sys.Modify` on `/`, and for `separate` also `User.Modify` on `/access/groups/proxcloud-kube` and the mint role `ProxCloudKubeMint` (`Permissions.Modify`) on `/storage`, `/sdn/zones` and `/nodes`. A site set up by an older script runs both again as root. The Check's `sandbox` row reads these rights.
6. **A site with the installer's sandbox cluster: creates answer `503` until the first provider sync after the upgrade** (#515). The workers' firewall gets a new generation, because outbound port 25 is now closed. Between the upgrade and the first provider sync the `fence` gate fails, as for any changed rule set, and a live sandbox provider starts nothing new: a tenant's sandbox create answers `503` "Sandboxes are not available on this location right now". Sandboxes that run keep running. Run a provider sync right after the upgrade, or wait for the timed one. Afterwards a worker no longer opens TCP 25 to the internet, and no longer sends an IP protocol other than TCP, UDP and ICMP there. Submission (587, 465) stays open. The length of the window was not measured.
7. **An `ssh-dss` (DSA) public key is refused** (#484). A key pair import answers `400` "ssh-dss (DSA) keys are no longer accepted: use an ed25519, ecdsa or rsa key", where it took the key before. A platform installation whose settings hold such a key under `spec.seed.sshKeys` is answered that the entry "is not an SSH public key": replace it before you save the settings again. OpenSSH itself no longer accepts these keys.
8. **A project's delete is refused while the job scheduler is off** (#485). `DELETE /project/{id}` answered `200` and `SCHEDULED_FOR_DELETION` on such an install, and nothing deleted the project. It now answers the `409` of "Delete now" and changes nothing. A project scheduled under an earlier release stays scheduled and can be cancelled.
9. **Two load balancer answers change.** A certificate signed over SHA-1, MD5, MD2 or RIPEMD-160 is refused at the upload with `400` (#491); on a site whose appliances run Debian 13 such a certificate was served, and a stored one keeps being served. A Service whose `proxcloud.io/lb-node-selector` has a term without a key (`=edge`) loses its members once its cluster's controller is updated (#486): write the key or remove the annotation.
10. **From `v0.11.0`, the upgrade notes of `v0.11.1` still hold.** Read the [notes of v0.11.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.11.1) first. From `v0.11.1` none of them happens again, and no balancer is pushed by this upgrade: each of the seven load balancer fixes changes no appliance's config, and each says so in the changelog.

The same one row holds for a platform that built `shared` or `separate` under the first candidate. Read from the code (`PlanFor` in a test), not run.

That is the first candidate's defect, now said by the gate. On the platform cluster: four agent-sandbox definitions. No run looks for them, because the record of the sandboxes is gone. They do no harm. A new build of `shared` with the same settings takes the pool and the templates over, and the off after it removes all three kinds. The commands to remove them by hand are in the [changelog](https://github.com/mutex-solutions/proxcloud/blob/v0.12.0-rc.2/CHANGELOG.md#unreleased), under "what the upgrade from 0.12.0-rc.1 gives".
5. **The sandbox machines' firewall gets a new generation at the first provider sync**, as in point 6 above. On the lab that drilled the first candidate no provider was ever live, so no tenant met the `503` there.
6. **One Check row more.** `scheduler` is now there while the scheduler runs too, with status ok. A script that counts the rows counts one more.

### Steps

1. **Before the upgrade, look at two things.**

   - **The platform's BOM.** The move is planned from the BOMs `0.10.1`, `0.10.2`, `0.11.0`, `0.11.1`, `0.12.0-rc.1` and their candidates. A platform on an older BOM (`0.8.0` to `0.10.0` and their candidates, all on Kubernetes 1.35.10) is refused by this build. Move it to `0.10.1` first with the `v0.10.1` build, both parts, as the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) describe.
   - **Do not change machine sizes, nodes or node groups together with the upgrade.** Apply such a change before it or after it. Together with the upgrade it is what `unexpected_rollout` refuses.

2. **Upgrade the portal.** On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.12.0-rc.2/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.12.0-rc.2
   ./proxcloud-up.sh upgrade v0.12.0-rc.2
   ```

   - **The database container is recreated once** (point 2 above).
   - **Nothing changes on the platform or on Proxmox by this step.** The platform stays on its BOM. No load balancer is pushed.
   - **On a platform of `0.11.1`: no Sandboxes block yet.** A save with `spec.sandbox` answers `400 invalid_installation`: "Upgrade the platform to release 0.12.0-rc.2 first".
   - **Clusters with a load balancer controller read as behind** (point 3 above). Update them when it suits.
   - **With sandbox workers on the site, run a provider sync now** (point 6 above).

3. **Read the plan.** Open System → Managed services and read the plan in step 4. It refuses nothing. From the BOM `0.11.1` (and from its five candidates) it lists three changes:

   | Change | From → to | Class | Stage | Wave |
   |---|---|---|---|---|
   | `release` | `0.11.1` → `0.12.0-rc.2` | record only | none | |
   | `pc-platform` (seed) | `proxmox-kamaji-cluster` `0.1.16` → `0.1.19` | chart | `cluster` | 3 |
   | `sandbox` (platform cluster) | none → `proxcloud-sandbox` `0.1.0` | added | `workload-platform` | 4 |

   From the BOM `0.12.0-rc.1` it lists one:

   | Change | From → to | Class | Stage | Wave |
   |---|---|---|---|---|
   | `release` | `0.12.0-rc.1` → `0.12.0-rc.2` | record only | none | |

   From the BOM `0.11.0` (and from `0.11.0-rc.1` and `0.11.0-rc.2`) there is a fourth beside the three: `tenantCharts.kubernetes`, `proxmox-kamaji-cluster` `0.1.17` → `0.1.19`, record only.

4. **Run the platform upgrade.** Type `upgrade <installation name> to 0.12.0-rc.2`. There is one action, with no parts, and no seed backup is asked for.

   - **The cluster chart row** (from `0.11.1`). In stage `cluster` the run applies the Application `pc-platform` at chart `0.1.19` without automated sync, waits until ArgoCD has compared the cluster with it, and reads the comparison. When no machine template, bootstrap template or control plane is out of sync, it records the check (`rolloutChecked` in the stage's receipt) and applies the Application as always, automated.
   - **`unexpected_rollout`.** The comparison found a machine template or bootstrap template that is new or would change, or a control plane that would change: Cluster API would replace machines. Nothing was synced and every machine runs as before. If machine sizes, nodes or node groups were changed together with the upgrade, put them back and **Retry**. Otherwise the release is at fault: stop, change nothing by hand and report it.
   - **The sandbox row.** The chart is rendered only for settings that ask for `shared`, so on a platform without the block nothing is synced for it.
   - **What the run does not do** on a platform without sandboxes. It replaces no machine, restarts no pod of a tenant and writes nothing on Proxmox. It makes no pool, ACL row, token, sandbox machine, sandbox Application or sandbox provider.
   - **From `0.12.0-rc.1` with `shared` built**, this run passes stage `cluster`, as every run does, and is the apply that repairs the rules (point 2 of the second list). Not run.
   - **From `0.11.0`** the run also writes chart `0.1.19` on the Kubernetes provider: new tenant clusters get it, and an existing one keeps its chart until its own chart upgrade.

5. **Decide whether to ask for sandboxes.** Skip the rest and nothing changes.

   - **Before.** The datacenter firewall is on: no VM firewall filters a packet while it is off, and the Check's `sandbox` row fails. The job scheduler runs (`PROXCLOUD_JOBS_SCHEDULER_ENABLED`). The two root scripts ran in their current form.
   - **Addresses and a name.** One free aligned CIDR inside the platform network for the sandbox machines, with room for one more machine per node. One address for the sandbox proxy: with `shared` a free address of the load balancer range, with `separate` a free address of the platform network outside every range. A DNS name whose wildcard `*.<domain>` resolves to the proxy address where clients are.
   - **A resolver outside the blocked networks.** A sandbox `dns` inside a blocked or management network, the platform gateway for instance, is dropped by the isolation rules. No Check reads it.
   - **The way from the internet is yours.** A managed platform has no entry appliance. Where a router translates the platform network, it forwards TCP 443 of a public address to the proxy address, and it decides who may reach it.
   - **`shared` is saved only with the tick** under the text on what it gives up.

6. **Save, Check, plan, apply.** Under **Sandboxes** in **Settings**, choose the placement and fill the machines, the range, the proxy address and the domain.

   - **Check** has the rows `sandbox` and `scheduler`, and the `capacity` row counts the sandbox machines and one spare per node. It fails for machines that no run has placed yet and that do not fit.
   - **The plan** lists three rows: `sandbox` (the machines, and how many sandboxes a machine of that size holds), `sandbox-pool` and `sandbox-access` (the ACL row, or the token). For `shared` the `sandbox` row says that the storage plugin's pods on the other machines are replaced once.
   - **The apply** makes the pool and its access, each written once, builds the machines beside the existing groups, syncs the sandbox chart and registers the provider "\<name> Sandboxes", disabled. The run's check lets through the new group's machine templates and nothing else.
   - **The isolation rules are written by the run**, in stage `cluster`, before any machine is made, and read back. For `shared` they hold five ACCEPTs above the DROP of the sandbox range: TCP 6443 to the cluster's API address, and TCP 6443, UDP 8472, TCP 4240 and ICMP to the cluster's node range. No provider sync is needed for them.
   - **The certificate.** The run makes one self-signed certificate for `*.<domain>` and keeps its key sealed. The Ready card offers the certificate for download.

7. **Wait for the fence, then read the gates.** A provider sync writes the VM firewall of each sandbox machine and takes its `unsecured` taint off, about 20 minutes after the machine joined. **Check the release gates** on the Ready card reads the four gates without changing anything. Before the first provider sync one gate fails, `fence`. After a sync and the 20 minutes all four should hold: no lab has shown that yet.

   | Gate | Holds when |
   |---|---|
   | `noderestriction` | The API server refuses a node identity a `node-restriction.kubernetes.io/` label on its own Node |
   | `isolation` | The cluster firewall holds the isolation rules for the sandbox range |
   | `fence` | Every Node that may take a sandbox is a VM of the sandbox pool whose firewall reads back as written, pinned to the Node's address, and no rule of the cluster firewall cuts the machine off its own cluster |
   | `network-guard` | Cilium leaves the CNI config to the network guard and its heartbeat is fresh, on every node that takes sandboxes |

8. **Go live.** On the provider's page under **Cloud providers**, set a price for sandbox minutes, choose a status other than Disabled and save. Attach the provider to projects as the two others.

   - **The save is refused** while a gate does not hold, or while the scheduler is off (`409`). With the scheduler off the answer now names the scheduler and every failing gate with its reason.
   - **The price rule holds a placeholder rate** until you set one, or 0.
   - **Clients must trust the run's certificate** (`SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS` for the JavaScript SDK). An operator's own certificate cannot be stored yet.
   - **No lab has gone this far.** Before a site with outside tenants goes live, a drill must have shown the fence from inside a sandbox, the placement must be `separate` unless the text on `shared` was read and accepted for that site, the router must restrict who reaches the proxy address, and a real invoice must have shown the sandbox line.

9. **Switching sandboxes off.** Disable the provider and let its sandboxes end first: the save of `placement: off` is refused (`409 sandbox_provider_live`) while the provider is not disabled, and so is the run. The apply then deletes the sandbox Application, the four agent-sandbox definitions (each once no object of its kind is left), the machines, the group's templates and its address pool, the fence settings, the pool's firewall groups and IP sets, the ACL row or the token, and the pool. It takes the range's rules out of the cluster firewall itself, so the next apply needs no provider sync. A VM of another owner in the pool makes the run wait and name it.

## Fixed since rc.1

Since `v0.12.0-rc.1`: eighteen merged pull requests, with `main` at `e8094012`, where these notes were closed. The release pull request of this candidate is not counted. A pull request merged after that commit and before the tag is not described here: the list GitHub adds below these notes names it, and the [Unreleased section](https://github.com/mutex-solutions/proxcloud/blob/v0.12.0-rc.2/CHANGELOG.md#unreleased) of the changelog describes it. Every fix below rests on tests with fakes. None ran on a lab.

### The three defects of the first drill

- **A shared sandbox machine was cut off from its own cluster by the product's own isolation rule** (#515). The isolation rules drop the sandbox range towards every blocked network, and the platform's API address and node range are blocked networks. On a Proxmox node where bridged frames pass the forward chain (`net.bridge.bridge-nf-call-iptables` is 1) that rule also saw the frames between the sandbox machine and its own cluster. On the lab's third node the machine could open no new connection to its cluster after the first provider sync: the API, the pod tunnel and the health port timed out, the chart degraded, and no sandbox could go live. The gates read ok all the while. **Now** the rule set holds five ACCEPTs above that DROP, for exactly what the machine's own firewall opens toward its cluster: TCP 6443 to the API address, and TCP 6443, UDP 8472, TCP 4240 and ICMP to the node range. Nothing else opens. Both layers are rendered from one list in the code, and the `fence` gate fails with the rule named when the cluster firewall cuts a machine off. `separate` needs no ACCEPT: its control plane is a load balancer address that is in no blocked network.
- **After sandboxes were switched on or off, every next run stopped at its first stage until a provider sync, the off included** (#515). The run wrote the sandbox range on the provider and left the isolation rules to "the next provider sync". Until that sync the Check's `isolation` row failed and stage `validate` stopped every run. On the lab the off was refused when it was needed, with two machines running, and after a successful off the next apply failed. With the scheduler off nothing healed it. **Now** the run writes the isolation rules itself, in the step that adds the range and in the step that removes it, under the lock a provider sync takes, and reads them back. An `isolation` row that differs only in the installation's own sandbox range is a warning and stops no run. Rules of another owner are never rewritten or removed.
- **Outbound port 25 was open from a sandbox machine** (#515). The notes said closed, and for a sandbox pod it was. The machine's own firewall had one rule for the internet, every protocol and port. **Now** it has three: TCP on every port but 25, UDP, ICMP. A tenant gets submission (587, 465) to a relay of its own and no direct SMTP. This holds for both placements and for the installer's sandbox cluster.

### The drill's other findings

- **An off of `shared` left objects behind** (#514). The group's address pool, its two templates and the four agent-sandbox definitions stayed, and the Application `pc-platform` read OutOfSync from then on. The run now deletes the definitions (each only when no object of its kind is left), then the machines, then the templates and the pool, and takes the access on Proxmox away last.
- **A run repeated its writes on Proxmox** (#514). One run sent the create of the pool 23 times, 22 of them answered `500`, and wrote the ACL row 23 times. The first mint of the `separate` token deleted a token that did not exist. The pool, the row and the token are now read first and written when missing. An apply that changes nothing sends no write to Proxmox.
- **The off of `separate` kept its token for minutes** (#514). The run waited for ArgoCD's next look at an Application whose objects were gone. It now asks ArgoCD to look. The token still goes after that wait, because the Cluster API provider needs it until the cluster's objects are gone.
- **A WARN every ten minutes** (#514). The API logged `sandbox template update: orphan sweep` with a `403` or `401` for a platform's sandbox provider. It no longer looks there.
- **Texts that were not true** (#514, #515). "The four gates fail before the sync": two failed in the first candidate, and one fails now, `fence`. ## Known issues

### What a shared node group gives up

The install page prints this text, shortened here, and saves `shared` only with a tick under it.

- **Code that escapes a sandbox is root on a machine of the platform cluster.** That cluster runs the datastore of every tenant's Kubernetes control plane, every tenant's API server, CloudNativePG and every tenant database, and ArgoCD.
- **The pod network is open to that machine.** It is a Cilium peer and can send packets with any source to any pod. Network policies do not stop it. What protects the targets is their own authentication.
- **The Cilium agent's credential on that machine can create and change CiliumNode objects.** A forged one pulls another node's pod traffic to the escaped machine.
- **The machine also holds** the kubelet's credential, the network guard's (it reads every pod's spec) and kube-proxy's.
- **No address of their own to the internet.** Abuse from a sandbox leaves under your site's public address. This holds for `separate` too.
- **A stolen portal token reaches a node of the platform cluster** through a sandbox machine's console, guest agent or disks.
- **A separate cluster limits the same escape to the sandbox cluster**: other tenants' sandboxes on it, its own control plane's API and the internet.

### Open findings of the fixes

- **Some private addresses are closed to a sandbox machine by its own VM firewall alone.** The cluster firewall's rules cover the provider's blocked networks. An address on the platform bridge that is in none of them is not covered: the load balancer range (MetalLB), another site's network or an older cluster's, and the metadata address. On a node where bridged frames do not pass the forward chain, every address on the platform bridge is held by the VM firewall alone. Closing it needs a new rule and is not decided.
- **Creates answer `503` from the upgrade to the first provider sync** on a site with a live sandbox provider (Upgrade, point 6).
- **With a Proxmox node that does not report its networks, the run waits at the rule step**, the off included.
- **An off whose rule write is refused by Proxmox between its adds and its deletes** leaves both rule sets in place. The next run fails `validate`, and on a site with no project the provider sync refuses too: the rules must then be deleted by hand.
- **A resolver inside a blocked network is dropped** for sandbox machines, and no Check reads it.
- **The `fence` gate judges from the rule list.** It skips a rule with a macro, an alias or an IP set in its source or destination. An operator's own forward DROP above the ACCEPTs fails it, also on a node where bridged frames never reach that rule.
- **A provider sync does not add the ACCEPTs** to a rule set in place that lacks them. An apply does.

### Seen in the first drill, still true

- **Switching `shared` on or off replaces the storage plugin's pod on every other machine of the platform cluster, once.** A mounted volume stays mounted. The plan says so now. A plugin pod can also start on a new sandbox machine for the first minutes, before the rule that keeps it off arrives; the machine still has its `unsecured` taint then.
- **The disabled provider row keeps the mode and the domain of the placement that is gone**, and a kubeconfig whose identity no longer exists.
- **The off's plan does not name the provider settings and the firewall objects it removes.**
- **The token of `separate` lives until its Application is gone**, minutes after the last machine. The run asks ArgoCD to look; what that saves on a real ArgoCD is not known.
- **An operator's cancel leaves the run's record in phase `failed`.**
- **Switching the scheduler on bills the whole current cycle at its first run.** The guide says only that it starts charging usage.
- **While stage `cluster` waits for ArgoCD's comparison, its message can end with "successfully synced"**: the Application's last operation, which can be days old.
- **Cluster API's first delete of a running VM answers `500` once** in the node's log.
- **On a lab with slow disks the cluster's API address was gone for about 30 s during a shared build.**

### Limits

- **A machine of 2 cores holds one sandbox of one vCPU.** Take 4 cores or more for several. The plan's `sandbox` row says the figure for the size chosen.
- **A template of 2 vCPU does not fit a machine of 2 cores.** `code-interpreter-v1` and `mcp-gateway` ask for 2 vCPU. Read in the code, not run.
- **No sandbox registry, no custom templates, no snapshots.** Pause and resume are held on every path.
- **No entry appliance.** The way from the internet to the proxy address is the operator's. With `separate`, the proxy address takes any source on 443.
- **Prices are placeholders** until you set one. Switching the scheduler on starts charging usage.
- **Fixed names.** The pool `proxcloud-sbx` and the token `capmox@pve!pc-sandbox`: two portals on one Proxmox cluster collide.
- **A self-signed certificate only.** Every client must trust the run's certificate.
- **The placement is fixed once built.** It changes only to `off`. The range and the proxy address are fixed as well.
- **`pc-sandbox` is not upgraded in place.** An upgrade that replaces the platform cluster's machines is refused while `separate` exists or is asked for.
- **A first start of a template the machines did not pull ahead waits for its pull.** `python` is pulled from docker.io, the others from ghcr.io.
- **Template images move with a release only.**

### Open findings of the earlier reviews

- **Sandboxes cannot be asked for in the same step as the BOM move.** Upgrade first, then save the block.
- **The sandbox chart's own images carry odd tags.** Chart `0.1.0` pins the runtime at the tag `dev-d26edd2` and the proxy at `v0.11.0-rc.1`, both by digest. With `separate`, the sandbox chart inside `pc-sandbox` is named by version, not by digest.
- **The sync fences every VM it finds in pool `proxcloud-sbx`**, also one that another hand put there. It is closed, never opened.
- **A sandbox machine takes sandboxes about 20 minutes after it joined**, and only once a provider sync ran. With the scheduler off, one operator sync fences once and nothing watches afterwards.
- **"All projects" waits while the provider is disabled.**
- **When the `shared` ACL row is deleted by hand**, the Check's rows `machines` and `boot-store` degrade and the `sandbox` row warns, until the next apply writes it again.
- **No Check reads that the proxy address of `separate` is free.**

### Still true from v0.11.1

So is the project delete with the scheduler off (#485). The others stand. Those an operator meets first:

- **Private keys of certificates** rest encrypted in the database, in `backups/` next to the copy of `.env` that opens them, and in clear on each appliance's disk.
- **Only `proxcloud.io/lb-*` annotations are read.** A Service that asks for an internal balancer under another cloud's annotation name gets a public address.
