ProxCloud v0.10.0-rc.1 is the first release candidate of `v0.10.0`, published as a prerelease. It holds everything `v0.10.0` is planned to bring since `v0.9.1`, and it exists so that a lab can run it: nothing of it has run on a lab yet. It is not for production. `v0.9.1` stays the current stable release.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this candidate is `0.10.0-rc.1`. Against `0.9.1` it moves the cluster chart to `0.1.15` and the database chart to `0.5.2`. It keeps Kubernetes `1.35.10` and k3s `v1.35.10+k3s1`.

## Highlights

- **The Proxmox console opens on the graphical display.** A VM made by ProxCloud opened on the serial terminal, an empty page until a key was pressed. New templates now use the standard display, and the serial terminal is still there.
- **Delete a withdrawn template.** The Imported templates table has a Delete button on withdrawn rows. No `qm destroy` on the node is needed.
- **An upgrade can replace the seed's k3s.** A release that names a newer k3s is no longer refused: the upgrade run replaces k3s on the running seed, and asks for a seed backup first. This candidate's BOM does not move k3s, so no upgrade to it does this.
- **An upgrade can replace the platform cluster's machines.** A release that names a newer Kubernetes is no longer refused. This ships dark: this candidate's BOM keeps Kubernetes `1.35.10`, so upgrading to it replaces no machine. The first real replacement comes with a later BOM.
- **An address for the platform's ArgoCD.** Opt-in: one address of the load balancer range, open to the operator networks you name, over HTTPS with a self-signed certificate.
- **Not run on a lab yet.** Nothing in this candidate: see below.

## Upgrade

Use a lab or another non-production site. Production sites should stay on `v0.9.1` and wait for `v0.10.0`.

These steps upgrade from `v0.9.1`. From an older release, read the [notes of v0.9.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.1) and the [notes of v0.9.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.0) first: their steps and cautions still apply.

1. Upgrade the portal. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0-rc.1/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.10.0-rc.1
   ./proxcloud-up.sh upgrade v0.10.0-rc.1
   ```

2. Let one services sync run. It runs every 15 minutes; on an install without the scheduler start it with `POST /api/v1/admin/job/external-service/sync`. It moves the console display as the list below says.

   - **At once, at that sync:** the templates that a Template updates import of this portal holds (not a withdrawn one), and the stopped servers and imported images in the pools of its projects. They get `vga: std`. A second sync writes nothing.
   - **At the next start from the portal:** a running server. Stop then Start sets `vga: std` while the server is stopped. So does an action that stops and starts it: resize, rebuild, restore, rollback. A Reboot does not.
   - **Only when a node group or the platform is rolled:** Kubernetes workers, the platform's machines and the seed. The portal never writes on them. They change when they are replaced from a template that has `vga: std`.
   - The portal never writes `vga` on a running VM and never leaves a pending change.

3. The platform is not changed by step 1: it stays on its BOM and keeps working. To move it, open System → Managed services, read the plan in step 4 and type the confirmation the page shows. From the BOM `0.9.1` the plan lists four changes and refuses nothing:

   | Change | From → to | Class | Stage |
   |---|---|---|---|
   | `release` | `0.9.1` → `0.10.0-rc.1` | record only | none |
   | `tenantCharts.kubernetes` | `proxmox-kamaji-cluster` `0.1.14` → `0.1.15` | record only | none |
   | `tenantCharts.database` | `database-cluster` `0.5.1` → `0.5.2` | record only | none |
   | `pc-platform` (seed) | `0.1.14` → `0.1.15` | chart | `cluster`, wave 3 |

   No machine is replaced, no k3s is replaced, and the run does not ask for a seed backup. Take one anyway, as the guide says. See ["Upgrade between BOMs"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0-rc.1/docs/managed-services.md#upgrade-between-boms).

4. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.9.0`, `0.9.0-rc.1` or `0.9.0-rc.2` | As from `0.9.1`: four changes, no refusal. |
| A platform on a `0.8.x` BOM | The plan lists seven changes and refuses nothing: the four above (the cluster chart from `0.1.13`) and the three components of platform chart `0.1.2` → `0.1.3`. Read the cautions in the [notes of v0.9.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.0). |
| A platform you move to the BOM `0.10.0-rc.1` | Keep it on a lab. Later builds apply it only while they carry this BOM; `v0.10.0` is planned to, and moving to its BOM is one more upgrade run. A build without it refuses the platform (`bom_unsupported`). |
| Tenant Kubernetes clusters and databases made before this upgrade | They keep their chart until their own chart update. A new database of one instance gets no disruption budget, and restarts when its node is drained. |
| Servers whose Proxmox console should open on the graphical display now | Stop then Start each from the portal. A Reboot does not change it. |
| A template the portal did not import, or one built by `images/build.py` | The portal does not write on it. Run `qm set <vmid> --vga std` on it. On a VM, stop and start it right after: between the two, the VM has a pending change and the portal refuses operations on it. |
| Withdrawn templates you want gone | Use Delete on the row in Template updates. It is refused while a cluster's node group, a provider's version map or a linked clone still uses the template. |
| A site that wants the ArgoCD address | Do not set it on a production site yet. Whether the platform cluster enforces the operator networks is the open point, and only a lab can show it. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |
| A new install | Pass `--version v0.10.0-rc.1` to `proxcloud-up.sh install`. The script's default, the chart and the installer still name `v0.9.1`. |

## What changed

Since `v0.9.1`.

### Operator console

- **Delete a withdrawn template.** The Imported templates table has **Delete** on withdrawn rows (`DELETE /admin/template-updates/templates/{importId}`, audited). It destroys the template with the disks its configuration names, and frees the import receipt. The digest stays blocked. It needs no new Proxmox privilege. See [the guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0-rc.1/docs/template-updates.md#delete-a-withdrawn-template).
- **Refusals of the delete.** It is refused, with the reason, while a Kubernetes cluster's node group or a provider's version map names the template, a linked clone uses its disk, or a smoke test or its import is running.

### Servers and templates

- **Graphical console by default.** A new template has `vga: std` and keeps `serial0: socket`. The Proxmox web UI opens such a VM on the graphical console; the serial terminal stays under Console → xterm.js and `qm terminal`. The portal's own console page works as before, on both tabs.
- **Existing templates and servers.** The services sync moves this portal's templates and its stopped servers. A running server moves at its next start from the portal. Workers and platform machines move when they are replaced. The portal never writes `vga` on a running VM. See ["Console display"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0-rc.1/docs/template-updates.md#console-display).
- **What a guest shows.** What appears on the graphical console and on the serial terminal depends on the guest's own kernel arguments. This was not measured.

### Managed services

- **The seed's k3s in an upgrade run.** A run toward a BOM with a newer k3s has a stage "Upgrade the seed's k3s". It replaces the binary on the running seed VM and restarts k3s. The seed's API is away for about a minute; the platform cluster, tenant clusters and databases keep serving. k3s moves by a patch, a k3s build or one minor, never back. This candidate's BOM names the k3s that `0.9.1` names, so the stage does not run. See ["The seed's k3s"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0-rc.1/docs/managed-services.md#the-seeds-k3s).
- **Seed backup check.** The Check has a row `seed-backup`: ok when a store of the seed's node holds a backup of the seed VM younger than 24 hours, a warning otherwise. An upgrade that replaces the seed's k3s is refused (`409 seed_backup_missing`) until the row is ok or the operator ticks that a backup was taken where the portal cannot see it.
- **Replacing the platform cluster's machines.** A run toward a BOM with a newer Kubernetes, or a rebuilt node image, is two actions in step 4: **Seed and node image**, then **Replace the machines**, with its own typed phrase. The control plane goes first, then one node group and node at a time. There is no way back once the new control plane machine has joined, and the plan says so. A node without room for one more machine of a group gets that group delete-first; a control plane node without room refuses the upgrade. This candidate's BOM keeps Kubernetes `1.35.10` and its node image, so none of this runs. See ["The platform cluster's machines"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0-rc.1/docs/managed-services.md#the-platform-clusters-machines).
- **ArgoCD address.** Under **Access** in step 1, name one address of the load balancer range and the operator networks, save and apply. The platform cluster's ArgoCD then answers at `https://<address>` for those networks only, with ArgoCD's own self-signed certificate, and the ready card shows the link. Sign in as `admin` with the password read through the one-hour platform kubeconfig. No account is created and no password is stored. The seed's ArgoCD never gets an address. A platform that does not set the block is rendered as before. See [the guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0-rc.1/docs/managed-services.md#an-address-for-the-platform-clusters-argocd).
- **New Check row `argocd-access`.** It warns when an operator network contains a Proxmox node's address: where tenant traffic leaves under that address, tenants then reach the login page. When MetalLB does not give the address, the run fails with `argocd_address_unavailable` and the platform keeps serving.

### Kubernetes and databases

- **Cluster chart `0.1.15`.** It reads two optional keys of a node group, used by the machine replacement. Without them it renders what `0.1.14` rendered, so no machine is replaced.
- **Database chart `0.5.2`.** A PostgreSQL or FerretDB database of one instance no longer has a disruption budget, which blocked every drain of its node. Such a database restarts when its node is drained. Existing databases keep their chart until their own chart update.

### Fixes

- **An old backup of another VM no longer counts as the seed's backup.** A backup counts only when it was made after the seed became ready and, when it has notes, the notes name the seed VM.
- **An apply no longer rewrites the seed VM's firewall options when they are as wanted.** It reads them first and writes only a difference.
- **The node wait counts every control plane machine.** With a control plane of three the wait for the nodes could not end.

### Release

- **BOM `0.10.0-rc.1`.** Cluster chart `0.1.15` for the platform cluster and for new tenant clusters, database chart `0.5.2`, platform chart `0.1.3`. No third-party chart, image, k3s, Kubernetes version or node image moved. This build carries the BOMs of `0.8.0`, `0.8.1`, `0.8.2`, `0.9.0-rc.1`, `0.9.0-rc.2`, `0.9.0` and `0.9.1` as previous BOMs.
- **Dependency updates.** Thirteen library updates of the Go module and the two consoles, among them the MCP Go SDK, the AWS S3 client, `koanf`, `mustache`, `@stripe/stripe-js` 10, `@base-ui/react`, `radix-ui`, `lucide-react`, `react-router-dom`, `vite` and `oxlint`.

## Known issues

- **A Reboot from the portal does not change the display.** A running server keeps the serial display through a Reboot, because Proxmox cannot change the display of a running VM. It affects every server made before this release. Use Stop then Start.
- **The machine replacement has never run on a real cluster.** It ran in tests against a fake seed only, and no released BOM starts it. It affects the first release whose BOM names a newer Kubernetes. Run that upgrade on a lab first.
- **The seed's k3s upgrade has never run on a real seed.** The same holds for it: tests only, and no released BOM starts it.
- **The ArgoCD address may be reachable by tenants.** On a site where tenant traffic leaves under a Proxmox node's address that an operator network contains, tenants reach the login page. The Check row `argocd-access` warns. It affects a site that sets the address. Do not set it on a production site yet.
- **The root command stops when the platform's token ids are taken.** The platform's two Proxmox tokens have fixed ids, `capmox@pve!capi` and `csi@pve!csi`. On a Proxmox cluster where one of them already exists for something else, the command stops before it changes anything. It affects a new install on such a site. The only way forward it offers is to remove that token, which breaks whatever else uses it. See ["The root command of an installation"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0-rc.1/docs/managed-services.md#the-root-command-of-an-installation).
- **A chart version that changes only its hook does not run the hook.** ArgoCD syncs an Application only when a rendered object differs. No chart of this candidate is such a version. It affects a later release, which must also change a rendered object.
- **Workers do not join when the node that holds the platform's addresses also translates tenant traffic.** On a `simple` tenant zone, tenant connections to the platform network are dropped on that node. The network of an installed platform is fixed, so `routed` mode helps a new one-node install only. Read the Check row `tenant-path`, run the test, and use one of [the two layouts that work](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0-rc.1/docs/managed-services.md#the-path-from-tenants-to-the-platform).
- **The platform upgrade is not shown on a lab with tenants.** It ran once on a production site that has them, to the BOM `0.9.0`. Take the seed backup first, or leave the platform on its BOM, where it keeps working.
- **A health check replaces nothing when every worker of a group fails.** That is its guard. The machines stay and are counted in the tenant's quota. Repair the cause, then use Replace or delete the cluster.
- **Replace on a node group of one leaves the group without a node.** The old machine goes first. It affects a tenant with one worker. Raise the group's count by one first when the workload cannot wait.
- **A standalone volume can lose its name at create.** A volume created without a server can answer `200` with no `id` when Proxmox is slow, and is then named after its disk at the next provider sync. Nothing is lost but the name; not fixed.
- **The `pve-api-rule` row can read `ok` while the rule matches nothing.** This happens on a site whose router translates the platform network on the way to the Proxmox node. Add a rule for the translated address: see [the guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0-rc.1/docs/managed-services.md#when-a-router-translates-the-platform-network).
- **Seed ISOs of servers created before `v0.8.0` are never swept.** When such a server is deleted, its seed ISO stays on the seed store and holds the server's user data. Clean it up by hand with the commands in the [release notes of v0.8.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.8.2).
