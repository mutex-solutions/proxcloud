ProxCloud v0.9.0 is a feature release on top of `v0.8.2`. An installed managed-services platform can now be upgraded in place. A new install is easier to size and to place on a network, and a tenant can use it as soon as it is green. Tenant Kubernetes workers can be repaired and put behind a firewall.

The platform bill of materials (BOM) is the list of exact versions a managed-services platform runs. The BOM of this release is `0.9.0`. It pins what the candidates `0.9.0-rc.1` and `0.9.0-rc.2` pin: cluster chart `0.1.14` and platform chart `0.1.3`. The release also carries the BOMs of `0.8.0`, `0.8.1`, `0.8.2` and of the two candidates, for the platforms those builds installed.

## Highlights

- **Upgrade an installed platform.** Step 4 of Managed services moves a platform from the BOM of `0.8.0`, `0.8.1` or `0.8.2` to this one, after a typed confirmation. Only ProxCloud's own charts move, and no machine is replaced. It ran once on a lab, on a platform without tenants: read Upgrade before you use it on a site that has them.
- **Presets and control plane count.** A new install starts from Homelab, Standard or Custom, with one or three control plane machines. A Check row, `capacity`, says whether the machines fit on each node.
- **Network modes and a path test.** The platform network takes a VLAN tag, or is made by ProxCloud on a one-node site (`routed`). "Test the tenant path" checks that a tenant network reaches the platform.
- **One root command.** One command per installation makes the Proxmox tokens and prints one line to paste. The install writes the firewall rule that lets the platform reach the Proxmox API.
- **Usable right after install.** A green install offers a Kubernetes version and attaches the providers to projects, as you choose in step 1.
- **Worker repair.** A worker that never joins is replaced after a timeout, in a node group of two or more. Replace does it on demand for one worker.
- **Worker firewall.** A cluster's workers can be put behind the Proxmox VM firewall. It is off by default.
- **Workers start with their node.** Tenant workers and their node templates get `onboot`, also on a site that was upgraded from `0.8.x`.
- **Console items.** Pending invitations with Revoke, editable security group rules, a first Kubernetes cluster without leaving the form, and clearer pages for load balancers and servers.

## Upgrade

These steps upgrade from `v0.8.2`. From an older release, also follow the upgrade steps of each release in between, starting with the [notes of v0.8.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.8.2).

1. Upgrade the portal first. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.9.0
   ./proxcloud-up.sh upgrade v0.9.0
   ```

2. Let one provider sync run. It runs every 15 minutes; on an install without the scheduler start it with `POST /api/v1/admin/job/external-service/sync`. The sync sets `onboot` on the Kubernetes node templates this portal imported and on the running workers of its tenant clusters, where it is missing. Do this before a planned Proxmox node reboot. It does not cover a template the portal did not import, or a worker that is stopped: see ["After a Proxmox node reboots"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0/docs/managed-services.md#after-a-proxmox-node-reboots).

3. The platform is not changed by step 1: it stays on its BOM and keeps working. Moving it to the BOM `0.9.0` is a separate run that you start, and you can leave it for later. Until then three control plane machines and a VLAN tag are refused on that platform, and Replace answers `502`.

4. Before you move the platform, read this.

   - **The upgrade has run on a lab without tenants only.** One platform went from the BOM `0.8.0` to `0.9.0-rc.1`, with no tenant cluster and no database on it. It has not run on a platform that has tenants, and it has not run to the BOM `0.9.0` itself.
   - **Take the seed backup first.** Back up the seed VM with `vzdump` and dump the portal database, as ["Credentials and the seed backup"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0/docs/managed-services.md#8-credentials-and-the-seed-backup) says. A restore after a failed upgrade has not been run on a lab.
   - **Check that tenant clusters and databases are healthy.** Do not change a machine size or count in the same step.

5. Move the platform. Open System → Managed services and read the plan in step 4. From a `0.8.x` BOM it lists six changes and refuses nothing: the release, the chart for new tenant clusters, and four charts of ProxCloud's own. No machine is replaced. Type the confirmation the page shows. See ["Upgrade between BOMs"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0/docs/managed-services.md#upgrade-between-boms).

6. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.9.0-rc.1` or `0.9.0-rc.2` | This release applies it as it is. To move it, confirm the upgrade in step 4. The plan lists one change, the release, and nothing is synced for it. Not run on a lab. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |
| Tenant Kubernetes clusters made before the upgrade | They stay on cluster chart `0.1.13` and get no health check until their own chart bump. Replace works on them once the platform is on the BOM `0.9.0`. |
| A Kubernetes provider with worker repair or firewall settings | Read the provider's page. `nodeStartupTimeoutSeconds` must now be `0` or 900 to 86400; a stored value outside that is read as the default, and the page says so. |
| Security groups whose name starts with `k8s-` | The prefix is now reserved for Kubernetes clusters. Creating such a group answers `400`. An existing one stays the tenant's, but can no longer be attached to another server. |
| A script that sends the installed BOM as `targetBom` | The answer is now `409 bom_installed`. It was `400 invalid_confirmation`. |
| A script that sends `preset` or `spec.sandbox` to an installation | A preset other than `custom` on an installed platform answers `409 fixed_fields`. `spec.sandbox` is refused. |
| A new install on a Proxmox cluster where `capmox@pve!capi` or `csi@pve!csi` already exists | Read Known issues first: the root command stops there. |

## What changed

### Managed services

- **Platform upgrade.** Step 4 shows the plan between the installed BOM and this release's, and starts the upgrade after a typed confirmation. A release that changes the Kubernetes version, an image, k3s, a Cluster API provider or a third-party chart is refused with a reason for each entry, and so is a `-dev` target. A Retry after a failed upgrade continues to the upgrade's target.
- **Presets.** Step 1 starts from Homelab, Standard or Custom. A preset fills the form of a new installation and every field stays editable. It is switched off on an installed platform, in the page and at the API.
- **One or three control plane machines.** Three keep the platform's API up when one control plane VM is lost. They are all on one Proxmox node, so they do not protect against the loss of that node. Going from 1 to 3 is an apply on an installed platform.
- **Check row `capacity`.** It compares, for each node, the memory of the machines with what the node can reserve. A larger control plane that does not fit is listed in the plan and blocked before any run.
- **Network mode and VLAN tag.** In `bridge` mode, the default, a VLAN tag can be set for every machine's NIC. In `routed` mode, on a site with one Proxmox node, ProxCloud makes the network at the install, with the node as its gateway. The network stays fixed after the first install.
- **Test the tenant path.** A button in step 3 of an installed platform. It clones one throwaway VM on a throwaway tenant network, opens a connection to the platform's load balancer range and removes both again.
- **One root command.** Step 2 shows one command for the installation. It prints no secret on the way and ends with one `PC-ENROLL:` line to paste into the page. It stops before it changes anything when a token it needs already exists for something else.
- **Proxmox API firewall rule.** The install writes the cluster firewall rule that lets the seed and the platform machines reach the Proxmox API, and Remove deletes it. New Check rows `boot-store` and `pve-api-rule`.
- **Usable after install.** Every apply offers the BOM's Kubernetes version on the provider once its node image is published on the platform's nodes. A new setting, `spec.tenants.attach`, says which projects get managed Kubernetes and databases. The ready card has one button that tests and publishes the node image and offers the version.
- **Settings save.** Saving the settings adds the seed's address, the API address and the node range to the provider's blocked networks, and creates a new `simple` tenant zone without a DHCP server.
- **Clearer texts.** Four checks name the one action that fixes them. The review step shows each node's free memory. The upgrade plan says that ArgoCD syncs a chart only where it renders an object differently. A stage shows `step 3 of 4, wave 2`.

### Kubernetes

- **Automatic worker repair.** A worker that registers no node is replaced after `nodeStartupTimeoutSeconds` (1800 by default), in node groups of two or more, while at most one machine of the group is unhealthy. It needs cluster chart `0.1.14`, which new clusters on this BOM get.
- **Replace.** One worker can be replaced from the customer console and the operator console. The node count, placement and quota do not change. The last Ready node of a group asks for a confirmation.
- **Worker firewall.** Inbound traffic to a worker is dropped except what the cluster's own security group allows. The operator turns it on for one cluster at a time, or for new clusters with `workerFirewall: true` on the provider. A new or replaced worker is covered at the next provider sync.
- **Join error.** The operator console's Machines dialog shows the error a worker reports when it does not join, with `kubeadm`'s own message and no credential in it.
- **`onboot` for workers.** A node image imported by Template updates starts its clones with their Proxmox node. The provider sync sets `onboot` on older node templates of this portal and on running workers that lack it.
- **Provider settings are checked on save.** Values that would delete machines in a loop or switch a setting off by accident are refused with the field and the reason.
- **"Needs attention" per machine.** A healthy worker no longer clears the mark for machines of the same group that are stuck.
- **Reserved security group names.** A name that starts with `k8s-` belongs to a Kubernetes cluster. A cluster's group cannot be deleted or detached while the cluster exists.

### Customer console

- **First Kubernetes cluster.** The form selects the project's network when exactly one fits and offers to create one when the project has none.
- **Invitations.** Members lists pending project invitations with Copy link and Revoke. On a site that sends no email the dialog shows the link.
- **Security group rules can be edited.** The rule form has a protocol list and a description.
- **Servers.** Hard reboot under More actions, and a "How to reach this server" card when the project has no public network. The create form explains which security group applies when none is ticked.
- **Load balancers.** The page lists what the operator must enable, in place of a failure at create.
- **Networks.** Create network says that it waits for the network to be applied on the nodes.

### Release and build

- **BOM `0.9.0`.** Cluster chart `proxmox-kamaji-cluster` `0.1.14` and platform chart `proxcloud-platform` `0.1.3`, both pinned by digest. Nothing else moved since `0.8.2`.
- **Release notes.** The body of a GitHub Release is now a file written for a reader, like this one.
- **Console images.** The two consoles' images run on NGINX 1.30.7, which closes five HIGH findings of the base image.
- **Sandbox template builds.** A build survives a package mirror or Launchpad that does not answer, installs the `mcp-gateway` servers from a lockfile, and names the template that failed.
- **CI.** A pull request runs only the jobs its changed files can affect.

## Verified on a lab

Three rounds on 2026-11-19, on one lab Proxmox VE cluster. Nothing was run on the published images of `v0.9.0` itself. The code of `v0.9.0-rc.2` is the code of this release without one fix to the sandbox template build.

Round 3, on the published images of `v0.9.0-rc.2`:

- **Fresh install in bridge mode.** One run of 40 minutes 5 seconds, no Retry and no failed stage. The platform was on the BOM `0.9.0-rc.2` with charts `0.1.14` and `0.1.3`, all five VMs had `onboot`, the plan showed no change and the Check passed with 25 rows.
- **Remove.** 54.2 seconds, no retry, and nothing left on Proxmox. The Proxmox API firewall rule was written by the install and deleted by Remove.
- **`409 bom_installed`.** Three requests that named the installed BOM as the target got this answer.
- **Control plane growth.** The plan listed 1 to 3 as a change and blocked it with the node's numbers, and the Check row `capacity` failed. After the count was put back the plan was empty.
- **`onboot` on old templates and workers.** The first provider sync wrote it on six node templates of this portal, withdrawn imports among them, and touched no other template. A second sync wrote nothing. A worker cloned from such a template had `onboot`, and the sync wrote nothing on workers that had it.
- **A tenant cluster of two workers.** Both nodes were Ready on chart `0.1.14`. The node group of two had its health check object, with a guard of 1 and a timeout of 1800 seconds.
- **LoadBalancer.** A Service of type LoadBalancer answered from both workers.
- **Database.** A managed database was ready and was reached from a tenant pod, with the tenant network as the allowed source, in a VLAN zone.
- **Tenant path test `passed`.** On a `simple` zone, from a node that does not hold the platform's addresses.
- **Deletes.** The cluster, the database and the network were deleted. The cluster's Proxmox token was released by the job and the quota went back to 0.

Round 2, on the published images of `v0.9.0-rc.1`, over a platform that `v0.8.0` installed:

- **The upgrade from `0.8.0` to `0.9.0-rc.1`, on a lab without tenants.** One run, no retry, 72.8 seconds. The plan showed six changes and nothing blocking. The lab had no tenant cluster and no database.
- **Nothing rolled.** The same four machines, nodes and boot ids, the same QEMU processes, and no Proxmox task. No pod restarted: 47 on the platform cluster, 16 on the seed. The platform API answered at each of 238 looks, one every 2 seconds.
- **What ArgoCD did.** It synced one Application of fourteen, `platform`. The three other chart moves were compared and found in sync, and no clusterctl hook ran. A second apply took 5 seconds and changed nothing.
- **Refusals.** Seven requests with a wrong confirmation or a wrong target were refused, and none started a run.
- **Chart `0.1.14` on a new tenant cluster.** A worker was Ready 9 minutes after the create. A node group of one gets no health check, by design; a group of two got one, with its guard.
- **Replace.** On the last Ready worker it asked for a confirmation, then made a new machine whose node was Ready 7 minutes 21 seconds later. The group had no node for about 6.7 minutes.
- **The health check, all workers failed.** On a cluster whose two workers could not join, it replaced nothing, as its guard says.
- **Worker firewall, one worker.** From a second tenant machine, the kubelet, SSH and port 4240 were closed afterwards, and NodePort and LoadBalancer stayed open. The node stayed Ready. Two of about 6000 one-second requests failed in 52 minutes, none at the change.
- **Provider settings check and join error.** The refusals and their texts, and `kubeadm`'s own error in the join log, with no token in it.
- **Tenant path test `failed`.** A full run on a `simple` zone gave the predicted verdict for the node that holds the platform's addresses, and cleaned up.

Round 1, on a build of `main`, over the same platform:

- **Volumes.** A volume keeps its row through attach, detach and rebuild, and the quota is right.
- **Worker firewall, one worker.** The Proxmox rules were written in the right order, the node stayed Ready, and Remove and the cluster delete cleaned up.
- **Replace.** Its refusals on a `0.8.0` platform, and "needs attention" after its time limit.
- **One root command.** The Check rows, the firewall rule and the refusals. The command was not run on a node.
- **Presets, network modes.** Only the refusals, the `capacity` row and the cleanup.
- **Usable after install, invitations, rule edit.** At the API only, and in part.

## Not verified

- **This release itself.** Not run: its published images, its tag's workflows, and the upgrade of a platform to the BOM `0.9.0`, from a `0.8.x` BOM or from a candidate's. The step from a candidate's BOM was planned as one record-only change and never run.
- **The upgrade with tenants.** No upgrade has run on a platform that has a tenant cluster or a database. Not seen: the wait for tenants in stage 9, a tenant that is unhealthy (`tenants_unhealthy`), the `platform` chart's sync beside live tenant control planes, and an existing cluster staying on chart `0.1.13`.
- **A failed upgrade or install.** Not run: a failed stage and Retry, a restore, and the refusal of a chart that would replace a machine (`unexpected_rollout`). The seed's backup was not taken before the lab upgrade.
- **The upgrade from other starts.** Not run: the portal's own step from `v0.8.2` (the lab's portal came from a build of `main` and the candidates), and a platform on the BOM of `0.8.1` or `0.8.2`.
- **The one root command on a fresh token set.** Not run: the command to its end and the `PC-ENROLL` line. On the lab the two token ids already existed, and the command stopped as designed. The lab install stored existing token secrets through the credentials step.
- **The Homelab preset as an install.** Only its save was seen. The lab's nodes have no room for it.
- **`routed` mode and a VLAN tag.** Not run: an install in `routed` mode, its Remove, and a VLAN tag on the platform network.
- **A replacement by the health check.** No worker was broken. The lab showed only the guard refusing when both workers of a group were unhealthy. Also not seen: Replace of a machine that has no node.
- **`onboot` beyond what is listed.** Not run: the sync on a running worker that has no `onboot`, a node template freshly imported by this release and its clone, and a Proxmox node reboot.
- **The tenant path test, both verdicts on one install.** `failed` and `passed` were seen on two different installs.
- **Three control plane machines.** Not built: on a new install or by an apply.
- **The button that publishes the node image.** Not pressed: the button on the ready card that tests and publishes the node image and offers the version. On the lab the image was already on the nodes, and the install's last stage said the version is offered.
- **Worker firewall.** Not run: two workers, a new or replaced worker, and `workerFirewall: true` on the provider.
- **The consoles.** Every round ran at the API. No page of either console was opened, step 4 of Managed services included.
- **Earlier releases.** Everything `v0.8.0`, `v0.8.1` and `v0.8.2` say is not verified still holds, except what is listed as verified here.

## Known issues

- **The upgrade is not shown for a site with tenants.** See Upgrade and Not verified. It affects a production platform on a `0.8.x` BOM. Take the seed backup first, or leave the platform on its BOM, where it keeps working.
- **The root command stops when the platform's token ids are taken.** The platform's two Proxmox tokens have fixed ids, `capmox@pve!capi` and `csi@pve!csi`. On a Proxmox cluster where one of them already exists for something else, the command stops before it changes anything and prints the command that removes the token. It affects a new install on such a site. The only way forward it offers is to remove that token, which breaks whatever else uses it. See ["The root command of an installation"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0/docs/managed-services.md#the-root-command-of-an-installation).
- **Workers do not join when the node that holds the platform's addresses also translates tenant traffic.** On a `simple` tenant zone, tenant connections to the platform network are dropped on the Proxmox node that both translates tenant traffic and runs the platform's machines. The path test reads `failed` from that node and `passed` from another. The network of an installed platform is fixed, so `routed` mode helps a new one-node install only. Read the Check row `tenant-path`, run the test, and use one of [the two layouts that work](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0/docs/managed-services.md#the-path-from-tenants-to-the-platform).
- **A chart version that changes only its hook does not run the hook.** ArgoCD syncs an Application only when a rendered object differs. No chart of this release is such a version. It affects a later release, which must also change a rendered object. See ["What a release checks about its BOM pairs"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0/docs/ci-release.md#what-a-release-checks-about-its-bom-pairs).
- **The Check row `boot-store` can name a VM that does not exist.** The row counts the owners of volumes on the store, so a leftover volume is listed under the id of a VM that is gone. It affects the row's text only.
- **The stored result of the tenant path test outlives Remove.** After a Remove and a new install, the page shows the verdict of the last test of the old platform until a new test runs. Run the test again after an install.
- **Deleting a tenant cluster logs one failed request on Proxmox.** The portal asks Proxmox to delete a `csi@pve` token that was never made, and Proxmox answers `500`. The delete still succeeds and nothing is left behind. It is noise in the Proxmox log; the cause is not found yet.
- **A tenant cluster's token gets `403` on a few status reads.** Seen on `GET /cluster/status` and on a VM's current status, at clone start and at delete. The machines came up and no effect was seen.
- **A health check replaces nothing when every worker of a group fails.** That is its guard. The machines stay, show "not joined" with "needs attention", and are counted in the tenant's quota. It affects a tenant whose workers cannot reach the platform. Repair the cause, then use Replace or delete the cluster.
- **Replace on a node group of one leaves the group without a node.** The old machine goes first: on the lab the group had no node for about 6.7 minutes. It affects a tenant with one worker. Raise the group's count by one first when the workload cannot wait.
- **A standalone volume can lose its name at create.** A volume created without a server can answer `200` with no `id` when Proxmox is slow, and is then named after its disk at the next provider sync. It affects a tenant who creates such a volume. Nothing is lost but the name; not fixed.
- **The `pve-api-rule` row can read `ok` while the rule matches nothing.** This happens on a site whose router translates the platform network on the way to the Proxmox node. It affects installs on such a site. Add a rule for the translated address: see [the guide](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0/docs/managed-services.md#when-a-router-translates-the-platform-network).
- **Seed ISOs of servers created before `v0.8.0` are never swept.** When such a server is deleted, its seed ISO stays on the seed store and holds the server's user data. It affects a site with such servers. Clean it up by hand with the commands in the [release notes of v0.8.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.8.2).
