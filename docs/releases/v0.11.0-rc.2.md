ProxCloud v0.11.0-rc.2 is the second release candidate of `v0.11.0`, published as a prerelease. It corrects what the full lab drill of `v0.11.0-rc.1` found in the load balancer: most of the drill passed, and two faults block a release. It exists so that the lab can run the drill again on the corrected code: none of the corrections has run on a lab yet. It is not for production. `v0.10.2` stays the current stable release.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this candidate is `0.11.0-rc.2`. Against `0.11.0-rc.1` it moves nothing but its own name. Against `0.10.2` it moves one thing: the cluster chart for new tenant clusters, `proxmox-kamaji-cluster` `0.1.16` → `0.1.17`.

## Highlights

- **The drill of rc.1 ran in full.** One lab, on 2026-11-21: a pair built by the product on a public network, 15 failovers, a managed cluster with its load balancer controller, billing rows, clean-up. See "Verified on a lab".
- **Failover held its targets.** All 18 measured switches stayed under them: a dead master lost 2.8 to 3.4 s, a planned switch 0.8 s.
- **Blocker 1: Replace appliances took the address down for 458 s.** The page read `ACTIVE` the whole time. The first config push met the HAProxy package's own first start, and the product recorded a config that HAProxy had not loaded.
- **Blocker 2: a stopped master was not started again.** The services sync started it in 1 of 6 tries, and the row kept saying `ACTIVE`. By the code, the same skip held back isolation rules, worker firewalls and start at boot for every tenant of the provider.
- **rc.2 records a config only when the appliance serves it** (#424). Each pass asks every appliance whether HAProxy listens on its addresses, and pushes again when it does not.
- **rc.2 keeps the sync running when an appliance is down** (#425). A stopped appliance no longer makes its project's inventory unproved.
- **Three smaller fixes for cluster balancers** (#425). An API restart no longer holds a cluster's balancer for 20 minutes. An unchanged controller call starts no pass. A refused credential is logged with its cluster and reason.
- **One timing changed.** A stopped appliance of a cluster's pair is now started within about 70 s. The drill of rc.1 measured 2 to 6 s, at the cost of 96 Proxmox calls a minute per cluster. The other appliance takes the address in seconds either way.
- **The corrections are not run on a lab yet.** They are tested against a real HAProxy and keepalived in a container and against a fake Proxmox. The second drill comes next.
- **UDP and TLS termination are not in v0.11.0.** They are planned for the next release, "complete layer 4".

## Upgrade

Use a lab or another non-production site. Production sites should stay on `v0.10.2` and wait for `v0.11.0`. These steps upgrade from `v0.10.2` or from `v0.11.0-rc.1`. From an older release, read the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) first: their steps and cautions still apply.

1. **Check the platform's BOM first.** The move is planned from the BOMs `0.10.1`, `0.10.2`, `0.11.0-rc.1` and the candidates of the first two. A platform on an older BOM (`0.8.0` to `0.10.0` and their candidates, all on Kubernetes 1.35.10) is refused by this build. Move it to `0.10.1` first with the `v0.10.1` build, both parts, as the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) describe.

2. **Upgrade the portal.** On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. `compose.yaml` did not change since `v0.10.2`. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0-rc.2/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.11.0-rc.2
   ./proxcloud-up.sh upgrade v0.11.0-rc.2
   ```

   - **From `v0.10.2`: a new load balancer is a pair from now on.** Each one costs two servers, their disks and one address. A tenant can still ask for one VM (`ha: false`).
   - **The appliances need their packages.** A stock image gets `haproxy`, `socat`, `keepalived` and `iproute2` from apt. A site with no egress bakes them into `config.lbImage`.
   - **A public network that is an SDN vnet is refused for a pair.** Use a plain bridge, with no VLAN tag.
   - **Existing balancers are not pushed at the upgrade.** Their config and its hash are what they were. From now on each pass asks every appliance whether HAProxy serves its config, and pushes only where it does not.

3. **From `v0.11.0-rc.1`: what the corrected code does to what rc.1 built.**

   - **A pair whose HAProxy runs the package's config is repaired by the next pass.** The pass finds HAProxy not listening on the balancer's addresses, the row reads `DEGRADED` or `DOWN` with the reason, and the config is loaded in that pass.
   - **An appliance's SERVER row that holds the balancer's address is rewritten by the next services sync.** There is no migration to run.
   - **Files on existing appliances stay mode 0666** until the balancer's next config change or Replace appliances. No secret is written to an appliance today.
   - **A server stopped outside the portal** (from inside the guest, or on Proxmox) now shows its configured addresses only while it is down, as after a stop through the portal. Its project is synced again.

4. **Optional on Compose: turn on the gateway listener.** Only for the load balancer controller of managed clusters. Re-run `install` on the same version with the address of this host that the platform cluster's nodes reach:

   ```sh
   ./proxcloud-up.sh install --cluster-gateway <address>
   ```

   - **Add the route.** The platform cluster's nodes, on the platform network, must reach the portal host on `<address>:8444`. Without it no controller reaches the gateway, and its cluster page says it has not reported. Nothing else breaks.
   - **Keep the volume `gateway`.** It holds the listener's key and self-signed certificate (made on the API's first start). A new certificate means a new gateway Secret for every cluster. Database backups do not hold it.
   - **Block volumes stay off on Compose.** No gateway token is registered there, with or without the listener.
   - On the lab the command took 14 s and recreated only the API container. See ["Optional features" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0-rc.2/deploy/compose/README.md#optional-features).

5. **Read the plan.** Open System → Managed services and read the plan in step 4. It refuses nothing from these BOMs.

   | From the BOM | Change | From → to | Class |
   |---|---|---|---|
   | `0.11.0-rc.1` | `release` | `0.11.0-rc.1` → `0.11.0-rc.2` | record only |
   | `0.10.2`, `0.10.2-rc.1` | `release` | `0.10.2` → `0.11.0-rc.2` | record only |
   | `0.10.2`, `0.10.2-rc.1` | `tenantCharts.kubernetes` | `proxmox-kamaji-cluster` `0.1.16` → `0.1.17` | record only |

6. **Run the upgrade.** Type `upgrade <installation name> to 0.11.0-rc.2`. There is one action, with no parts.

   - **What it does.** It records the new release. From `0.10.2` it also writes chart `0.1.17` on the Kubernetes provider, and clusters created after it get the new chart.
   - **What it does not do.** It replaces no machine, syncs nothing and writes nothing on Proxmox. The platform cluster stays on chart `0.1.16`. No tenant cluster changes chart, and none loses MetalLB.
   - **How long.** The same kind of run to `0.11.0-rc.1` took 39.6 s on the lab. The run to `0.11.0-rc.2` was read as a plan, not run.

7. **Let new clusters get the controller.** On the Kubernetes provider, set `config.cluster.loadBalancer`: a public network of the workers' Proxmox provider (with a gateway, on a plain bridge) and the flavor of the appliances. The form calls them **Load balancer public network** and **Load balancer flavor id**. A new cluster then gets the controller in default mode when every gate holds:

   - the portal has a gateway URL and the controller image (Compose: `--cluster-gateway`; the installer chart: `api.csiGateway`);
   - the provider pins chart `0.1.17` or later (step 6);
   - the workers are the project's own, not shared;
   - the project may use that public network.

   In default mode a Service without a class gets a public address, and MetalLB serves only class `proxcloud.io/internal`. NGINX Gateway Fabric then takes one public address per Gateway. When a gate does not hold, the cluster is made as before, with MetalLB alone, and the API log says which gate.

8. **Optional: add the controller to an existing cluster.** An existing cluster keeps MetalLB as its default. The operator's **Load balancer** dialog (provider → clusters) runs **Enable load balancer controller**, in class-only mode: only Services of class `proxcloud.io/lb` get the product's balancer, and no MetalLB address moves. It moves the cluster to the provider's chart, so run step 6 first. See ["How a cluster lands on Proxmox"](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0-rc.2/docs/managed-k8s.md#9-how-a-cluster-lands-on-proxmox).

   ```text
   POST /api/v1/admin/service/{kubernetesProviderId}/k8s-clusters/{clusterId}/load-balancer
   ```

Back up the cert-manager resources first, as the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) say. Read, not run. |

| A new install | Pass `--version v0.11.0-rc.2` to `proxcloud-up.sh install`. The script's default, the chart and the installer still name `v0.10.2`. |

## What the drill of rc.1 found

Two faults block the release. Both left the product saying `ACTIVE` over something that was not.

### Replace appliances: 458 s without service

- **What was seen.** After the planned switch of a Replace, the address refused every connection for 458.1 s: 4580 of 6830 requests failed. The row read `ACTIVE`, both appliances `up`. It ended only when the tenant changed the balancer's config.
- **Why.** The product called an appliance ready as soon as the HAProxy binary existed, while dpkg was still configuring the package. Its first push met the package's own first start: HAProxy was "activating", the product joined that start and took it for success, and HAProxy had read the package's default config. The config's hash was stored, so nothing was pushed again.
- **How narrow.** On the second appliance of the same Replace the same race went the other way by milliseconds. A single appliance has the same check and the same push.

### A stopped master appliance: not started again

- **What was seen.** The master of a pair was stopped six times. The services sync started it again once. The other five times the row kept reading `ACTIVE`, "MASTER up", for a VM that was off, until the tenant sent the balancer's config again.
- **Why.** A sync had read the pair's public address from the master's guest agent into its server row. A stopped or paused VM has no agent, so the address counted as lost and the project's inventory as unproved. The sync then left out its load balancer pass, the one that starts a stopped appliance.
- **How wide.** By the code, and shown by a test since, the same skip left out the provider's isolation rules, worker firewalls, start at boot and the sandbox pass, for every tenant of the provider, for as long as the VM stayed down. The traffic itself kept flowing: the other appliance held the address.

### Smaller findings

- **A cluster's balancer stood still for 24.7 minutes** after an API restart in the middle of a pass. A deleted Service kept its address for that time.
- **Every controller call ran a full pass:** 96 Proxmox calls a minute per cluster with a balancer.
- **A stopped keepalived or HAProxy on a running appliance was never started**, and the message named Replace appliances, which is the wrong remedy.
- **Config files on the appliances were mode 0666.**
- **During a Replace the row read `ACTIVE` with one appliance listed.**
- **A refused credential was logged without its cluster or reason**, and not audited.

## What changed

Since `v0.11.0-rc.1`: three merged pull requests with product changes.

### The appliance apply (#424)

- **Ready means installed.** An appliance is ready when dpkg reports every package `install ok installed`, no `apt-get`, `apt` or `dpkg` runs, and the units exist.
- **The apply proves what it loaded.** It starts HAProxy when it does not run, reloads it through its master socket in every case, and then wants every `bind` of the pushed file to be a socket HAProxy listens on. If anything fails, the old file goes back, no hash is recorded, and the next pass pushes again.
- **A recorded hash is checked on every pass.** Each appliance is asked whether HAProxy listens on every bind of its config. One that does not is not `up`, and is pushed again in that pass.
- **A pair's Services are called ready only when an appliance serves the config.** Two appliances that both hold the address read `DEGRADED` whatever they run.
- **Health says so too.** `GET_HEALTH` gives a member that the stored config holds and the running HAProxy does not the status `NOT LOADED` (it was empty), with `notLoaded` and `message`.
- **Stopped services are started.** A stopped keepalived or HAProxy on a running appliance is started by the pass that sees it. The message of a `DEGRADED` pair names the cause; "Replace appliances" appears only when an appliance is gone.
- **File modes.** Files written through the guest agent are root's, mode 0644, the two scripts 0755.
- **Replace states the row.** During a Replace the row reads `DEGRADED`, "One appliance carries the traffic while the other is being replaced".
- **The single appliance and the sandbox entry appliance** use the same push. A single appliance's config and hash are unchanged.

### The sync, the lock and the gateway (#425)

- **An appliance's server row holds what the platform configured.** Its guest is never asked for addresses, so a pair's address never enters a server row.
- **A stopped or paused VM is known to have no agent.** Its row goes back to its configured addresses and its project is synced. This holds for any server, not only an appliance. A running VM whose agent does not answer keeps its addresses, as before.
- **An unproved project holds back less.** It holds back its own rows, isolation and clean-up, the provider's seed sweep and the sandbox pass's sweep. The other projects, the load balancer pass, the provider's isolation rules, worker firewalls, start at boot and the fencing of sandbox workers run. See ["What an unproved inventory holds back"](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0-rc.2/docs/vm-inventory-safety.md#what-an-unproved-inventory-holds-back).
- **"Gone" is proved.** An appliance missing from the VM list is gone only when its VMID is free in the cluster. One the platform's token cannot see is `down`, "the platform cannot see its VM", and nothing says delete or replace.
- **The cluster lock lasts one minute.** Its holder extends it while it works; a holder that died loses it a minute later. It was 20 minutes.
- **An unchanged state starts no pass.** A controller's call starts one when the state changed, when the balancer is not settled, or when the last look is a minute old.
- **A refused credential says whose and why.** The log line carries the cluster the caller claimed and `malformed`, `unknown cluster`, `revoked` or `wrong secret`. A revoked credential and a wrong secret of a known cluster are audit events (`LB_GATEWAY` / `DENY`), at most one per cluster and reason a minute. The caller gets the same 401.
- **Guides.** The guides now say that in-cluster clients of a Service with `ipMode: VIP` do not pass the pair, that the default quota is five public addresses, and that a public network is a plain bridge with no VLAN tag.

### Sandbox nodes (#420)

- **A new sandbox node installs gVisor again.** The installer's node setup asked an apt suite for a runsc version the suite no longer lists. It now downloads the release's own package, checks its SHA256 and installs it: runsc `20261116.0`. Not run on a lab.

### Release

- **BOM `0.11.0-rc.2`.** The pins of `0.11.0-rc.1`. No chart of the product changed since its tag. This build carries the BOMs of `0.8.0` to `0.11.0-rc.1` (fifteen) as previous BOMs.
- **A candidate moves nothing a final moves.** The app chart, the installer's ProxCloud pin and the Compose default stay on `v0.10.2`.

## Verified on a lab

All of it on `v0.11.0-rc.1`, on 2026-11-21, on one lab. None of it was run again on this candidate. The lab: a nested three-node Proxmox cluster, a Compose portal, a one-node seed and a four-node platform cluster on Kubernetes 1.36.6, and a public test range on a plain bridge. Every appliance landed on one node. The appliances were Ubuntu 26.04 and installed their packages from apt through the lab's router. These are one lab's figures, not a promise for a site.

### Upgrade and listener

- **The portal upgrade** `v0.10.2-rc.1` → `v0.11.0-rc.1` by the script took 28 s, with PostgreSQL, Keycloak and Traefik kept.
- **The platform run** `0.10.2-rc.1` → `0.11.0-rc.1`: two record-only rows, 39.6 s, no Proxmox write, no VM restarted.
- **`--cluster-gateway`** was switched on and off six times: 14 s each, only the API container recreated. It listens on `<address>:8444` only and answers 401 to a missing or forged credential.

### A pair made by a tenant

- **Create.** The create call answered after 3 min 9 s with both VMs built. The pair was `ACTIVE` 8 min 16 s after the request; most of it was the package install.
- **What the product wrote.** On each appliance: a `vrrp` rule from its peer, one rule per listener to the balancer's address, the address in the public NIC's filter set, and no way in by SSH.
- **Traffic.** Requests from the public side and from a tenant network both reached the address, and the answers alternated between the two members.
- **Failover.** A client sent 10 requests per second with a 1 s timeout. Three runs of each fault, on the master:

  | Fault on the master | Requests lost for |
  |---|---|
  | Guest shutdown (a planned switch) | 0.8 s, 0.8 s, 0.8 s |
  | VM stopped hard (a dead master) | 3.1 s, 3.2 s, 2.8 s |
  | keepalived stopped | 0.7 s, 0.7 s, 0.7 s |
  | HAProxy stopped and left down | 2.7 s, 2.2 s, 2.6 s |
  | VM paused for 19 to 35 s, then resumed | 3.5 s, 3.4 s, 3.2 s |

- **No loss at a return.** No request failed when a stopped appliance came back. After a pause, the address went back to the resumed VM in two of three runs, with no failed request.
- **A deleted `vrrp` rule.** The rule was deleted by hand on the backup. The pair did not split in 100 s, and the next sync wrote the rule back.
- **Guarded.** Stop and hard reboot aimed at an appliance's server row are refused (409): the balancer is changed or deleted instead.
- **`ha: false`** made one VM as before, `ACTIVE` after 5 min 47 s.
- **Totals.** 38983 requests in 65 minutes: 296 failed in the 15 failover windows, 4580 in the Replace outage, none anywhere else.

### A cluster's load balancer

- **A new cluster in default mode** was ready after 7 min 42 s, with its controller on the platform cluster. The controller's NetworkPolicy allows DNS, the control planes of its namespace and the gateway's port only. MetalLB ran with class `proxcloud.io/internal`.
- **The first Service** had its address in `status` after 4 min 22 s and answered from outside after 6 min 7 s. Most of it was the two appliance builds.
- **One public address per Service.** Five Services held five addresses on one pair.
- **Refusals reach the tenant as Events:** a UDP port (`UDPNotSupported`), `allocateLoadBalancerNodePorts: false` (`NoNodePort`), `spec.loadBalancerIP` (`LoadBalancerIPIgnored`, an address from the pool instead), a sixth address (`QuotaExceeded`).
- **Class `proxcloud.io/internal`** got a MetalLB address on the tenant network.
- **PROXY protocol v2** carried the client's address to the pod.
- **Source ranges.** The allowed outside address passed. The refusal of another outside address was not shown.
- **Policy Local.** The pool checks each worker's health check port: the worker with no local endpoint read `DOWN`.
- **Workers follow.** A new worker was a member on both appliances 8 s after its Node appeared. A removed worker's member left within 29 s.
- **A dead master of the cluster's pair** lost 3.1 s, 3.4 s and 3.4 s. The portal started the stopped appliance again within 2 to 6 s (rc.1's pass on every call; about 70 s on this candidate, not run).
- **An idle TCP connection** survived 330 s.
- **A deleted Service** gave its address back, and a waiting Service had it 30 s later.

### Credentials, suspension, clean-up

- **Nodes that are not the cluster's workers** were refused as members and audited: a tenant added two Node objects with the portal's and an appliance's address, and neither reached the HAProxy config.
- **A rotated credential.** The old one was refused three times, and the controller had the new one after 36 s.
- **A suspended project** changed nothing: the Service waited with the Event `ProjectNotEnabled`, and answered on its address 71 s after the project was enabled again.
- **The gateway down during a Service's delete.** The Service waited with its finalizer and was gone at the first call the gateway took again.
- **A cluster's delete** revoked the credential and removed the pair, its addresses, its rows and the controller.
- **Enable on an existing cluster (class-only).** MetalLB's arguments did not change. An existing Service kept its address. A Service of class `proxcloud.io/lb` answered on a public address after 5 min 46 s, and a Service without a class still got a MetalLB address.

### Billing

- **One floating IP row per address** (one address, and five), owned by the balancer.
- **Traffic counted once:** one counter per appliance on its public NIC, none per address.
- **At the end** the project had no object and no quota in use, and the Proxmox cluster held the guests, rules and tokens it had before.

## Not verified

- **The corrections of this candidate.** Nothing of #424 or #425 has run on a lab: Replace appliances with no outage, a stopped master started by the sync, the one-minute lock, the pass once a minute, the refused credential's audit event. They are tested against the distributions' own systemd, dpkg, HAProxy and keepalived in a container (Debian 13, Ubuntu 26.04) and against a fake Proxmox.
- **A controller following a Service's ports.** A Service added and removed was seen. A port added to or removed from a live Service was not run.
- **Two nodes.** Both appliances ran on one node: VRRP between two nodes, placement on two nodes and the loss of a node were not run. Open connections across a switch were not measured.
- **The consoles.** No page of the tenant or operator console was looked at in the drill; every step went through the API.
- **A production site.** Nothing of v0.11.0 has run on one.
- **The default appliance image.** The lab's appliances ran Ubuntu 26.04 (`config.lbImage`). Debian 13, the default, ran in the container test only.
- **A balancer made before v0.11.0** under this code: "not pushed at the upgrade" rests on tests (the config and its hash are unchanged).
- **Also not run:** NGINX Gateway Fabric in default mode, a cluster made on chart `0.1.16` and then enabled, a scale-down under load with policy Cluster, a project's delete with a balancer, the installer path, the sandbox fix (#420).
- **The upgrade to this candidate.** No move to the BOM `0.11.0-rc.2` has run; its images and its tag's workflows do not exist before the tag.
- **Earlier releases.** Everything the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) list as not verified still holds.

## Known issues

- **No UDP and no TLS termination.** A UDP port of a Service is refused with an Event, and a listener is plain TCP or HTTP. Both are planned for the next release, "complete layer 4".
- **One pair per cluster.** All Services of a cluster share one pair of appliances, each with its own address.
- **In-cluster clients do not pass the pair.** A pod that calls a Service's public address is answered inside the cluster (`ipMode: VIP`): it sees neither a pair outage nor the source ranges. Only a PROXY protocol Service (`ipMode: Proxy`) goes out through the pair.
- **Five public addresses by default.** The built-in project quota is `floatingIps: 5`. In default mode every Service of type LoadBalancer and every Gateway takes one; the sixth waits with `QuotaExceeded`. Raise the project's quota or the provider's default quota.
- **The first Service waits for the pair.** 6 min 7 s on the lab, with packages from apt. An image with the packages baked in (`config.lbImage`) shortens it; not measured.
- **A stopped appliance of a cluster's pair is started within about 70 s**, not at once.
- **An address released before a sync saw it is not billed.** Its floating IP row is made by the services sync. Seen on the lab, which runs no scheduler.
- **Some locks still outlive a dead API.** One balancer's own lock for up to 3 minutes, and a Replace's mark for up to 60 minutes.
- **A new cluster's first MetalLB address can take about 10 minutes.** The pool's first apply fails while MetalLB's webhook starts, and is tried again later. Not new in v0.11.0.
- **One node is not node HA.** Where both appliances run on one node, the loss of the node takes the address down. Where the appliance image is on one node only, both appliances land on it.
- **A switch cuts open connections.** There is no connection state sync between the appliances.
- **A large state is refused whole.** The gateway takes at most 64 KiB per call. A cluster with many Services (around 45 or more, with several ports or long source ranges) may pass that before the 50-Service limit; then no Service of the cluster is updated.
- **A gateway URL that is a host name** leaves the controller's egress port open to any address. Use an IPv4 address.
- **Enable during a cluster's delete** can mint the cluster's credential again. Operator only; do not enable a cluster that is being deleted.
- **IPv4 only.** An IPv6 Service is refused, with an Event.
- **No grace for an address.** A Service deleted and created again gets a new address.
- **Cluster appliances skip the server quota.** Only the addresses count against the quota (`floatingIps`).
- **Cilium is still outside its own support matrix on 1.36.** This candidate does not move it.
- **Earlier releases.** The other known issues in the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) still hold.
