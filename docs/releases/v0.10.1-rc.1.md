ProxCloud v0.10.1-rc.1 is the first release candidate of `v0.10.1`, published as a prerelease. It is the first release whose platform upgrade moves Kubernetes: the seed's k3s and every machine of the platform cluster go from 1.35 to 1.36. It exists so that a lab can run that upgrade: nothing of it has run on a lab yet. It is not for production. `v0.10.0` stays the current stable release.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this candidate is `0.10.1-rc.1`. Against `0.10.0` it moves the seed's k3s from `v1.35.10+k3s1` to `v1.36.6+k3s1`, and the platform cluster from Kubernetes `1.35.10` to `1.36.6` with the node image built for it. It moves no chart, no Cluster API provider and no other image.

## Highlights

- **The platform upgrade moves Kubernetes one minor, in two operator actions.** "Seed and node image" replaces k3s on the seed. "Platform cluster" then replaces every machine of the platform cluster. Each has its own typed phrase.
- **The machine replacement has no way back.** Once the new control plane machine has joined, nothing brings the old machines or Kubernetes 1.35 back. The seed's k3s has a way back by hand, with the etcd snapshot the run saves.
- **Tenant clusters and databases keep their version.** No tenant cluster is upgraded: each stays on the Kubernetes version it has (1.35.10). They are interrupted while the machines under them are replaced: see "Upgrade".
- **Two components are outside their own support matrix on Kubernetes 1.36.** cert-manager `v1.20.2` and Cilium `1.18.16`. Both are accepted as "to be proven by the lab drill".
- **A network with host bits is refused.** Kubernetes 1.36 refuses `192.168.0.5/24` in a new value. The portal now refuses it at its inputs and names the form to write. Stored values keep working.
- **The seed's k3s runs without leader election in three components.** A missed lease under disk load ended k3s on a lab seed.
- **Not run on a lab yet.** Nothing in this candidate: see below.

## Upgrade

Use a lab or another non-production site. Production sites should stay on `v0.10.0` and wait for `v0.10.1`.

These steps upgrade from `v0.10.0`. From an older release, read the [notes of v0.10.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.0) first: their steps and cautions still apply.

1. Upgrade the portal. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1-rc.1/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.10.1-rc.1
   ./proxcloud-up.sh upgrade v0.10.1-rc.1
   ```

2. The platform is not changed by step 1: it stays on its BOM and keeps working. Before you move it, do these three things.

   - **Back up the seed VM.** Run `vzdump <seed VMID>` on the seed's node. The upgrade is refused (`409 seed_backup_missing`) until the portal sees a backup of the seed VM younger than 24 hours, or you confirm one.
   - **Know how to answer the backup question.** On most stores the portal cannot see the seed's backups, and the Check row `seed-backup` says so. Then check in Proxmox that there is an archive of this seed VM, made after the seed VM was created and younger than 24 hours. Then tick the box "I checked in Proxmox: seed VM … has a backup …" in step 4 (`"seedBackupTaken": true` by API).
   - **Read the allow-lists for a network with host bits.** Look at each database's and each tenant cluster's `allowedCidrs`, the Kubernetes provider's default and the sources of the ArgoCD address. Correct a value such as `192.168.0.5/24` through the portal. This is a precaution: a stored value keeps working.

3. Open System → Managed services and read the plan in step 4. The page shows the card **Kubernetes upgrade to release 0.10.1-rc.1** with two actions. From the BOM `0.10.0`, with one control plane machine and one machine each in `system`, `kamaji` and `dbaas`, the plan lists 17 changes and refuses nothing:

   | Change | From → to | Class | Stage | Part |
   |---|---|---|---|---|
   | `roll` (there is no way back) | | machines | `cluster` | Platform cluster |
   | `release` | `0.10.0` → `0.10.1-rc.1` | record only | none | |
   | `kubernetes.version` | `1.35.10` → `1.36.6` | machines | `cluster` | Platform cluster |
   | `kubernetes.nodeImage` | `ubuntu-2604-k8s-1.35.10-…` → `ubuntu-2604-k8s-1.36.6-20261116194043-72f0eaa3d0d4` | machines | `cluster` | Platform cluster (the import is in "Seed and node image") |
   | `seed.k3s` | `v1.35.10+k3s1` → `v1.36.6+k3s1` | seed | `seed-k3s` | Seed and node image |
   | `seed-k3s-job` | Job `proxcloud-system/k3s-upgrade-v1-36-6-k3s1` on the seed | site | `seed-k3s` | Seed and node image |
   | `seed-etcd-snapshot` | `/var/lib/rancher/k3s/server/db/snapshots/pre-upgrade-v1.35.10-k3s1-<node>-<time>` | site | `seed-k3s` | Seed and node image |

   | `roll-vm/controlPlane`, `roll-vm/system@<node>`, `roll-vm/kamaji@<node>`, `roll-vm/dbaas@<node>` | 1 new VM cloned, 1 old VM deleted with its boot disk | site | `cluster` | Platform cluster |

4. Run **Seed and node image**. Type `upgrade <installation name> to 0.10.1-rc.1`. No duration below was measured.

   - **What it does.** It imports the 1.36.6 node image as a template on every Proxmox node the cluster uses (a download of about 2.4 GiB). On the seed it saves an etcd snapshot, writes the k3s config file that turns leader election off in three components, replaces the k3s binary and restarts k3s. Then it compares the seed's charts again.
   - **What stops serving.** The seed's API, expected for about a minute. Meanwhile no machine is repaired, the seed's ArgoCD syncs nothing and no platform run goes on.
   - **What keeps serving.** The platform cluster, every tenant cluster, the tenant API servers and the databases.
   - **It replaces no machine.** Stop here if something looks wrong on the seed: the platform cluster is still on 1.35.10.

5. Run **Platform cluster** (the button **Replace the machines**). Until step 4 is done it is blocked with `seed_not_upgraded`. Type `upgrade <installation name> to 0.10.1-rc.1 and replace its machines`. No duration below was measured.

   - **Control plane first.** A second machine is cloned from the 1.36.6 template and joins, then the old one is removed. The platform cluster's API does not answer from the removal of the old etcd member until the new machine holds the API address, expected one to a few minutes. Meanwhile no tenant cluster or database operation runs, nothing is repaired or failed over, and the consoles show stale status. Running tenant API servers, workloads and databases are expected to keep answering.
   - **Then `system`.** The platform's operators (ArgoCD, Cluster API for tenants, CloudNativePG, MetalLB, cert-manager) restart on the new machine. A MetalLB address may move.
   - **Then `kamaji`.** With one machine in the group, **every tenant API server is away** while its pod restarts on the new machine. Tenant workloads keep running.
   - **Then `dbaas`.** **Every database with one instance on the machine is down** while its pod and disk move. A database with three instances fails over.
   - **A node without room.** A group on a node without room for one more machine is replaced delete-first: everything on that machine is away for the whole clone and join. A control plane node without room refuses the upgrade (`capacity_short`).
   - **Pause.** Pause stops the run between two units, and Resume goes on at the next one.

6. Know the way back before you start.

   - **The seed's k3s has a way back by hand.** If the seed's API does not return, the message of `seed_k3s_timeout` gives one command to run on the seed over SSH. Across a minor the old binary alone is not enough: the command stops k3s and its pods (`k3s-killall.sh`), puts `k3s.prev` back, restores the etcd snapshot the run saved (`k3s server --cluster-reset --cluster-reset-restore-path=<snapshot>`) and starts k3s. Then use Retry. This command was not tried on a lab.

     ```sh
     S="$(ls -t /var/lib/rancher/k3s/server/db/snapshots/pre-upgrade-v1.35.10-k3s1-* | head -n 1)" && test -n "$S" && k3s-killall.sh && mv /usr/local/bin/k3s.prev /usr/local/bin/k3s && k3s server --cluster-reset --cluster-reset-restore-path="$S" && systemctl start k3s
     ```

   - **If that fails, the backup of the seed VM is the last net.** That is why step 2 asks for it.
   - **The machine replacement has NO way back.** Once the new control plane machine has joined the platform cluster's etcd, the run restores nothing. Neither Cancel nor Remove brings the old machines or Kubernetes 1.35 back. A step that fails leaves the machines that still run serving, and Retry goes on at that step. Tenant backups are the only net for a database whose volume does not follow it to the new machine.

7. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.10.0-rc.1` | As from `0.10.0`: 17 changes, the same two actions. Read, not run. |
| A platform on the BOM `0.9.0`, `0.9.1` or a candidate of `0.9.0` | The plan lists 20 changes: the 17 above, the two tenant charts and the cluster chart `0.1.14` → `0.1.15`, which moves with the first step of the replacement. Read, not run: the lab drill covers the move from `0.10.0` only. |
| A platform on a `0.8.x` BOM | The plan lists 23 changes: the 17 above, the two tenant charts, the cluster chart `0.1.13` → `0.1.15` and the three components of platform chart `0.1.2` → `0.1.3`. Read, not run. Move to `0.10.0` first if you can. |
| A platform you move to the BOM `0.10.1-rc.1` | Keep it on a lab. Later builds apply it only while they carry this BOM; `v0.10.1` is planned to. A build without it refuses the platform (`bom_unsupported`). |
| Tenant Kubernetes clusters and databases | They are not upgraded and stay on their version (1.35.10). They are interrupted during step 5 as listed there. Afterwards the Kubernetes provider also offers 1.36.6 for a new tenant cluster; none was created at that version anywhere. |
| An allow-list with a network that has host bits | A stored value keeps working and is not rewritten. A new or changed value must be canonical: the portal answers `192.168.0.5/24 has host bits set: use 192.168.0.0/24`. |
| A site installed with the Ansible installer | Nothing moves. The installer keeps k3s `v1.35.10+k3s1` and Kubernetes `1.35.10`. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |
| A new install | Pass `--version v0.10.1-rc.1` to `proxcloud-up.sh install`. The script's default, the chart and the installer still name `v0.10.0`. |

## What changed

Since `v0.10.0`: three merged pull requests.

### Managed services

- **BOM with k3s `v1.36.6+k3s1` and Kubernetes `1.36.6`** (#397). The node image is `ubuntu-2604-k8s-1.36.6-20261116194043-72f0eaa3d0d4`, built from the same source commit as the 1.35.10 image. It is the first BOM that names another k3s or Kubernetes than the ones before it. The upgrade code is that of `v0.10.0`. See ["Upgrade to Kubernetes 1.36.6"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1-rc.1/docs/managed-services.md#upgrade-to-kubernetes-1366).
- **No leader election on the seed** (#398). The seed is one k3s server. Its kube-controller-manager, kube-scheduler and cloud-controller-manager now run with `leader-elect=false`, from the file `/etc/rancher/k3s/config.yaml.d/10-proxcloud-leader-elect.yaml`. A new seed gets it at first boot. An existing seed gets it in "Seed and node image", and it takes effect with that restart. k3s's own controllers keep their lease.
- **The way back across a k3s minor names the snapshot restore** (#398). The message of `seed_k3s_timeout` and the plan's row `seed-k3s-binary` give the whole command when the move crosses a minor. A patch step keeps the short command. Text only: the product restores nothing by itself.
- **Two components are outside their own support matrix on Kubernetes 1.36.** cert-manager `v1.20.2` lists Kubernetes 1.32 to 1.35; the first cert-manager that lists 1.36 is 1.21. Cilium `1.18.16` lists 1.30 to 1.33 and was outside its list on 1.35.10 already. No source says either breaks on 1.36, and neither was run on it. Both are accepted as "to be proven by the lab drill". An upgrade cannot move a third-party chart in this release, so if one fails on the lab, stop before the next action or unit.
- **The installer path stays on 1.35.** `versions.yml` keeps k3s `v1.35.10+k3s1` and Kubernetes `1.35.10`. The kubectl in the clusterctl image stays at 1.35.10, one minor behind the API servers it talks to.

### Networks

- **A network with host bits is refused where it ends in a Kubernetes field** (#399). Kubernetes 1.36 refuses a new or changed CIDR with host bits, a leading zero or an IPv4-mapped IPv6 address in `loadBalancerSourceRanges`. The portal now answers `400` with the form to write at four inputs: a database's `allowedCidrs`, a tenant cluster's `allowedCidrs`, a Kubernetes provider's default and the sources of the ArgoCD address.
- **Stored values are not rewritten and do not lock their object.** A save that sends a list as it is stored passes. The Check row `argocd-access` warns about a stored source with host bits, and the Kubernetes provider's page names a stored default. A new tenant cluster that takes a stored default gets it without the host bits.

### Fixes

- **A Withdraw or a Delete of a template that changes nothing writes no audit row** (#399).
- **A server's row keeps its Proxmox uuid after an action** (#399). Stop, Start, a snapshot or a NIC change dropped it until the next sync.

### Release

- **BOM `0.10.1-rc.1`.** No chart of the product changed since its tag, so no chart version moved. This build carries the BOMs of `0.8.0`, `0.8.1`, `0.8.2`, `0.9.0-rc.1`, `0.9.0-rc.2`, `0.9.0`, `0.9.1`, `0.10.0-rc.1` and `0.10.0` as previous BOMs.
- **A candidate moves nothing a final moves.** The app chart, the installer pin and the Compose default stay on `v0.10.0`.

## Verified on a lab

Nothing. No upgrade to this BOM has run on a lab or on a site, and nothing was run on this candidate's images: they do not exist before the tag. Everything above is covered by tests only, against a fake seed and a fake Cluster API. This candidate exists to run the lab drill.

## Known issues

- **The upgrade to this BOM has never run on a real seed or cluster.** The seed's k3s upgrade and the machine replacement ran in tests against a fake seed only. It affects every platform moved to this BOM. Run it on a lab first.
- **The machine replacement cannot be undone.** After the new control plane machine has joined, the only nets are the seed VM's backup and the tenants' own backups. Take both before step 5.
- **With one `kamaji` machine every tenant API server is away during its replacement.** With one `dbaas` machine every one-instance database on it is down during its replacement. How long was not measured.
- **cert-manager and Cilium are outside their own support matrix on 1.36.** If one fails after the upgrade, this release cannot move its chart.
- **The `seed-backup` row cannot see a backup on most stores.** The portal token is kept off the seed VM on purpose, and Proxmox leaves the seed's archives out of its list. The upgrade is then started with the box that says a backup was taken. See [the permissions guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1-rc.1/docs/proxmox-permissions.md#what-the-fence-hides-from-the-portal-the-seeds-backups).
- **A backup of the seed can restart its k3s on a stalled disk.** Seen on the lab on `v0.10.0`. The file without leader election is meant to end this; it is on an existing seed only after "Seed and node image", and it was not shown on a lab.
- **An existing seed gets the file without leader election only from an upgrade that replaces its k3s.** No other apply writes it.
- **A stored database allow-list with host bits has no warning of its own.** The list is shown as stored. Read it yourself before step 5.
- **The ArgoCD address may be reachable by tenants.** On a site where tenant traffic leaves under a Proxmox node's address that an operator network contains, tenants reach the login page. The Check row `argocd-access` warns. Leave the address unset there.
- **Earlier releases.** The other known issues in the [notes of v0.10.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.0) still hold.
