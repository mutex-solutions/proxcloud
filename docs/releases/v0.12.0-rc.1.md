ProxCloud v0.12.0-rc.1 is the first release candidate of `v0.12.0`, published as a prerelease. `v0.12.0` offers sandboxes on the managed-services platform: an operator who runs managed Kubernetes and databases from the portal can now add sandboxes there, without the Ansible installer. The candidate exists so that a lab can run the drill of this code: nothing of it has run on a lab yet. It is not for production. `v0.11.1` stays the current stable release and `latest`.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this candidate is `0.12.0-rc.1`. Against `0.11.1` it moves two things: the platform's own cluster chart, `proxmox-kamaji-cluster` `0.1.16` → `0.1.19`, and a new component, the sandbox chart `proxcloud-sandbox` `0.1.0`, which is installed only where the settings ask for sandboxes.

## Highlights

- **Read the first six points of "Upgrade" before you upgrade.**
- **Sandboxes on the managed platform, in two placements.** `shared`: a node group `sandbox` of the platform cluster. `separate`: a hosted cluster of its own, `pc-sandbox`, whose control plane runs as pods on the platform cluster's `kamaji` group (about 0.6 GiB) and which needs one more machine for the sandbox proxy. `off` is where every installation starts.
- **What a tenant gets.** Sandboxes on gVisor with the E2B-compatible API and the native one, and four built-in templates at the images this release pins: `base`, `code-interpreter-v1`, `python` and `mcp-gateway`. Each sandbox answers at `https://<port>-<id>.<domain>`. A tenant sees nothing of it until the operator has set the provider live and attached it to the tenant's project.
- **What an operator does.** Four settings under **Sandboxes** on the install page or in **Settings** of a ready platform: the machines, one address range for them inside the platform network, one address for the sandbox proxy, and a DNS name whose wildcard points at that address. Then Check, the plan, and an apply.
- **The provider is registered disabled, and a run never sets it live.** The operator sets it live on its page under **Cloud providers**. That save is refused while one of four release gates does not hold, and while the job scheduler is off.
- **The job scheduler is required.** It writes the firewall of each sandbox machine, keeps watching it and ends sandboxes that are gone. Switching it on also starts charging usage.
- **What a shared node group gives up, as the console prints it before the tick.** Code that escapes a sandbox (a gVisor escape) is root on a machine of the platform cluster: the cluster that runs the datastore of every tenant's Kubernetes control plane, every tenant's API server, every tenant database and ArgoCD. The pod network is open to that machine, and network policies do not stop it. What protects the targets then is their own authentication. Sandboxes have no address of their own to the internet: abuse from a sandbox leaves under your site's public address. `shared` is the homelab choice: one operator, no outside tenants. See Known issues for the full list.
- **A separate cluster limits the same escape to the sandbox cluster**: other tenants' sandboxes on it, its own control plane's API and the internet.
- **An existing platform gets nothing of sandboxes until its operator asks**, and asking is possible only after the platform's own upgrade to this BOM.
- **The platform upgrade replaces no machine.** From the BOM `0.11.1` the plan has exactly three rows, and the run checks on the real cluster that no machine would be replaced before it syncs anything.
- **Fourteen dependency updates** (#484). One of them changes an answer: an `ssh-dss` public key is refused.
- **Not run on a lab yet.** Nothing in this candidate. Only the method was tried by hand, on 2026-11-21, before the code existed.

## Upgrade

Use a lab or another non-production site. Production sites should stay on `v0.11.1` and wait for `v0.12.0`. These steps upgrade from `v0.11.1`. No duration below was measured.

### Read these six first

1. **The platform upgrade has exactly three rows from the BOM `0.11.1`, and replaces no machine.** The rows: `release`, record only; the platform's own cluster chart `proxmox-kamaji-cluster` `0.1.16` → `0.1.19`, class chart; and `sandbox`, the sandbox chart, class added. From the BOM `0.11.0` there is one more, record only: the cluster chart for new tenant clusters, `0.1.17` → `0.1.19`. No machines row, no parts, no seed backup. **The run proves it itself**: before it syncs anything of the cluster chart, it lets ArgoCD compare the live cluster with chart `0.1.19` and reads the comparison. A machine template or bootstrap template that is new or would change, or a control plane that would change, stops the run with `unexpected_rollout`. Nothing was synced then, every machine runs as before, and the Application `pc-platform` is left at the new chart version without automated sync. See step 4.
2. **An existing platform gets nothing of sandboxes until its operator asks, and asking is possible only after the upgrade.** Upgrading the portal changes no platform. On a platform that is still on the BOM of an earlier release the page shows no Sandboxes block, and a save with the block answers `400 invalid_installation`, naming the release to upgrade to. The platform upgrade itself builds nothing of sandboxes: no pool, no ACL row, no token, no machine, no Application, no provider. Only then is the block taken, and only an apply after that save builds anything.
3. **Asking writes on Proxmox, with the portal token.** The pool `proxcloud-sbx`. With `shared`, one ACL row: the platform's Cluster API token `capmox@pve!capi` with `ProxCloudCAPI` on `/pool/proxcloud-sbx`. With `separate`, a token of its own, `capmox@pve!pc-sandbox`, minted as a tenant cluster's token is. Then the sandbox machines in that pool, the VM firewall of each of them, and the pool's security groups and IP sets in the cluster firewall. **No new role, no new privilege and no row for root to add.** What the two root scripts must have granted: the portal token's platform role on `/pool` with propagate, `Sys.Modify` on `/`, and for `separate` also `User.Modify` on `/access/groups/proxcloud-kube` and the mint role `ProxCloudKubeMint` (`Permissions.Modify`) on `/storage`, `/sdn/zones` and `/nodes`, as for a tenant cluster's token. A site set up by an older script runs both again as root. The Check's `sandbox` row reads these rights.
4. **The provider is registered disabled, and four gates stand before "live".** `noderestriction`, `isolation`, `fence` and `network-guard` must hold at the save that sets the provider live, and are read again before every sandbox create. The save is also refused while the job scheduler is off. A new sandbox machine passes `fence` about 20 minutes after it joined. The gates are necessary and not sufficient: see step 8.
5. **An `ssh-dss` (DSA) public key is refused** (#484). A key pair import answers `400` "ssh-dss (DSA) keys are no longer accepted: use an ed25519, ecdsa or rsa key", where it took the key before. A platform installation whose settings hold such a key under `spec.seed.sshKeys` is answered that the entry "is not an SSH public key": replace it before you save the settings again. OpenSSH itself no longer accepts these keys.
6. **From `v0.11.0`, the upgrade notes of `v0.11.1` still hold.** Its six first points apply to a site that skips `v0.11.1`: the floating IP rows billed from their allocation time, the one push of every load balancer, the cluster chart a cluster needs for UDP and TLS, `proxcloud.io/lb-internal`, the kept addresses before a rollback, and the silent UDP port. Read the [notes of v0.11.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.11.1) first. From `v0.11.1` none of them happens again: no file of a load balancer appliance changed since `v0.11.1`, so no balancer is pushed.

### Steps

1. **Before the upgrade, look at two things.**

   - **The platform's BOM.** The move is planned from the BOMs `0.10.1`, `0.10.2`, `0.11.0`, `0.11.1` and their candidates. A platform on an older BOM (`0.8.0` to `0.10.0` and their candidates, all on Kubernetes 1.35.10) is refused by this build. Move it to `0.10.1` first with the `v0.10.1` build, both parts, as the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) describe.
   - **Do not change machine sizes, nodes or node groups together with the upgrade.** Apply such a change before it or after it. Together with the upgrade it is what `unexpected_rollout` refuses.

2. **Upgrade the portal.** On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. `compose.yaml` did not change since `v0.11.1`. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.12.0-rc.1/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.12.0-rc.1
   ./proxcloud-up.sh upgrade v0.12.0-rc.1
   ```

   - **Nothing changes on the platform or on Proxmox by this step.** The platform stays on its BOM. No load balancer is pushed.
   - **No Sandboxes block yet.** The page shows none, and a save with `spec.sandbox` answers `400 invalid_installation`: "Upgrade the platform to release 0.12.0-rc.1 first".

3. **Read the plan.** Open System → Managed services and read the plan in step 4. It refuses nothing. From the BOM `0.11.1` (and from its five candidates) it lists three changes:

   | Change | From → to | Class | Stage | Wave |
   |---|---|---|---|---|
   | `release` | `0.11.1` → `0.12.0-rc.1` | record only | none | |
   | `pc-platform` (seed) | `proxmox-kamaji-cluster` `0.1.16` → `0.1.19` | chart | `cluster` | 3 |
   | `sandbox` (platform cluster) | none → `proxcloud-sandbox` `0.1.0` | added | `workload-platform` | 4 |

   From the BOM `0.11.0` (and from `0.11.0-rc.1` and `0.11.0-rc.2`) there is a fourth: `tenantCharts.kubernetes`, `proxmox-kamaji-cluster` `0.1.17` → `0.1.19`, record only.

4. **Run the platform upgrade.** Type `upgrade <installation name> to 0.12.0-rc.1`. There is one action, with no parts, and no seed backup is asked for.

   - **The cluster chart row.** In stage `cluster` the run applies the Application `pc-platform` at chart `0.1.19` without automated sync, waits until ArgoCD has compared the cluster with it, and reads the comparison. When no machine template, bootstrap template or control plane is out of sync, it records the check (`rolloutChecked` in the stage's receipt) and applies the Application as always, automated.
   - **Why nothing should differ.** For a platform without a sandbox group, chart `0.1.19` renders the objects chart `0.1.16` renders. That was compared in the release's tests for each of the fourteen BOMs an upgrade is allowed from, and once by hand with the published charts. On a lab it was not run.
   - **`unexpected_rollout`.** The comparison found a machine template or bootstrap template that is new or would change, or a control plane that would change: Cluster API would replace machines. Nothing was synced and every machine runs as before. The Application `pc-platform` is left at chart `0.1.19` without automated sync. If machine sizes, nodes or node groups were changed together with the upgrade, put them back and **Retry**. Otherwise the release is at fault: stop, change nothing by hand and report it. Sandboxes are not tried on such a platform.
   - **The sandbox row.** The chart is rendered only for settings that ask for `shared`, so on a platform without the block nothing is synced for it, and the platform's record does not list it.
   - **What the run does not do.** It replaces no machine, restarts no pod of a tenant and writes nothing on Proxmox. It makes no pool, ACL row, token, sandbox machine, sandbox Application or sandbox provider.
   - **From `0.11.0`** the run also writes chart `0.1.19` on the Kubernetes provider: new tenant clusters get it, and an existing one keeps its chart until its own chart upgrade.

5. **Decide whether to ask for sandboxes.** Skip the rest and nothing changes.

   - **Before.** The datacenter firewall is on: no VM firewall filters a packet while it is off, and the Check's `sandbox` row fails. The job scheduler runs (`PROXCLOUD_JOBS_SCHEDULER_ENABLED`). The two root scripts ran in their current form (the third point above).
   - **Addresses and a name.** One free aligned CIDR inside the platform network for the sandbox machines, with room for one more machine per node. One address for the sandbox proxy: with `shared` a free address of the load balancer range, with `separate` a free address of the platform network outside every range. A DNS name whose wildcard `*.<domain>` resolves to the proxy address where clients are.
   - **The way from the internet is yours.** A managed platform has no entry appliance. Where a router translates the platform network, it forwards TCP 443 of a public address to the proxy address, and it decides who may reach it.
   - **`shared` is saved only with the tick** under the text on what it gives up.

6. **Save, Check, plan, apply.** Under **Sandboxes** in **Settings**, choose the placement and fill the machines, the range, the proxy address and the domain.

   - **Check** adds the rows `sandbox` and `scheduler`, and the `capacity` row counts the sandbox machines and one spare per node. It fails for machines that no run has placed yet and that do not fit.
   - **The plan** lists three rows: `sandbox` (the machines, and how many sandboxes a machine of that size holds), `sandbox-pool` and `sandbox-access` (the ACL row, or the token).
   - **The apply** makes the pool and its access, builds the machines beside the existing groups, syncs the sandbox chart and registers the provider "\<name> Sandboxes", disabled. The run's check lets through the new group's machine templates and nothing else: no other machine of the platform cluster is replaced.
   - **What it writes on the Proxmox provider.** The sandbox range as a sandbox network, and the settings of the fence. The next provider sync writes the isolation rules for the range.
   - **The certificate.** The run makes one self-signed certificate for `*.<domain>` and keeps its key sealed. The Ready card offers the certificate for download.

7. **Wait for the fence, then read the gates.** A provider sync writes the VM firewall of each sandbox machine and takes its `unsecured` taint off, about 20 minutes after the machine joined. **Check the release gates** on the Ready card reads the four gates without changing anything.

   | Gate | Holds when |
   |---|---|
   | `noderestriction` | The API server refuses a node identity a `node-restriction.kubernetes.io/` label on its own Node |
   | `isolation` | The cluster firewall holds the isolation rules for the sandbox range |
   | `fence` | Every Node that may take a sandbox is a VM of the sandbox pool whose firewall reads back as written, pinned to the Node's address |
   | `network-guard` | Cilium leaves the CNI config to the network guard and its heartbeat is fresh, on every node that takes sandboxes |

8. **Go live.** On the provider's page under **Cloud providers**, set a price for sandbox minutes, choose a status other than Disabled and save. Attach the provider to projects as the two others.

   - **The save is refused** while a gate does not hold, or while the scheduler is off (`409`).
   - **The price rule holds a placeholder rate** until you set one, or 0.
   - **Clients must trust the run's certificate** (`SSL_CERT_FILE`, `NODE_EXTRA_CA_CERTS` for the JavaScript SDK). An operator's own certificate cannot be stored yet.
   - **Before a site with outside tenants goes live**, the gates are not enough. The drill of this candidate must have shown the fence from inside a sandbox machine. The placement must be `separate`, unless the text on `shared` was read and accepted for that site. The router must restrict who reaches the proxy address. A real invoice must have shown the sandbox line.

9. **Switching sandboxes off.** Disable the provider and let its sandboxes end first: the save of `placement: off` is refused (`409 sandbox_provider_live`) while the provider is not disabled, and so is the run. The apply then deletes the sandbox Application, the machines, the fence settings, the pool's firewall groups and IP sets, the ACL row or the token, and the pool. A VM of another owner in the pool makes the run wait and name it.

10. **Follow each row of this table that matches your site.**

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.11.1` or one of its five candidates | The plan lists three changes (step 3). |
| A platform on the BOM `0.11.0`, `0.11.0-rc.1`, `0.11.0-rc.2`, `0.10.2` or `0.10.2-rc.1` | Four changes, allowed: those three and the tenant chart to `0.1.19`, record only (from `0.1.17`, or from `0.1.16` for the two of `0.10.2`). |
| A platform on the BOM `0.10.1`, `0.10.1-rc.1` or `0.10.1-rc.2` | Six changes, allowed: those four and `cert-manager` `v1.20.2` → `v1.21.3` on the seed and on the platform cluster. From `0.10.1-rc.1` the platform's cluster chart moves from `0.1.15`. Back up the cert-manager resources first, as the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) describe. |
| A platform on an older BOM | Refused (step 1). |
| A portal that comes from `v0.11.0` | Read the [notes of v0.11.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.11.1) first (the sixth point above). |
| A sandbox cluster of the Ansible installer on the same Proxmox provider | The provider fences one sandbox pool. The save and the run refuse the block (`sandbox_refused`) while the provider holds another owner's sandbox settings. Remove that sandbox cluster and its settings first. |
| Two portals on one Proxmox cluster | Only one of them can build sandboxes: the pool name and the token name are fixed. |
| A platform whose `separate` sandbox cluster exists | A later upgrade that replaces the platform cluster's machines is refused while it exists. Set `placement: off`, apply, upgrade, then set `separate` again: the cluster is built new. |
| A site installed with the Ansible installer | Its ProxCloud pin stays `v0.11.1`. The installer path was not drilled. |
| A new install | `proxcloud-up.sh install` still takes `v0.11.1` by default. Pass the candidate's version to try it on a lab. |

11. **If you roll the portal back to `v0.11.1`.** A platform that was moved to the BOM `0.12.0-rc.1` is not known to an older build: that portal refuses the platform (`bom_unsupported`) until the roll forward. A rollback before step 4 leaves the platform on a BOM the old portal knows. No rollback ran on a lab.

## What changed

Since `v0.11.1`: four merged pull requests, with `main` at `65c24cc0`, where these notes were closed. The release pull request of this candidate is not counted. A pull request merged after that commit and before the tag is not described here: the list GitHub adds below these notes names it, and the [Unreleased section](https://github.com/mutex-solutions/proxcloud/blob/v0.12.0-rc.1/CHANGELOG.md#unreleased) of the changelog describes it.

### Sandboxes on the managed platform

- **Sandboxes are offered** (#483). The BOM names the sandbox chart `proxcloud-sandbox` `0.1.0` as the component `sandbox`, and moves the platform's own cluster chart to `0.1.19`, the first pin that gives a node group a pool, an address range and DNS servers of its own. The code was in `v0.11.1`, switched off (#422, #423, #432, #436): no BOM named the chart.
- **Two placements** (#432). `shared`: a node group of the platform cluster, with its machines in pool `proxcloud-sbx`, addresses from its own range, and the taints `proxcloud.io/sandbox` and `proxcloud.io/unsecured`. `separate`: the cluster `pc-sandbox`, built with the tenant cluster chart, with the sandbox chart as its add-on and a system machine for the sandbox proxy.
- **The sandbox provider** (#436). Registered disabled, with the E2B-compatible API on, the four templates by digest, an egress cap of 100 Mbit/s and the abuse check in `alert` mode. A later apply adopts the row and keeps what you changed.
- **The fence** (#436). The provider sync fences every VM of pool `proxcloud-sbx` and no other. Both policies are DROP and every rule is an ACCEPT, so a missing rule closes more. The platform's prefix is denied in both placements.
- **The portal's identities on a shared cluster are narrowed** (#423, #436). Admission policies of the chart hold the portal's identity to the project namespaces `sb-<projectId>`, and hold every pod of such a namespace to the gVisor runtime class with no host access.
- **The built-in template images are those of the Actions build of 2026-11-23** (#483). On the managed platform they move with a release and no other way.
- **A run no longer overwrites another owner's sandbox settings that name no pool** (#483). It refuses them, as it refuses a block with a pool.
- See ["Sandboxes on the platform"](https://github.com/mutex-solutions/proxcloud/blob/v0.12.0-rc.1/docs/managed-services.md#sandboxes-on-the-platform), ["The sandbox provider"](https://github.com/mutex-solutions/proxcloud/blob/v0.12.0-rc.1/docs/managed-services.md#the-sandbox-provider) and [the Proxmox rights](https://github.com/mutex-solutions/proxcloud/blob/v0.12.0-rc.1/docs/proxmox-permissions.md#sandboxes-on-the-managed-platform).

## Verified on a lab

Nothing of this code. One thing ran on a lab before the code was written: a spike of the method, by hand, on 2026-11-21. It is not a test of this code.

- **Where.** A throwaway tenant cluster on one lab, made through the product: Kubernetes 1.36.6 on the platform's node image (Ubuntu 26.04, kernel 7.0, containerd 2.3.2), Cilium 1.18.16, workers of 2 vCPU and 2 GiB. The platform cluster itself was only read.
- **gVisor on the node image.** runsc 20261116.0 installed in 33 s and ran pods; a first gVisor pod was Ready in 3.0 s, with no AppArmor or seccomp denial in the journal.
- **Start times.** A cold start of `base` took 127 s, all but 2 s of it the image pull. A warm start took 3 s.
- **Room.** A node of 2 vCPU took exactly one sandbox of one vCPU. An idle sandbox cost about 35 to 50 MiB of host memory.
- **Egress from a sandbox with the planned policies.** Internet on 443 and 587 open, 25 closed. Every in-cluster and private target timed out: the cluster's API, both kubelets, another namespace, another project's sandbox, the lab's hosts and the link-local address.
- **The egress cap.** A cap of 10 Mbit/s measured 9.4 Mbit/s, three times. Without a cap, 331 to 401 Mbit/s. The network guard refused a sandbox pod without a cap.
- **Admission policies.** A policy saw `exec` into a pod and refused it outside the project namespaces. A privileged pod, a pod without the gVisor class, a host path, host namespaces and an added capability were each refused.
- **What the spike did not cover.** The platform cluster as the place of the node group. The pool `proxcloud-sbx`, the ACL row and the token. The VM firewall of a sandbox machine. The provider, its gates and the scheduler. The `separate` placement. The upgrade. Any code of this candidate.

Everything else rests on tests: a fake Proxmox that stores rules and filters no packet, fake ArgoCD, Cluster API and Kamaji, fake clusters, and the real charts rendered, not installed.

## Known issues

### What a shared node group gives up

The install page prints this text, shortened here, and saves `shared` only with a tick under it. The points on the portal token and on the Ready card are from the guide.

- **Code that escapes a sandbox is root on a machine of the platform cluster.** That cluster runs the datastore of every tenant's Kubernetes control plane, every tenant's API server, CloudNativePG and every tenant database, and ArgoCD.
- **The pod network is open to that machine.** It is a Cilium peer and can send packets with any source to any pod. Network policies do not stop it. What protects the targets is their own authentication: client certificates on the datastore, passwords on the databases, tokens on the API servers.
- **The Cilium agent's credential on that machine can create and change CiliumNode objects.** A forged one pulls another node's pod traffic to the escaped machine. Traffic between pods that is not encrypted with both ends authenticated can be read and forged.
- **The machine also holds** the kubelet's credential (its own Node and the Secrets of the pods on it), the network guard's (it reads every pod's spec) and kube-proxy's.
- **No address of their own to the internet.** Abuse from a sandbox leaves under your site's public address. This holds for `separate` too.
- **A stolen portal token reaches a node of the platform cluster** through a sandbox machine's console, guest agent or disks. On every other platform node it holds `NoAccess`.
- **What still holds.** The machine's VM firewall keeps the Proxmox API, the seed, the management networks, tenant networks and every address of the platform network that is not a machine of the cluster closed to it. Of the cluster's own machines it reaches the pod tunnel, the health port, ICMP and the Kubernetes API port, nothing else, and it cannot take another machine's address.
- **The provider reads "reduced isolation"** on the Ready card.

### Limits

- **A machine of 2 cores holds one sandbox of one vCPU.** A sandbox asks for whole cores, and the node's own pods need a part of one. Take 4 cores or more for several. The plan's `sandbox` row says the figure for the size chosen.
- **A template of 2 vCPU does not fit a machine of 2 cores.** `code-interpreter-v1` and `mcp-gateway` ask for 2 vCPU. On the Homelab preset's machine they are expected to stay pending, and only `base` and `python` to start. Read in the code and in the spike's figures, not run.
- **No sandbox registry, no custom templates, no snapshots.** The other built-in templates of the installer path, the GPU one among them, are not there either. Pause and resume are held on every path.
- **No entry appliance.** The way from the internet to the proxy address is the operator's: a DNS wildcard, and a router that forwards TCP 443.
- **With `separate`, the proxy address takes any source on 443.** Your router decides who reaches it.
- **Prices are placeholders.** The price rule for sandbox minutes holds a placeholder rate until you set one. Switching the scheduler on starts charging usage.
- **Fixed names.** The pool `proxcloud-sbx` and the token `capmox@pve!pc-sandbox` are fixed, so two portals on one Proxmox cluster collide: only one can build sandboxes.
- **A self-signed certificate only.** An operator's own certificate is refused at the save. Every client must trust the run's certificate.
- **The placement is fixed once built.** It changes only to `off`. From `shared` to `separate`: `off`, apply, then `separate`. The range and the proxy address are fixed as well.
- **`pc-sandbox` is not upgraded in place.** An upgrade that replaces the platform cluster's machines is refused while `separate` exists or is asked for. With `shared`, such an upgrade replaces the group last, and every sandbox on a replaced machine ends.
- **A first start of a template the machines did not pull ahead waits for its pull.** `base` and `code-interpreter` are pulled ahead. In the spike a cold start of `base` took about two minutes.
- **The templates come from two registries.** `python` is pulled from docker.io, the others from ghcr.io.
- **Template images move with a release only.** The template update job of the installer path does not run here.

### Open findings of the reviews

- **Sandboxes cannot be asked for in the same step as the BOM move.** The save is refused until the upgrade is done: upgrade first, then save the block.
- **A record that holds the block under an older BOM still shows the three sandbox rows in the plan.** The save refuses such a record, so only a write past the save makes one. The run refuses it with `sandbox_refused`.
- **The sandbox chart's own images carry odd tags.** Chart `0.1.0` pins the runtime at the tag `dev-d26edd2` and the proxy at `v0.11.0-rc.1`, both by digest. The runtime is the first build whose network guard works on a shared node group.
- **With `separate`, the sandbox chart inside `pc-sandbox` is named by version, not by digest.**
- **The sync fences every VM it finds in pool `proxcloud-sbx`**, also one that another hand put there. It is closed, never opened. The Check's `sandbox` row names it.
- **A sandbox machine takes sandboxes about 20 minutes after it joined**, and only once a provider sync ran. With the scheduler off, one operator sync fences once and nothing watches afterwards.
- **"All projects" waits while the provider is disabled.** The attach choice is applied once the provider is live.
- **When the `shared` ACL row is deleted by hand**, the Check's rows `machines` and `boot-store` degrade and the `sandbox` row warns, until the next apply writes it again.
- **A sandbox machine resized in place only warns on capacity**, as every other group does.
- **No Check reads that the proxy address of `separate` is free.** The `sandbox` row reads the platform cluster's Services only.
- **With a bridged platform network, the isolation rules see routed traffic only.** Inside the network the VM firewall is what holds.

### Still true from v0.11.1

No change merged since `v0.11.1`, up to the commit named under "What changed", answers one of its known issues. All of them stand. Those an operator meets first:

- **UDP only on a pair**, and a UDP server never sees the client's address.
- **Private keys of certificates** rest encrypted in the database, in `backups/` next to the copy of `.env` that opens them, and in clear on each appliance's disk.
- **Only `proxcloud.io/lb-*` annotations are read.** A Service that asks for an internal balancer under another cloud's annotation name gets a public address.
- **The gateway has no rate limit per cluster.**
- **The balancer says "the platform tries again within half a minute"** also when its six retries are over.
- **A certificate with a signature the appliance's HAProxy refuses** is taken by the upload and refused at the push.
- **A services sync can archive the floating IP row a pass just wrote.** The next pass or sync writes it again.
- **With the scheduler off, a project's delete answers `SCHEDULED_FOR_DELETION`** though nothing will delete it.
- **The sandbox invoice line.** A bill with sandbox items that round to 0.00 gets one summed item, "Sandbox runs below 0.005 each (n)". It was not seen on a sent bill.
