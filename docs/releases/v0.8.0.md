ProxCloud v0.8.0 is a feature release on top of `v0.7.0`. Its main addition is the managed-services platform: managed Kubernetes and managed databases, installed on your Proxmox VE cluster from the operator console. The platform is off by default.

## Highlights

- **Managed services from the operator console.** System → Managed services installs, repairs and removes a platform on your Proxmox VE cluster: a seed VM, a platform Kubernetes cluster, Kamaji, CloudNativePG and the two providers.
- **Pinned by a bill of materials.** A run applies exactly what the release's bill of materials (BOM) lists: every chart, image and download, with a version and a digest that CI compares with the registries.
- **Managed Kubernetes placement and status.** On sites without shared storage, workers are placed by free capacity. A cluster that is not there yet says why, per node group, with a "needs attention" state.
- **Managed databases on the platform cluster.** Databases are placed on their own node group, behind an egress fence. No tenant database is recorded healthy on a lab yet: see "Not verified".
- **Template updates: publish on all nodes.** One action publishes a Kubernetes node image on every node of a provider, for sites that keep a copy on each node.
- **Fixed Ubuntu 26.04 VM images.** Images exported before the fix can come up with a read-only root filesystem after a reboot. The four images were exported again; the affected tags stay in the registry.
- **Security.** The portal token can create Proxmox API tokens for two service users only, where it could for every user, `root@pam` included. ArgoCD's `default` project is locked on installer-built services clusters.

## Upgrade

These steps upgrade from `v0.7.0`. Read the linked guide sections before you start: they hold the exact steps.

1. On the Docker Compose host, check out the tag and run the upgrade. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.8.0
   ./proxcloud-up.sh upgrade v0.8.0
   ```

2. Managed services stay off after the upgrade. To turn them on, install with the switch. It also turns template updates on. Read the [managed-services guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/managed-services.md) first.

   ```sh
   ./proxcloud-up.sh install --managed-services
   ```

3. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| Ubuntu 26.04 templates imported before the fix | Import the fixed tag, publish it, then withdraw the affected one. The **Imported templates** tab shows each digest, and the affected tags and digests are [listed here](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/public-vm-sanitization.md#known-issue-stale-orphan-file-inode-in-ubuntu-2604-images-published-before-the-fix). Ubuntu 24.04 images are not affected. |
| Servers or Kubernetes nodes cloned from an affected Ubuntu 26.04 template | They keep the defect. Test and repair them as the [template updates guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/template-updates.md#known-issue-ubuntu-2604-images-exported-before-the-orphan-file-fix) says. Do not reboot a VM that has logged the error. |
| Managed Kubernetes with the mint grant: an installer site in split mode, or a site that ran the managed-services script of a build of `main` | Run `make upgrade` on the installer site, or the managed-services script again as root on a node, once per portal token. Until then the preflight row `mint-scope` fails and Test connection warns. See ["An existing site"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/proxmox-permissions.md#an-existing-site). |
| Managed Kubernetes, on any site | Make sure every Proxmox node has `libpve-access-control` 9.2.1 or later. The product does not check it. |
| An installer-built services cluster | Expect the next `make install` (stage 50) to lock ArgoCD's `default` project. It first stops on any Application still in that project: move each one, and its provider, to a named project, then run it again. |
| An installer-built site, older token rows | Stage 10 adds narrower rows for the CAPMOX and CSI tokens. It leaves the broad ones for you to remove. |
| Scripts against the API | Check four behaviour changes. An `imageId` sent for a node group is ignored. A tenant network in a VLAN zone has no DHCP and no SNAT, and asking for either is a `400`. A project's "Delete now" answers `409` while the job scheduler is off. An `UPGRADE` of a tenant cluster on a provider that offers no version is refused. |
| A platform installed from a `dev-<sha>` build of `main` | This release refuses it (`bom_unsupported`). Keep the build that installed it, or Remove and install again. See ["Not implemented yet"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/managed-services.md#not-implemented-yet). |

## What changed

This section groups and shortens about a thousand lines of changelog. The [changelog of 0.8.0](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/CHANGELOG.md#080---2026-11-17) has every entry in full.

### Operator console

- **Managed services page.** System → Managed services walks through the installation: settings, the Proxmox identities script, the checks with what to do for each failed one, the review, and the run with its stages, Retry and Cancel.
- **A ready installation.** The page shows the live state of the components and the two providers. It offers the seed kubeconfig download, the seed credential replacement, and Remove behind a typed confirmation.
- **Machines dialog.** On a cluster's row of the Kubernetes provider page, **Machines** shows what Cluster API reports per worker, with credentials cut out.
- **Platform setup.** Platform setup and the Dashboard gain an optional `managed` step after Go live. Go live never waits for it.

### Managed services

- **Install as a durable job.** A run has eleven stages, from the checks to the two providers. It resumes after an API restart, and Retry, Cancel and Remove are part of it. The [operator guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/managed-services.md) lists every stage and every failure code with cause and action.
- **Bill of materials.** `deploy/platform/platform-bom.yaml` (`0.8.0`) pins Kubernetes 1.35.10, the seed and node images, k3s, the Cluster API providers and every chart. Nothing in it is pending.
- **No upgrade between BOMs yet.** A platform installed from another BOM is refused (`bom_unsupported`). `seed.mode: existing` is not implemented either. See ["Not implemented yet"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/managed-services.md#not-implemented-yet).
- **Proxmox identities script.** The setup script creates the roles, the pool `proxcloud-seed`, the users `capmox@pve` and `csi@pve` with their tokens, and the portal's mint grant. See the [permissions guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/proxmox-permissions.md#managed-services).
- **Preflight checks.** The Check reads only. It covers both tokens' privileges, the fence of the platform pools, the ISO store, the stores, and the isolation of the platform network. New rows include `token-scope`, `mint-scope` and `tenant-network`.
- **Break-glass access.** The seed kubeconfig download is a one-hour cluster-admin kubeconfig, and it is audited. A seed credential rotation writes its own audit entry (`ROTATE_CREDENTIAL`).
- **Seed backup and restore.** The guide gives the restore sequence over the protected seed VM, and the backup job with compression and pruning. A backup taken before a seed credential rotation cannot be restored from. See ["Credentials and the seed backup"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/managed-services.md#8-credentials-and-the-seed-backup).
- **Fixes from the lab runs.** A seed that restarts no longer ends the run. Stage 7 now sees a machine that failed and names it. A failed ArgoCD sync hook no longer passes for done. Remove lists what it deleted, left and did not check.
- **Isolation rules.** The provider sync writes the isolation rules of a provider that has an installation, with or without a project. The order is: save the installation, run a provider sync, then run the Check.

### Kubernetes

- **Placement by free capacity.** On a site without shared storage, a new worker goes to a node that holds the image and has the storage, CPU and memory free. Running workers never move. A request that does not fit answers `409` with how many fit. See ["How a cluster lands on Proxmox"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/managed-k8s.md#9-how-a-cluster-lands-on-proxmox).
- **Existing sites and placement.** They get it only after the operator sets the provider's `chartVersion` to 0.1.13 and bumps each cluster. A platform installed from this BOM registers its provider with 0.1.13.
- **Why a cluster is not there yet.** Each unsettled node group carries a reason code and a fixed text for the tenant. A group without progress for 15 to 90 minutes needs attention, shown as an amber chip. See ["Provisioning status"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/managed-k8s.md#provisioning-status-reason-and-needs-attention).
- **Installer-built sites and the status.** Re-apply `deploy/mgmt-cluster/rbac.yaml` to get the new status fields. Until then they are absent and nothing else changes.
- **Free memory is counted differently, on every site.** Placement now also counts memory used by VMs the provider's token cannot see, and by the host itself. A node can read less free than before, so a server create or a worker placement that passed can answer `409`. For the ZFS ARC, cap it (`zfs_arc_max`).
- **Smaller fixes.** `SET_NODE_GROUPS` takes a node group without `rootVolumeGiB` when the provider has a default. A cluster create on a provider that offers no version is refused before anything is reserved.

### Managed databases

- **Placement and egress fence.** Two optional provider keys keep tenant control planes and databases on their own node groups. They also limit a database namespace's pods to that namespace, DNS and the API server. See the [managed databases guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/managed-dbaas.md).
- **The fence and backups.** The egress fence is refused together with `config.database.backup`: it has no object-store rule yet.
- **PostgreSQL on Ubuntu 26.04 nodes.** The Kubernetes node images now set the AppArmor sysctl a PostgreSQL container needs on kernel 7.0.0-42 and newer. Without it no PostgreSQL database comes up.

### Templates and images

- **Publish on all nodes.** **Publish on all nodes…** on a version's row publishes every node whose smoke test passed, and starts at most one import or smoke test at a time. A failed import or smoke test is not repeated, and nothing is withdrawn. See ["Publish on all nodes"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/template-updates.md#publish-on-all-nodes).
- **Blocked state.** When a copy's smoke test, import or publish has failed, the action now says `blocked` instead of "Nothing more to do". API clients that only know `done` must treat `blocked` as "stop posting".
- **Ubuntu 26.04 orphan-file defect.** The export now removes the stale ext4 field and refuses an image that still has it. The fixed tags are `ubuntu-2604-os-20261116170652-72f0eaa3d0d4` and the three `ubuntu-2604-k8s-*-72f0eaa3d0d4` images. The BOM pins the fixed seed and node image.
- **Kubernetes node templates.** Template updates now puts the cloud-init drive on `ide0` for a Kubernetes node image. A template imported earlier with the drive on another slot fails its smoke test (`template_mismatch`), with the `qm set <vmid> --delete <slot>` command.
- **Smoke test.** It no longer needs a package mirror on the smoke network, and keeps cloud-init's own error in the record when it fails.

### Networking

- **VLAN zones.** A tenant network in a VLAN zone is written and answered without DHCP and SNAT, which Proxmox does not do there. The site's router is its gateway.
- **Provider sync.** The sync again retires the rows of servers and volumes that are gone, on the documented Proxmox grants. It retired none before, so a deleted worker could stay ACTIVE in a tenant's list. No grant changes; do not add a `/vms` ACL. See [VM inventory safety](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/vm-inventory-safety.md).

### Security

- **Narrower mint grant.** The portal token can create API tokens for `capmox@pve` and `csi@pve` only, and holds no `Permissions.Modify` on `/pool`. Existing sites must act: see the Upgrade table. Afterwards, list the tokens of `root@pam` and of the other administrator accounts for ones nobody on your side created.
- **Node group image.** A node group's `imageId` is no longer taken from a request. The image always comes from the provider's version matrix.
- **ArgoCD `default` project.** It is locked on installer-built services clusters, so an Application in `default` there stops syncing. The management cluster stays open.
- **Still open, and accepted for this release.** `Permissions.Modify` on `/storage`, `/sdn/zones` and `/nodes`, and the portal token's power to delete the tokens of the two service users. See ["The mint grant in M1"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/proxmox-permissions.md#the-mint-grant-in-m1).

### Installer

- **Stage 10.** It narrows the services cluster's CAPMOX and CSI tokens to the services pool and storage. It only adds rows, so an older site keeps its broad rows until an operator removes them.
- **Stage 50 on an existing split-mode site.** A re-run replaces the services cluster's control plane machine. It needs one spare address and room for a second control plane VM, and the API address can be away for up to a minute. See the [install guide](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/install.md).
- **Stages 40 and 50.** The next run scales `argocd-applicationset-controller` to 0 on the management and the services cluster. A site that added its own ApplicationSet must set the replicas back.

### Docker Compose install

- **Managed-services switch.** `./proxcloud-up.sh install --managed-services` turns the platform on, and `--no-managed-services` turns it off. A later `install` without the flag and every `upgrade` keep the recorded value.
- **Limits.** A platform built from Compose lacks tenant block volumes and database backups. The host needs a route from the API container to the platform network. See ["Limits on the Compose install"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/managed-services.md#9-limits-on-the-compose-install).
- **Builds of `main`.** The script accepts `dev-<sha>` as a version, with a warning that it is not for production.
- **Delete now.** A project's "Delete now" is refused with a `409` while the job scheduler is off. It used to leave the project in `DELETE_IN_PROGRESS` for good.

### Release process

- **Chart mirror.** The nine third-party charts of the BOM are served from `ghcr.io/mutex-solutions/charts-mirror` by a CI flow of their own. See ["Chart mirror"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/ci-release.md#chart-mirror).
- **BOM release gate.** CI compares every pin of the BOM with its registry on pull requests, weekly and on every `v*` tag. A tag whose BOM has a moved or pending pin publishes no image and no chart.
- **`proxcloud-clusterctl` image.** The image that installs the Cluster API providers is built from upstream source with patched Go modules, and makes no GitHub call at runtime.

## Verified on a lab

The managed path ran on builds of `main` on one lab Proxmox VE cluster. The last round was on 2026-11-17 (`cb2f052`). The record, row by row, is in the guide under ["Not verified on a lab yet"](https://github.com/mutex-solutions/proxcloud/blob/v0.8.0/docs/managed-services.md#not-verified-on-a-lab-yet).

- **Install.** It finished twice, the second time in one run without a Retry, on cluster chart 0.1.13 and platform chart 0.1.2.
- **Remove.** Remove of a ready platform passed, and so did Remove from a failed stage 7.
- **Tenant cluster.** A cluster on a network of a VLAN zone had three workers Ready 12 minutes after the create. A scale-up and scale-down placed and removed one replica.
- **Publish on all nodes.** It published two nodes.
- **Seed.** On a seed built from the fixed image, two clean reboots passed. One restore of the seed over itself passed. A seed credential rotation was measured.
- **Restart and cancel.** An API restart in stages 7 and 8 of an apply with nothing new to write resumed. A cancel followed by Retry passed.

## Not verified

- **Anything on the published artifacts of this release.** The lab used builds of `main`. `--managed-services` on a Compose host against a published release was not run.
- **The lab checks L0 to L11 of the design.** They are not recorded as passed.
- **A healthy tenant database.** No tenant database became healthy on the lab's first end-to-end run. None is recorded healthy since, on the fixed node image either.
- **Restarts and failures.** Not run: an API restart in stages 2, 3 and 9 of a real install, and the failure drills.
- **Seed backup.** Not run: the scheduled seed backup job and its pruning, and a restore from an archive older than a credential rotation.
- **The mint grant.** Not run on a Proxmox cluster: the grant on the group, and its migration.
- **Other cases.** Not run: an upgrade of a tenant cluster, the console dialogs of publish on all nodes, an installer or Helm install of this release, and an install on a single-node Proxmox cluster.
- **Earlier releases.** Everything `v0.5.0` to `v0.7.0` say is not verified still holds.

## Known issues

- **Seed ISOs of servers created before this release are never swept.** When such a server is deleted, its seed ISO (`pcseed-v1-<...>.iso`) stays on the seed store for good. It holds the server's user data. Clean it up by hand as root on a node, once its server is deleted. The cleanup itself is not verified on a lab.

  ```sh
  pvesm list <seed store> --content iso | grep pcseed-v1-
  grep -l <file name> /etc/pve/nodes/*/qemu-server/*.conf   # prints nothing for a leftover
  pvesm free <volume>                                       # only for an ISO older than a day that no VM names
  ```

- **Published Ubuntu 26.04 images exported before the fix stay affected.** The ten older tags stay in the registry. Anyone who imported one, or runs VMs cloned from one, must follow the Upgrade table. A VM that has logged the error must not be rebooted: shut it down and repair it offline.
