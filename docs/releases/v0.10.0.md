ProxCloud v0.10.0 is a feature release on top of `v0.9.1`. The Proxmox console of a VM made by ProxCloud opens on the graphical display, a withdrawn template can be deleted from the admin console, and the platform's ArgoCD can be given an address. It also brings the machinery to upgrade the seed's k3s and to replace the platform cluster's machines, which no upgrade to this release uses yet.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this release is `0.10.0`. Against `0.9.1` it moves the cluster chart to `0.1.15` and the database chart to `0.5.2`. It keeps k3s `v1.35.10+k3s1` and Kubernetes `1.35.10`. It pins what the candidate `0.10.0-rc.1` pins.

## Highlights

- **Graphical console by default in the Proxmox web UI.** A VM made by ProxCloud opened on the serial terminal, an empty page until a key was pressed. New templates now use the standard display, and the serial terminal is still there.
  - At the next services sync: the templates of this portal and its stopped servers.
  - At the next Stop then Start from the portal: a running server.
  - Only when its node group is rolled: a Kubernetes worker.
  - A Reboot does not change it.
- **Delete a withdrawn template.** The Imported templates table of the admin console has a Delete button on withdrawn rows. No `qm destroy` on the node is needed.
- **An address for the platform's ArgoCD.** Opt-in: one address of the load balancer range, over HTTPS with ArgoCD's self-signed certificate, open to the operator networks you name and to no one else.
- **Upgrade machinery for the seed's k3s and for the platform cluster's machines. Both ship dark.** An upgrade run can now replace k3s on the seed, and replace every machine of the platform cluster for a newer Kubernetes. This release's BOM keeps k3s `v1.35.10+k3s1` (no newer patch of 1.35 exists) and Kubernetes `1.35.10`. So upgrading to `v0.10.0` moves charts only and replaces no machine. Neither part has run on a lab.
- **Thirteen dependency updates** of the Go module and the two consoles.

## Upgrade

These steps upgrade from `v0.9.1`. From an older release, read the [notes of v0.9.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.1) and the [notes of v0.9.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.0) first: their steps and cautions still apply.

1. Upgrade the portal. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. The Compose file did not change since `v0.9.1`, so PostgreSQL and Keycloak keep their containers. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.10.0
   ./proxcloud-up.sh upgrade v0.10.0
   ```

2. Move the platform. It is not changed by step 1: it stays on its BOM and keeps working, and the move can wait. Open System → Managed services, read the plan in step 4 and type the confirmation the page shows. From the BOM `0.9.1` the plan lists these four changes and refuses nothing:

   | Change | From → to | Class | Stage |
   |---|---|---|---|
   | `release` | `0.9.1` → `0.10.0` | record only | none |
   | `tenantCharts.kubernetes` | `proxmox-kamaji-cluster` `0.1.14` → `0.1.15` | record only | none |
   | `tenantCharts.database` | `database-cluster` `0.5.1` → `0.5.2` | record only | none |
   | `pc-platform` (seed) | `0.1.14` → `0.1.15` | chart | `cluster`, wave 3 |

   Nothing is rolled: no machine and no k3s is replaced. No seed backup is needed for this BOM, and the run does not ask for one. See ["Upgrade between BOMs"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/managed-services.md#upgrade-between-boms).

3. Let one services sync run. It runs every 15 minutes; on an install without the scheduler start it with `POST /api/v1/admin/job/external-service/sync`. It moves the console display:

   - **At once, at that sync:** the templates that a Template updates import of this portal holds (not a withdrawn one), and the stopped servers and imported images in the pools of its projects. They get `vga: std`. A second sync writes nothing.
   - **At the next Stop then Start from the portal:** a running server. So does an action that stops and starts it: resize, rebuild, restore, rollback. A Reboot does not change it.
   - **Only when a node group or the platform is rolled:** Kubernetes workers, the platform's machines and the seed. The portal never writes on them.
   - The portal never writes `vga` on a running VM and never leaves a pending change.

4. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.9.0`, `0.9.0-rc.1` or `0.9.0-rc.2` | As from `0.9.1`: four changes, no refusal. |
| A platform on a `0.8.x` BOM | The plan lists seven changes and refuses nothing: the four above (the cluster chart from `0.1.13`) and the three components of platform chart `0.1.2` → `0.1.3`. Read the cautions in the [notes of v0.9.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.0). |
| A platform on the BOM `0.10.0-rc.1` | This release applies it as it is. To move it, confirm the upgrade in step 4: one change, the release, record only, and nothing is synced for it. Not run on a lab. |
| Tenant Kubernetes clusters and databases made before this upgrade | They keep their chart until their own chart update. A new database of one instance gets no disruption budget, and restarts when its node is drained. |
| Servers whose Proxmox console should open on the graphical display now | Stop then Start each from the portal. A Reboot does not change it. |
| A template the portal did not import, or one built by `images/build.py` | The portal does not write on it. Run `qm set <vmid> --vga std` on it. On a VM, stop and start it right after: between the two, the VM has a pending change and the portal refuses operations on it. |
| Withdrawn templates you want gone | Use Delete on the row in Template updates. It is refused while a cluster's node group, a provider's version map or a linked clone still uses the template. |
| A site that wants the ArgoCD address | Read the Check row `argocd-access` after you save. Leave the address unset where tenant traffic leaves under a Proxmox node's address (SNAT): the row warns there, and that layout was not run on a lab. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |

## What changed

Since `v0.9.1`.

### Operator console

- **Delete a withdrawn template.** The Imported templates table has **Delete** on withdrawn rows (`DELETE /admin/template-updates/templates/{importId}`, audited). It destroys the template with the disks its configuration names, and frees the import receipt. The digest stays blocked. It needs no new Proxmox privilege. See [the guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/template-updates.md#delete-a-withdrawn-template).
- **Refusals of the delete.** It is refused, with the reason, while a Kubernetes cluster's node group or a provider's version map names the template, a linked clone uses its disk, or a smoke test or its import is running.
- **Withdraw warning.** A withdraw of a Kubernetes node image warns only when a provider's version, a cluster's node group or a platform still names a withdrawn copy, and says who.

### Servers and templates

- **Graphical console by default.** A new template has `vga: std` and keeps `serial0: socket`. The Proxmox web UI opens such a VM on the graphical console; the serial terminal stays under Console → xterm.js and `qm terminal`. The portal's own console page works as before, on both tabs.
- **Existing templates and servers.** The services sync moves this portal's templates and its stopped servers. A running server moves at its next start from the portal. Workers and platform machines move when they are replaced. The portal never writes `vga` on a running VM. See ["Console display"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/template-updates.md#console-display).
- **What a guest shows.** What appears on the graphical console and on the serial terminal depends on the guest's own kernel arguments.

### Managed services

- **ArgoCD address.** Under **Access** in step 1, name one address of the load balancer range and the operator networks, save and apply. The platform cluster's ArgoCD then answers at `https://<address>` for those networks only, with ArgoCD's own self-signed certificate, and the ready card shows the link. Sign in as `admin` with the password read through the one-hour platform kubeconfig. No account is created and no password is stored. The seed's ArgoCD never gets an address. See [the guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/managed-services.md#an-address-for-the-platform-clusters-argocd).
- **New Check row `argocd-access`.** It warns when an operator network contains a Proxmox node's address: where tenant traffic leaves under that address, tenants then reach the login page. When MetalLB does not give the address, the run fails with `argocd_address_unavailable` and the platform keeps serving.
- **The seed's k3s in an upgrade run (ships dark).** A run toward a BOM with a newer k3s has a stage "Upgrade the seed's k3s". It replaces the binary on the running seed VM and restarts k3s. The seed's API is away for about a minute; the platform cluster, tenant clusters and databases keep serving. This release's BOM names the k3s that `0.9.1` names, so the stage does not run. See ["The seed's k3s"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/managed-services.md#the-seeds-k3s).
- **Seed backup check.** The Check has a row `seed-backup`. An upgrade that replaces the seed's k3s is refused (`409 seed_backup_missing`) until the row sees a backup of the seed VM younger than 24 hours, or the operator ticks that one was taken. On most stores the portal cannot see the seed's backups, and the row says so: see Known issues.
- **Replacing the platform cluster's machines (ships dark).** A run toward a BOM with a newer Kubernetes, or a rebuilt node image, is two actions in step 4: **Seed and node image**, then **Replace the machines**, with its own typed phrase. The control plane goes first, then one node group and node at a time. There is no way back once the new control plane machine has joined, and the plan says so. This release's BOM keeps Kubernetes `1.35.10` and its node image, so none of this runs. See ["The platform cluster's machines"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/managed-services.md#the-platform-clusters-machines).

### Kubernetes and databases

- **Cluster chart `0.1.15`.** It reads two optional keys of a node group, used by the machine replacement. Without them it renders what `0.1.14` rendered, so no machine is replaced.
- **Database chart `0.5.2`.** A PostgreSQL or FerretDB database of one instance no longer has a disruption budget, which blocked every drain of its node. Such a database restarts when its node is drained. Existing databases keep their chart until their own chart update.

### Fixes

- **The `seed-backup` row says what it cannot see.** It said that the stores hold no backup when Proxmox had left the seed's archives out of the list. It now names the stores it can read and says for the others that the portal cannot see backups of the seed VM there. No privilege is added.
- **An old backup of another VM no longer counts as the seed's backup.** A backup counts only when it was made after the seed became ready and, when it has notes, the notes name the seed VM.
- **An apply no longer rewrites the seed VM's firewall options when they are as wanted.** It reads them first and writes only a difference.
- **The node wait counts every control plane machine.** With a control plane of three the wait for the nodes could not end.
- **A Delete that deleted nothing keeps `deleted` false in its audit row.**

### Release

- **BOM `0.10.0`.** Cluster chart `0.1.15` for the platform cluster and for new tenant clusters, database chart `0.5.2`, platform chart `0.1.3`. No third-party chart, image, k3s, Kubernetes version or node image moved. This build carries the BOMs of `0.8.0`, `0.8.1`, `0.8.2`, `0.9.0-rc.1`, `0.9.0-rc.2`, `0.9.0`, `0.9.1` and `0.10.0-rc.1` as previous BOMs.
- **App chart `0.10.0`.** The installer pin and the default of `proxcloud-up.sh` name `v0.10.0`.
- **Dependency updates.** Thirteen library updates, among them the MCP Go SDK, the AWS S3 client, `koanf`, `mustache`, `@stripe/stripe-js` 10, `@base-ui/react`, `radix-ui`, `lucide-react`, `react-router-dom`, `vite` and `oxlint`.

## Verified on a lab

One round on 2026-11-20, on one lab Proxmox VE cluster of three nodes, checked afterwards by a read-only audit. It ran on the published images of the candidate `v0.10.0-rc.1`, not on those of `v0.10.0`.

The code of this release is the code of that candidate plus one change, the fixes for what the round found. That change makes the `seed-backup` row say what it cannot see, limits the withdraw warning to copies something still names, keeps `deleted` false in the audit row of a Delete that deleted nothing, and updates the guides. It has not run on a lab.

- **The candidate's images and the portal upgrade.** A Compose upgrade from `v0.9.1`, with the PostgreSQL and Keycloak containers kept.
- **The move from the BOM `0.9.1` to `0.10.0-rc.1`.** On a three-node platform in bridge mode: 23 seconds, no retry, no machine replaced, no write on Proxmox, the seed's firewall file untouched, the platform API answering throughout. One tenant server was present; no tenant cluster and no database.
- **Graphical console: templates.** Six templates of the portal changed at the first sync. Later syncs wrote nothing. Withdrawn templates and templates the portal did not import were untouched.
- **Graphical console: servers.** No running VM had a pending change. A stopped server was changed at a sync and started with `vga: std`. A new server and a new worker had `vga: std`. Volume attach and detach worked on an old running server.
- **Graphical console: the portal's console page.** Both tabs showed a login prompt on Ubuntu 26.04 servers.
- **Delete of a withdrawn template.** The refusals `not_withdrawn` and `template_in_use`. One destroy, with only the template's base disk gone. The receipt read `template_missing`. A second Delete answered `unchanged`.
- **ArgoCD address: the settings.** An address from the pool was accepted. An address outside it and `/0` got `400`. The row `argocd-access` was seen as a warning and as ok.
- **ArgoCD address: who reaches it.** HTTPS with the self-signed certificate answered the operator address. The Proxmox nodes, the gateway host and a tenant VM got no answer, on a layout without SNAT. Clearing the block put the Service back to ClusterIP.
- **The machine replacement stays dark.** No roll was offered, and its phrase and `part` were refused.
- **A tenant cluster on chart `0.1.15`.** Created and deleted.

- **The seed's k3s upgrade, entirely.** Not run: the stage that replaces k3s, `seed_backup_missing` and its override, and an old archive of another VM. The `seed-backup` row turning ok was not seen: the row of the candidate could not.

## Known issues

- **A backup of the seed can restart its k3s on a stalled disk.** On a busy node or a slow disk a snapshot backup stalls the seed's disk for seconds. The seed's k3s then exits and is started again, and the seed's API is away for about a minute. Seen on the lab twice: during the seed's own `vzdump`, and during an apply with no backup running, which retried its stage and passed. The same backup also left the etcd of another control plane VM on that node unhealthy until it ended. It affects a site whose seed shares a busy node or a slow disk, a one-node site most of all. Take the backup in a quiet hour, some minutes before a run, and wait until the seed's API answers again. Not fixed in this release. See ["The seed's k3s"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/managed-services.md#the-seeds-k3s).
- **Seed ISOs of deleted servers stay on the store until they are cleaned.** Without the optional inventory reader the portal keeps the first-boot CD of a deleted server, which holds the server's user data, and logs "seed cleanup pending" at every sync. It affects every site without that reader. Configure it, or remove the files by hand: see ["Optional complete inventory reader"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/server-seed-safety.md#optional-complete-inventory-reader).
- **The `seed-backup` row cannot see a backup on most stores.** The portal token is kept off the seed VM on purpose, and Proxmox leaves the seed's archives out of its list. The row says so. An upgrade that replaces the seed's k3s is then started with the box that says a backup was taken. No upgrade to this release's BOM asks for it. See [the permissions guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/proxmox-permissions.md#what-the-fence-hides-from-the-portal-the-seeds-backups).
- **The seed's k3s upgrade and the machine replacement have never run on a real seed or cluster.** They ran in tests against a fake seed only, and no released BOM starts them. It affects the first release whose BOM names a newer k3s or Kubernetes. Run that upgrade on a lab first.
- **The ArgoCD address may be reachable by tenants.** On a site where tenant traffic leaves under a Proxmox node's address that an operator network contains, tenants reach the login page. The Check row `argocd-access` warns. Leave the address unset there.
- **A Reboot from the portal does not change the display.** A running server keeps the serial display through a Reboot, because Proxmox cannot change the display of a running VM. Use Stop then Start.
- **The platform's token ids are fixed.** The platform's two Proxmox tokens are always `capmox@pve!capi` and `csi@pve!csi`. On a Proxmox cluster where one of them already exists for something else, the root command stops before it changes anything. It affects a new install on such a site. The only way forward it offers is to remove that token, which breaks whatever else uses it. See ["The root command of an installation"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/managed-services.md#the-root-command-of-an-installation).
- **A chart version that changes only its hook does not run the hook.** ArgoCD syncs an Application only when a rendered object differs. No chart of this release is such a version. It affects a later release, which must also change a rendered object.
- **Workers do not join when the node that holds the platform's addresses also translates tenant traffic.** On a `simple` tenant zone, tenant connections to the platform network are dropped on that node. The network of an installed platform is fixed, so `routed` mode helps a new one-node install only. Read the Check row `tenant-path`, run the test, and use one of [the two layouts that work](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/managed-services.md#the-path-from-tenants-to-the-platform).
- **The platform upgrade is not shown on a lab with tenants.** It ran once on a production site that has them, to the BOM `0.9.0`. Take the seed backup first, or leave the platform on its BOM, where it keeps working.
- **A health check replaces nothing when every worker of a group fails.** That is its guard. The machines stay and are counted in the tenant's quota. Repair the cause, then use Replace or delete the cluster.
- **Replace on a node group of one leaves the group without a node.** The old machine goes first. It affects a tenant with one worker. Raise the group's count by one first when the workload cannot wait.
- **A standalone volume can lose its name at create.** A volume created without a server can answer `200` with no `id` when Proxmox is slow, and is then named after its disk at the next provider sync. Nothing is lost but the name; not fixed.
- **The `pve-api-rule` row can read `ok` while the rule matches nothing.** This happens on a site whose router translates the platform network on the way to the Proxmox node. Add a rule for the translated address: see [the guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.0/docs/managed-services.md#when-a-router-translates-the-platform-network).
- **Seed ISOs of servers created before `v0.8.0` are never swept.** When such a server is deleted, its seed ISO stays on the seed store and holds the server's user data. Clean it up by hand with the commands in the [release notes of v0.8.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.8.2).
