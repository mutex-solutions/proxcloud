ProxCloud v0.10.1 is a patch release on top of `v0.10.0`, and the first whose BOM moves Kubernetes. A managed-services platform can now move its seed and its platform cluster from Kubernetes 1.35.10 to 1.36.6, in two operator actions. Tenant clusters and databases keep their version.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this release is `0.10.1`. Against `0.10.0` it moves the seed's k3s from `v1.35.10+k3s1` to `v1.36.6+k3s1`, the platform cluster from Kubernetes `1.35.10` to `1.36.6` with the node image built for it, and the cluster chart from `0.1.15` to `0.1.16`. Nothing else moves. It pins what the candidate `0.10.1-rc.2` pins.

## Highlights

- **The platform moves to Kubernetes 1.36.6.** The seed's k3s goes from `v1.35.10+k3s1` to `v1.36.6+k3s1`, and the platform cluster from `1.35.10` to `1.36.6`.
- **Two operator actions.** First "Seed and node image", then "Platform cluster", which replaces every machine of the platform cluster, one unit at a time. There is no way back once the new control plane machine has joined.
- **Tenants keep their version.** Tenant clusters and databases are not upgraded. They keep their Kubernetes version and their chart.
- **1.36.6 for tenants after a smoke test.** The provider offers 1.36.6 for new tenant clusters once you have smoke-tested and published the new node image in Template updates.
- **A stuck replacement gets out with one Retry.** A platform that stood after the control plane's unit on `v0.10.1-rc.1` goes on with one Retry, with nothing to type and nothing to do by hand.
- **The wait between two units holds for tenants that are really away.** It now reads what the kubelets report, not only a status written by controllers the same drain stops. This fix has not run on a lab.

## Upgrade

These steps upgrade from `v0.10.0`. From an older release, read the [notes of v0.10.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.0) first: their steps and cautions still apply. The figures below are one lab's sample, not a promise for a site: two drills on three Proxmox nodes on one shared disk, with one control plane machine, one machine per group, one tenant cluster and one database under a write loop.

1. Upgrade the portal. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. The Compose file did not change since `v0.10.0`, so PostgreSQL and Keycloak keep their containers. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.10.1
   ./proxcloud-up.sh upgrade v0.10.1
   ```

2. The platform is not changed by step 1. It stays on its BOM and keeps working, and the move can wait. Pick a quiet hour for steps 4 and 5, and announce a window of about two hours.

3. Before you move a platform, do these things.

   - **Back up the seed VM** in a quiet hour, some minutes before the run: `vzdump <seed VMID>` on the seed's node. Wait until the seed's API answers again.
   - **Back up each database you keep.** The `dbaas` unit stops every database of one instance for minutes.
   - **Read the allow-lists for a network with host bits.** Correct a value such as `192.168.0.5/24` through the portal, in databases, tenant clusters, the provider default and the ArgoCD sources. A stored value keeps working; a new one with host bits is refused.
   - **Look for rules keyed by a VM id.** The roll gives the ids of old platform machines to new ones, possibly on another node. Check your backup jobs, firewall rules and notes that name a platform machine by its VM id.

4. Run **Seed and node image**. Open System → Managed services, read the plan in step 4, and type `upgrade <installation name> to 0.10.1`.

   - **What it does.** It imports the 1.36.6 node image as a template on every Proxmox node the cluster uses, one node after another. On the seed it saves an etcd snapshot, writes the k3s config file that turns leader election off in three components, replaces the k3s binary and restarts k3s.
   - **The seed backup question.** The run is refused with `409 seed_backup_missing` until the Check row `seed-backup` sees a backup of the seed VM younger than 24 hours. On most stores the portal cannot see the seed's backups, and the row says so. Then check in Proxmox that an archive of this seed VM exists, made after the seed VM was created and younger than 24 hours, and tick the box "I checked in Proxmox: seed VM … has a backup …" (`"seedBackupTaken": true` by API).
   - **How long.** About 11 to 19 minutes per node for the image import on the lab, 41 minutes for three nodes. The whole part took 43 min 20 s.
   - **What stops serving.** The seed's API, for about 45 s (43 s on the lab). Meanwhile no machine is repaired, the seed's ArgoCD syncs nothing and no platform run goes on.
   - **What keeps serving.** The platform cluster, every tenant API server, tenant workloads and the databases: the tenants are not affected. On a shared or slow disk the import can stall an API for seconds; on the lab single looks failed during the import, and the seed's k3s restarted once (39 s).
   - **It replaces no machine.** Stop here if something looks wrong on the seed: the platform cluster is still on 1.35.10.

5. Run **Platform cluster** (the button **Replace the machines**). It is blocked with `seed_not_upgraded` until step 4 is done. Type `upgrade <installation name> to 0.10.1 and replace its machines`.

   - **THERE IS NO WAY BACK once the new control plane machine has joined** the platform cluster's etcd. A step that fails leaves the machines that still run serving, and Retry goes on at that step. The last nets are the seed VM's backup and the tenants' own backups.
   - **Control plane first.** A second machine is cloned from the 1.36.6 template and joins, then the old one is removed. The platform cluster's API was away for up to 88 s during the clone on its own node, and for 65 s at the hand-over. Tenant API servers and databases kept answering. About 11 minutes on the lab.
   - **Then `system`.** The platform's operators (ArgoCD, Cluster API for tenants, CloudNativePG, MetalLB's controller, cert-manager, CoreDNS) are away for 3 to 5 minutes while they start on the new machine. No tenant API or database gap was seen. 8 min 50 s on the lab.
   - **Then `kamaji`.** **Every tenant API server is away**: 6 min 54 s on the lab. Tenant workloads keep running. During this unit's clone on the control plane's node, single looks at the platform and tenant APIs failed for up to 10 s. 10 min 21 s on the lab.
   - **Then `dbaas`.** **Every database with one instance on that machine is down**: 4 min 8 s on the lab. A writer that inserted every 2 s failed 53 times and lost no row. 11 min 20 s on the lab.
   - **A node without room.** A group on a node without room for one more machine is replaced delete-first: everything on it is away for the whole clone and join. Not run on a lab. A control plane node without room refuses the upgrade (`capacity_short`).
   - **Pause and Resume.** Pause stops the run between two units (15 s on the lab). The installation then reads `failed` with its step kept, and the Application `pc-platform` can stay without automated sync until the next run. Resume is an apply without a target: it goes on at the stored step.
   - **What Retry does.** It is an apply without a target. It goes on at the stored step, keeps the units already replaced, and deletes a Node that is not Ready and that no machine owns. Do not delete such a Node by hand.

6. Offer 1.36.6 to tenants, when you want to. The run imports the node image but does not publish it. Until then the run's item `kubernetes-version` warns, and a tenant's create at 1.36.6 is refused. Open Template updates, smoke-test the new image on each node and publish it (the Ready card's button does all nodes). See ["Upgrade to Kubernetes 1.36.6"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/docs/managed-services.md#upgrade-to-kubernetes-1366).

7. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A site with one Proxmox node | Not run on a lab. Every clone shares the disk with everything else: the control plane, kamaji-etcd, the databases and your own VMs. Expect the gaps of step 5 to be longer, and the API to be away during the control plane's clone as well. |
| A platform that stands in the replacement toward `0.10.1-rc.1` or `0.10.1-rc.2` | Press **Retry**. There is nothing to type: the plan shows the upgrade in progress to `0.10.1`, with the candidate as `carried`. The step is kept. |
| A platform that ran "Seed and node image" under a candidate and has not started "Platform cluster" | An apply without a target would go on to that candidate. Start the move to this release instead: the plan offers it next to the unfinished one. Type `upgrade <installation name> to 0.10.1 and replace its machines`. Read, not run. |
| A platform on the BOM `0.10.1-rc.2` with its upgrade finished | The plan lists one change, the release, record only. Type `upgrade <installation name> to 0.10.1`. Not run on a lab. |
| A platform on the BOM `0.10.1-rc.1` with its upgrade finished | The plan lists three changes and replaces no machine: the release, the tenant chart and the cluster chart `0.1.15` → `0.1.16`. Read, not run. |
| A platform on the BOM `0.10.0-rc.1` | As from `0.10.0`: 19 changes, the same two actions. Read, not run. |
| A platform on the BOM `0.9.0`, `0.9.1` or a candidate of `0.9.0` | 20 changes, the two actions, with the two tenant charts and the cluster chart `0.1.14` → `0.1.16`. Read, not run. |
| A platform on a `0.8.x` BOM | 23 changes, also the three components of platform chart `0.1.2` → `0.1.3`. Read, not run. Move to `0.10.0` first if you can. |
| Tenant Kubernetes clusters and databases | They are not upgraded and stay on their version. A new tenant cluster gets cluster chart `0.1.16`; an existing one keeps its chart until its own chart update. |
| A site installed with the Ansible installer | Nothing moves. The installer keeps k3s `v1.35.10+k3s1` and Kubernetes `1.35.10`. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |

## What changed

Since `v0.10.0`: the changes of the two release candidates `v0.10.1-rc.1` and `v0.10.1-rc.2`, and one fix merged after the second.

### Managed services

- **Upgrade to Kubernetes 1.36.6.** The BOM names k3s `v1.36.6+k3s1`, Kubernetes `1.36.6` and its node image. The upgrade is two parts with their own phrases. See ["Upgrade to Kubernetes 1.36.6"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/docs/managed-services.md#upgrade-to-kubernetes-1366).
- **No leader election on the seed.** The seed's k3s runs kube-controller-manager, kube-scheduler and its cloud-controller-manager without leader election. The k3s upgrade stage writes the config file. See ["The seed's k3s"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/docs/managed-services.md#the-seeds-k3s).
- **The seed's way back names the snapshot restore.** Across a minor, the message of `seed_k3s_timeout` and the plan give k3s's whole rollback for embedded etcd, with the snapshot the stage saved. The snapshot's real name is recorded on the run.
- **The seed's k3s stage can wait and record its failure.** The job store refused a code with a digit, so the stage looked once a minute and spent a job attempt per look.
- **The old machine's Node is deleted.** Cluster chart `0.1.16` gives Cluster API 30 minutes to delete it. The run also deletes a Node that is not Ready and that no machine owns, keeps an item for it and writes an audit entry. See ["The platform cluster's machines"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/docs/managed-services.md#the-platform-clusters-machines).
- **A replacement continues under a later BOM.** While a unit is still to be replaced, a later BOM that differs only in the product's own charts and the release takes the target's place at Retry.
- **The wait between two units reads Deployments and pods.** Per tenant control plane the Deployment Kamaji runs it as, per database its Ready instance pods, and the operators' Deployments. On the drill of rc.2 the old read let the `dbaas` unit start while the only tenant API server was away. Not run on a lab.
- **The Check has a row `nodes`.** It warns, by name, about a node of the platform cluster that is not Ready. It never fails the Check.
- **An import that is tried again says so.** The `images` item shows the try and the code the one before ended with.

### Kubernetes and databases

- **Cluster chart `0.1.16`.** It sets `nodeDeletionTimeoutSeconds` (1800) on the control plane's machines and on every node group's. Cluster API puts it on existing machines in place: no machine is replaced for it.
- **A network with host bits is refused.** Kubernetes 1.36 refuses a new CIDR such as `192.168.0.5/24`. The portal now answers `400` with the form to write, for a database's and a tenant cluster's `allowedCidrs`, a provider's default and the ArgoCD sources. Stored values keep working.
- **A database that waits for room says so.** While a pod of the database cannot be scheduled, the tenant's database page shows the scheduler's reason under the status.

### Servers and templates

- **A server keeps `pveUUID` after an action.** Stop, Start, a snapshot or a NIC change no longer drops the VM's uuid from the server's row until the next sync.
- **Template updates lists no VMID twice.** A `template_missing` row names no VMID another guest holds.
- **No audit row for an unchanged Withdraw or Delete.** The answer is `unchanged: true` as before.
- **A released cluster token takes its ACL rows with it.** Proxmox kept the rows of a deleted token as dead lines and warned at every `pveum` call. Rows an earlier release left go at the next ACL change.

### Security

- **`libxml2` refreshed in both console images** (CVE-2026-86144, fixed in Alpine's `2.13.9-r3`).

### Release

- **BOM `0.10.1`.** The pins of `0.10.1-rc.2`: k3s `v1.36.6+k3s1`, Kubernetes `1.36.6`, node image `ubuntu-2604-k8s-1.36.6-20261116194043-72f0eaa3d0d4`, cluster chart `0.1.16`, database chart `0.5.2`, platform chart `0.1.3`. No third-party chart, provider or clusterctl image moved. This build carries the BOMs of `0.8.0` to `0.10.1-rc.2` (eleven) as previous BOMs.
- **App chart `0.10.1`.** The installer pin and the default of `proxcloud-up.sh` name `v0.10.1`. The installer's k3s and Kubernetes pins stay at `1.35.10`.

## Verified on a lab

Two drills on one lab Proxmox VE cluster of three nodes on one shared disk, with one control plane machine, one tenant cluster and one database under a write loop, each checked afterwards by a read-only audit. Each part ran on the published images of a candidate, not on those of `v0.10.1`.

The code of this release is the code of `v0.10.1-rc.2` plus one change: the wait for the tenants between two units, the kept item and audit entry of a deleted Node, the ACL rows of a released token, and the reason of a database that waits for room. **That change has not run on a lab.** The corrected wait for the tenants was tested against test doubles only.

- **On rc.1: the seed part, with the tenants live.** The seed's k3s went from `v1.35.10+k3s1` to `v1.36.6+k3s1`, with the same node and boot, containerd 2.3.7. The seed's API was away 43 s in the k3s stage. The database port had no failed look.
- **On rc.1: the seed's snapshot and config file.** The etcd snapshot exists as an object. The config file without leader election was seen by its effect: the three components' leases were not renewed.
- **On rc.1: the control plane's unit,** on cluster chart `0.1.15`. One clone, the new etcd member added and the old one removed, the old VM destroyed. The platform API was away 88 s and 54 s during the clone and 65 s at the hand-over. The old machine's Node stayed, which rc.2 corrected.
- **On rc.2: the way out by one Retry.** The stuck roll was carried to the new BOM, the Node left behind was deleted by the run, and `nodeDeletionTimeoutSeconds` 1800 was put on the machines in place, with no machine replaced.
- **On rc.2: units `system`, `kamaji` and `dbaas`.** Each was replaced with one more machine first, with no Node left behind.
- **On rc.2: Pause and Resume.** Pause was honoured in 15 s, and Resume went on at the stored step.
- **On rc.2: data kept.** The marker row was unchanged. The writer had 53 failed inserts in 4 min 8 s and lost no row.
- **On rc.2: the platform cluster on 1.36.6.** Cilium `1.18.16`, MetalLB, CloudNativePG, Kamaji and proxmox-csi run on it.
- **On rc.2: a 1.36.6 tenant cluster.** A new tenant cluster at 1.36.6, after the node image was smoke-tested and published, and one at 1.35.10.
- **On rc.2: databases and allow-lists.** A new database, a change of a database's allow-list accepted by the 1.36.6 API server, and an entry with host bits refused by the portal.

## Not verified

- **The fixes merged after rc.2.** Not run on a lab: the wait for the tenants between two units, the kept item and audit entry of a deleted Node, the removal of a released token's ACL rows on a real Proxmox, and the scheduler's reason on a real database.
- **This release itself.** Not run: its published images, its tag's workflows, any move to the BOM `0.10.1` (the record-only step from `0.10.1-rc.2` included), and one uninterrupted run from `0.10.0` to it.
- **The control plane's unit under cluster chart `0.1.16`.** On the lab it ran under `0.1.15`. Whether the 30 minutes keep the Node from being left at all is not shown; the run's own deletion is the proven net.
- **A one-node site.** Not run. The lab has three nodes.
- **A site with SNAT or a routed tenant path.** Not run under a roll.
- **A unit replaced delete-first.** All three units on the lab had room for one more machine.
- **The seed's way back.** The restore by the etcd snapshot was not tried, and neither was a restore of the seed from an archive.
- **cert-manager on 1.36.** No certificate was issued or renewed after the move, on the seed or on the platform cluster.
- **More than one control plane machine,** the etcd member list, and a tenant cluster with two workers during the roll.
- **The moves from BOMs older than `0.10.0`.** Their plans were read, not run.
- **Earlier releases.** Everything the [notes of v0.10.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.0) list as not verified still holds, except what is listed as verified here.

## Known issues

- **The stateful gaps of a replacement are minutes.** A new machine counts as Ready, and the old one is drained, before the CSI node plugin of the new node has registered. The disks of kamaji-etcd and of each database then wait to be attached. On the lab every tenant API server was away 6 min 54 s and a database 4 min 8 s. It affects every site with tenants. Announce a window longer than these figures; this release does not shorten them.
- **cert-manager and Cilium are outside their own support matrix on 1.36.** cert-manager `v1.20.2` lists Kubernetes 1.32 to 1.35, Cilium `1.18.16` lists 1.30 to 1.33. No fault was seen in the two drills, and no new certificate was issued on 1.36. If one fails after the upgrade, this release cannot move its chart.
- **Sites installed with the Ansible installer stay on 1.35.10.** The installer keeps k3s `v1.35.10+k3s1` and Kubernetes `1.35.10`. The installer path takes the minor step in a release of its own.
- **The machine replacement cannot be undone.** After the new control plane machine has joined, the only nets are the seed VM's backup and the tenants' own backups.
- **With one control plane machine, a clone on its node is felt.** The platform API was away up to 88 s during the control plane's own clone on the lab. A clone of the `kamaji` unit or a smoke test on that node made single looks fail, up to 52 s on a tenant API. On a one-node site every clone is there. Pick a quiet hour.
- **A backup of the seed can restart its k3s on a stalled disk.** Until the seed part has run, the seed's components still use leader election, and a stalled disk can end k3s; the seed's API is then away for about a minute. Take the backup in a quiet hour, some minutes before the run. See ["The seed's k3s"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/docs/managed-services.md#the-seeds-k3s).
- **The `seed-backup` row cannot see a backup on most stores.** The upgrade is then started with the box that says a backup was taken. See [the permissions guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/docs/proxmox-permissions.md#what-the-fence-hides-from-the-portal-the-seeds-backups).
- **Seed ISOs of deleted servers stay on the store until they are cleaned.** Without the optional inventory reader the portal keeps the first-boot CD of a deleted server, which holds its user data. See ["Optional complete inventory reader"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/docs/server-seed-safety.md#optional-complete-inventory-reader).
- **The ArgoCD address may be reachable by tenants.** On a site where tenant traffic leaves under a Proxmox node's address that an operator network contains, tenants reach the login page. The Check row `argocd-access` warns. Leave the address unset there.
- **A Reboot from the portal does not change the display.** Use Stop then Start.
- **The platform's token ids are fixed.** The root command stops on a Proxmox cluster where `capmox@pve!capi` or `csi@pve!csi` already exists for something else. See ["The root command of an installation"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/docs/managed-services.md#the-root-command-of-an-installation).
- **A chart version that changes only its hook does not run the hook.** A later release must also change a rendered object.
- **Workers do not join when the node that holds the platform's addresses also translates tenant traffic.** Read the Check row `tenant-path` and use one of [the two layouts that work](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/docs/managed-services.md#the-path-from-tenants-to-the-platform).
- **A health check replaces nothing when every worker of a group fails.** Repair the cause, then use Replace or delete the cluster.
- **Replace on a node group of one leaves the group without a node.** Raise the group's count by one first when the workload cannot wait.
- **A standalone volume can lose its name at create** when Proxmox is slow. Nothing is lost but the name.
- **The `pve-api-rule` row can read `ok` while the rule matches nothing,** on a site whose router translates the platform network. See [the guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1/docs/managed-services.md#when-a-router-translates-the-platform-network).
- **Seed ISOs of servers created before `v0.8.0` are never swept.** Clean them up by hand with the commands in the [release notes of v0.8.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.8.2).
