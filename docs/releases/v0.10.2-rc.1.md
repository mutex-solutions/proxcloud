ProxCloud v0.10.2-rc.1 is the first release candidate of `v0.10.2`, published as a prerelease. It moves cert-manager from `v1.20.2` to `v1.21.3` on the seed and on the platform cluster of a managed-services platform, by one upgrade run that replaces no machine. It exists so that a lab can run that upgrade: nothing of it has run on a lab yet. It is not for production. `v0.10.1` stays the current stable release.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this candidate is `0.10.2-rc.1`. Against `0.10.1` it moves cert-manager from `v1.20.2` to `v1.21.3` on the seed and on the platform cluster, and nothing else: the same k3s, Kubernetes version, node image, providers, other third-party charts and product charts.

## Highlights

- **cert-manager `v1.20.2` → `v1.21.3`.** On the seed and on the platform cluster, by an upgrade run from the BOM `0.10.1`. cert-manager is the first third-party chart an upgrade moves.
- **A light run.** No machine is replaced, nothing is written on Proxmox, the seed's k3s is not touched and no seed backup is asked for. No pod of a tenant restarts.
- **No way back.** A platform does not go back to a BOM, and cert-manager documents no downgrade. Back up the cert-manager resources first: see "Upgrade".
- **Inside its support table again.** cert-manager 1.21 lists Kubernetes 1.33 to 1.36, so it covers the platform's 1.36.6 and the installer's 1.35.10. `v1.20.2` lists 1.32 to 1.35 and ran outside its table on 1.36 since `v0.10.1`.
- **A security fix.** `v1.20.2` is affected by [GHSA-8rvj-mm4h-c258](https://github.com/advisories/GHSA-8rvj-mm4h-c258) (high), fixed upstream since `v1.20.3`. `v1.21.3` has the fix.
- **A new Check row `certificates`.** It warns about cert-manager Deployments that are not available and Certificates that are not Ready, by name. It is a warning only: no run waits on it.
- **The installer path moves too.** `cert_manager_chart` is `v1.21.3`: stage 40 moves at `make upgrade`, stage 50 at the next `make install`. No drill covers this path.
- **Not run on a lab yet.** Nothing in this candidate: see below.

## Upgrade

Use a lab or another non-production site. Production sites should stay on `v0.10.1` and wait for `v0.10.2`.

1. **Check the platform's BOM first.** The move is planned from the BOM `0.10.1` (and from its candidates). A platform on an older BOM (`0.8.0` to `0.10.0` and their candidates, all on Kubernetes 1.35.10) is refused by this build: the move would change k3s and Kubernetes too, and a third-party chart moves only in an upgrade that changes neither. Upgrade such a platform to `0.10.1` with the `v0.10.1` build first, both parts, as the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) describe. Then come back to step 2.

2. Upgrade the portal. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. The Compose file did not change since `v0.10.1`. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2-rc.1/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.10.2-rc.1
   ./proxcloud-up.sh upgrade v0.10.2-rc.1
   ```

3. The platform is not changed by step 2. It stays on its BOM and keeps working. Before you move it, do these things.

   - **Back up the cert-manager resources.** Upstream's upgrade guide advises it, and there is no way back. Download the seed kubeconfig and the platform kubeconfig (System → Managed services), then run this once with each:

     ```sh
     kubectl get certificates,issuers,clusterissuers -A -o yaml > cert-manager-backup.yaml
     ```

   - **Read the Check row `certificates`.** It should be `ok`. A warning names each Deployment or Certificate that is not right. Fix a Certificate that is not Ready on its own first: the run does not wait on it, and a Certificate that is not Ready keeps the certificate its Secret holds.

4. Open System → Managed services and read the plan in step 4. From the BOM `0.10.1` (or `0.10.1-rc.2`) it lists three changes and refuses nothing:

   | Change | From → to | Class | Stage | Wave |
   |---|---|---|---|---|
   | `release` | `0.10.1` → `0.10.2-rc.1` | record only | none | |
   | seed `cert-manager` | `v1.20.2` → `v1.21.3` | chart | `seed-platform` | 1 |
   | platform cluster `cert-manager` | `v1.20.2` → `v1.21.3` | chart | `workload-platform` | 1 |

5. Run the upgrade. Type `upgrade <installation name> to 0.10.2-rc.1`. There is one action, with no parts. No duration below was measured.

   - **What it does.** ArgoCD syncs cert-manager to the new chart on the seed, then on the platform cluster. It applies the CRDs in place (`v1` stays the only version) and removes what the new chart no longer renders (the Role and RoleBinding `cert-manager-tokenrequest`).
   - **The three Deployments roll together.** The controller, the cainjector and the webhook each start their new pod and remove the old one only when the new one is Ready.
   - **The wait.** The wave waits until the Application is Synced and Healthy and its sync Succeeded, which includes the chart's `startupapicheck` Job: a dry-run Certificate against the webhook. cert-manager is recorded at `v1.21.3` only after its wave passed.
   - **If the check fails.** The sync fails, and the run starts it once more. When that one fails too, the stage fails `component_unhealthy` with what the sync failed on. Fix the cause, then **Retry**.
   - **What it does not do.** It replaces no machine, writes nothing on Proxmox, does not touch the seed's k3s and restarts no pod of a tenant. Certificates and their Secrets stay; the move is not expected to issue any again (not measured). The webhooks of Cluster API and Kamaji keep their certificates.

6. Read the Check row `certificates` again. It should be `ok` on both clusters.

7. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.10.1-rc.2` | As from `0.10.1`: the same three changes. Read, not run. |
| A platform on the BOM `0.10.1-rc.1` with its upgrade finished | The plan lists five changes and replaces no machine: the three above, the tenant chart (record only) and the cluster chart `0.1.15` → `0.1.16` (chart, stage `cluster`, wave 3). Read, not run. |
| A platform that stands in the replacement of its machines toward `0.10.1` or one of its candidates | Press **Retry** first: it goes on to that BOM, which this build carries. This candidate does not take its place, and the plan shows its move as refused until the replacement is finished. Then upgrade as above. |
| A platform on an older BOM | Refused (step 1). Each cert-manager row says: finish an upgrade to a release with this one's Kubernetes version (1.36.6), k3s (`v1.36.6+k3s1`) and node image, with that release's build, then start this one. |
| A platform you move to the BOM `0.10.2-rc.1` | Keep it on a lab. Later builds apply it only while they carry this BOM; `v0.10.2` is planned to. A build without it refuses the platform (`bom_unsupported`). |
| Tenant Kubernetes clusters and databases | Nothing moves for them. The tenant cluster chart's cert-manager addon (off by default) stays at `v1.20.2`. |
| A site installed with the Ansible installer | The tag's `cert_manager_chart` is `v1.21.3`. Stage 40 moves the management cluster's cert-manager at `make upgrade`; its wait can pass on the old Deployment, so read the Application `cert-manager` for Synced and Healthy at `v1.21.3`. Stage 50 moves the services cluster's at the next `make install`, where plugin-barman-cloud also uses it (two Certificates and an Issuer). Back up the cert-manager resources first. No drill covers this path. See [Install, "Stages"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2-rc.1/docs/install.md#stages). |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |
| A new install | Pass `--version v0.10.2-rc.1` to `proxcloud-up.sh install`. The script's default, the chart and the installer still name `v0.10.1`. |

## What changed

Since `v0.10.1`: four merged pull requests.

### Managed services

- **An upgrade may move cert-manager** (#407). On the seed and on the platform cluster, cert-manager moves as a chart of the product does: only to a version whose BOM entry lists the installed one in `upgradeFrom`, as class `chart` in its wave. It moves only in an upgrade that changes no k3s, Kubernetes version or node image; next to such a change each cert-manager row is refused with a sentence that says what to do. Every other third-party chart stays refused. See ["A cert-manager move"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2-rc.1/docs/managed-services.md#a-cert-manager-move).
- **The Check row `certificates`** (#407). `ok` when cert-manager's three Deployments are available on the seed and on the platform cluster and every Certificate there is Ready; a warning that names each one that is not. It never fails and no run waits on it. See [the API reference](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2-rc.1/docs/api.md).
- **cert-manager `v1.21.3` pinned** (#409, #410). The chart mirror publishes it unchanged from charts.jetstack.io; the BOM pins its mirror digest on both clusters, with `upgradeFrom: ["v1.20.2"]`. See ["What this release moves"](https://github.com/mutex-solutions/proxcloud/blob/v0.10.2-rc.1/docs/managed-services.md#what-this-release-moves-and-what-it-refuses).
- **Upstream's breaking items of 1.20 → 1.21 do not touch the product.** The chart no longer renders the `cert-manager-tokenrequest` Role and RoleBinding, the `cert-manager-edit` role loses Challenge and Order writes, and three monitoring values are gone. The product sets `crds.enabled` only and uses none of them.

### Security

- **[GHSA-8rvj-mm4h-c258](https://github.com/advisories/GHSA-8rvj-mm4h-c258) (high): a direct ACME Challenge resource could bypass an Issuer's DNS01 solver policy and use a ClusterIssuer's DNS credentials.** Affects cert-manager `1.20.0` to `1.20.2`; fixed since `v1.20.3`. `v1.21.3` has the fix. A platform keeps `v1.20.2` until it has run this move.

### Installer

- **`cert_manager_chart` is `v1.21.3`** (#410). Stage 40 and stage 50 follow the platform BOM's pin. See the installer row of step 7.
- **The clusterctl image keeps its cert-manager file at `v1.20.2`** until its next rebuild. clusterctl skips a cert-manager that answers, whatever its version; cert-manager is always installed first.

### Release

- **BOM `0.10.2-rc.1`.** The pins of `0.10.1` but cert-manager. No chart of the product changed since its tag, so no chart version moved. This build carries the BOMs of `0.8.0` to `0.10.1` (twelve) as previous BOMs.
- **A candidate moves nothing a final moves.** The app chart, the installer's ProxCloud pin and the Compose default stay on `v0.10.1`.

## Verified on a lab

Nothing. No upgrade to this BOM has run on a lab or on a site, and nothing was run on this candidate's images: they do not exist before the tag. The move is covered by tests only: the plan against the embedded BOMs, the run against a fake seed and a fake platform cluster, and a render of both cert-manager charts pulled from the mirror. This candidate exists to run the lab drill.

## Not verified

- **This candidate.** Not run: its images, its tag's workflows, and the move of a platform to the BOM `0.10.2-rc.1` from any previous BOM.
- **The cert-manager move, entirely.** Not run on any seed or platform cluster: ArgoCD's sync of the new chart, the server-side apply of the CRDs, the removal of the tokenrequest Role and RoleBinding, the three rolling Deployments, the `startupapicheck` Job, and the time it all takes.
- **Existing Certificates across the move.** Not measured: whether any is issued again, and whether the webhooks of cert-manager, Cluster API and Kamaji answer without a gap.
- **A new Certificate on 1.36.** None was issued or renewed by cert-manager on Kubernetes 1.36, on `v1.20.2` or on `v1.21.3`.
- **The Check row `certificates` on a real cluster.** Tested against fakes only.
- **The installer path.** Stage 40 at `make upgrade` and stage 50 at `make install` were not run with `v1.21.3`.
- **The moves from `0.10.1-rc.1` and `0.10.1-rc.2`.** Their plans were read, not run.
- **Earlier releases.** Everything the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) list as not verified still holds.

## Known issues

- **The move has never run on a real cluster.** It ran in tests against fakes only. Run it on a lab first.
- **There is no way back.** cert-manager documents no downgrade, and a platform does not go back to a BOM. Back up the cert-manager resources before the run (step 3).
- **Platforms on a BOM before `0.10.1` cannot take this move.** They upgrade to `0.10.1` with the `v0.10.1` build first.
- **The installer path is not drilled.** Stage 40's wait can pass before ArgoCD has synced the new version. Read the Application yourself.
- **Cilium is still outside its own support matrix on 1.36.** Cilium `1.18.16` lists Kubernetes 1.30 to 1.33. This candidate does not move it.
- **The tenant cluster chart's cert-manager addon stays at `v1.20.2`.** It is off by default; it moves with a later tenant chart version.
- **cert-manager 1.20 reaches end of life when 1.22 is released.** A platform that has not made this move stays on `v1.20.2`. 1.22 comes in a later release, from `v1.21.3`.
- **Earlier releases.** The other known issues in the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) still hold, except the one about cert-manager outside its support matrix, which this move closes for a platform that makes it.
