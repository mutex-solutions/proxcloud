ProxCloud v0.9.0-rc.1 is a release candidate of `v0.9.0`, published as a prerelease. It is for a lab: to drill the platform upgrade from a `0.8.x` BOM and to run a fresh install. It is not for production. `v0.8.2` stays the current stable release.

A candidate is needed because the platform upgrade takes only a release BOM as its target. The BOM (bill of materials) is the list of exact versions a managed-services platform runs. A build of `main` carries a `-dev` BOM, which the upgrade refuses.

## Highlights

What `v0.9.0` holds so far. Most of it has not run on a lab: see below.

- **Upgrade an installed platform.** Step 4 of Managed services moves a platform from the BOM of `0.8.0`, `0.8.1` or `0.8.2` to this one, after a typed confirmation. Only ProxCloud's own charts move, and no machine is replaced.
- **Presets and control plane count.** A new install starts from Homelab, Standard or Custom, with one or three control plane machines.
- **Network modes and a path test.** The platform network takes a VLAN tag, or is made by ProxCloud on a one-node site (`routed`). "Test the tenant path" checks that a tenant network reaches the platform.
- **One root command.** One command per installation makes the Proxmox tokens and prints one line to paste. The install writes the firewall rule that lets the platform reach the Proxmox API.
- **Usable right after install.** A green install offers a Kubernetes version and attaches the providers to projects, as you choose in step 1.
- **Worker repair and worker firewall.** A worker that never joins is replaced after a timeout, and Replace does it on demand. A cluster's workers can be put behind the Proxmox VM firewall, off by default.
- **Console items and fixes.** Pending invitations with Revoke, editable security group rules, clearer pages for load balancers and servers, and the fixes for what the first lab round found.

## Upgrade

Use a lab or another non-production site. Production sites should wait for `v0.9.0`.

1. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0-rc.1/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.9.0-rc.1
   ./proxcloud-up.sh upgrade v0.9.0-rc.1
   ```

2. The platform is not changed by step 1: it stays on its BOM. To move it, open System → Managed services, read the plan in step 4 and confirm the upgrade. The plan lists six changes and refuses nothing. See ["Upgrade between BOMs"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0-rc.1/docs/managed-services.md#upgrade-between-boms).

3. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform you moved to the BOM `0.9.0-rc.1` | Keep it on a lab. Later builds apply it only while they carry this BOM; `v0.9.0` is planned to, and moving to its BOM is one more upgrade run. A build without it refuses the platform (`bom_unsupported`). |
| A platform you leave on a `0.8.x` BOM | Nothing. Three control plane machines and a VLAN tag are refused there, and Replace answers `502`, until the upgrade. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |
| A new install | Pass `--version v0.9.0-rc.1` to `proxcloud-up.sh install`. The script's default, the chart and the installer still name `v0.8.2`. |
| A Kubernetes provider with worker repair or firewall settings | Read the provider's page. `nodeStartupTimeoutSeconds` must now be `0` or 900 to 86400; a stored value outside that is read as the default, and the page says so. |

## Verified on a lab

One round, on 2026-11-19, on a build of `main` over a platform that `v0.8.0` installed. It ran before the fixes for its own findings, so none of those fixes was run on a lab.

- **Volumes.** A volume keeps its row through attach, detach and rebuild, and the quota is right: verified.
- **Worker firewall, one worker.** The Proxmox rules were written in the right order, the node stayed Ready, and Remove and the cluster delete cleaned up. Which ports were closed afterwards was read but not saved.
- **Replace.** Only its refusals on a `0.8.0` platform, and "needs attention" after its time limit.
- **One root command.** The Check rows, the firewall rule and the refusals. The command was not run on a node, and the rule matched nothing on that lab, whose router translates the platform network.
- **Presets, network modes, path test.** Only the refusals, the `capacity` row and the cleanup. The path test gave no verdict.
- **Usable after install, invitations, rule edit.** At the API only, and in part.

## Not verified

- **The upgrade between BOMs.** Only the refusal of a `-dev` target was seen. Not run: the upgrade from `0.8.0`, `0.8.1` or `0.8.2`, a second upgrade from this BOM, a failed upgrade's Retry, and a restore.
- **A fresh install from this candidate.** Not run: a preset, three control plane machines, `routed` mode, a VLAN tag, and the button that publishes the node image and offers the version.
- **Chart 0.1.14 on a cluster.** Not run: the health check, a working Replace, and the worker firewall with two workers.
- **The lab-round fixes.** Not run: the path test with its new image choice, the provider settings check, and the join error excerpt on real `kubeadm` output.
- **The consoles.** No page of either console was opened in the round.
- **The tag's workflows.** No candidate before this one carried a release notes file or a previous BOM.
- **Earlier releases.** Everything `v0.8.0`, `v0.8.1` and `v0.8.2` say is not verified still holds, except what is listed as verified here.

## Known issues

- **A standalone volume can lose its name at create.** A volume created without a server can answer `200` with no `id` when Proxmox is slow, and is then named after its disk at the next provider sync. It affects a tenant who creates such a volume. Nothing is lost but the name; not fixed.
- **Workers do not join on some site layouts.** Tenant connections to the platform network are dropped on a site where one Proxmox node translates tenant traffic and also runs the platform's machines. The network of an installed platform is fixed, so `routed` mode helps a new one-node install only. Read the Check row `tenant-path` and use one of [the two layouts that work](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0-rc.1/docs/managed-services.md#the-path-from-tenants-to-the-platform).
- **A node group cannot be scaled to 0.** A worker that never joined stays "not joined" after its cause is repaired, and "needs attention" stays on it until a new machine is healthy. It affects a tenant with such a worker. Use Replace on a platform upgraded to this BOM; on a `0.8.x` BOM raise the group's count by one and lower it again. Replace has not replaced a machine on a lab yet.
- **The `pve-api-rule` row can read `ok` while the rule matches nothing.** This happens on a site whose router translates the platform network on the way to the Proxmox node. It affects installs on such a site. Add a rule for the translated address: see [the guide](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0-rc.1/docs/managed-services.md#when-a-router-translates-the-platform-network).
- **Seed ISOs of servers created before `v0.8.0` are never swept.** When such a server is deleted, its seed ISO stays on the seed store and holds the server's user data. It affects a site with such servers. Clean it up by hand with the commands in the [release notes of v0.8.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.8.2).
