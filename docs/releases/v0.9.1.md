ProxCloud v0.9.1 is a patch release on top of `v0.9.0`. It adds no feature. It fixes what the first production upgrade to `v0.9.0` and the last lab round of `v0.9.0` found.

The platform bill of materials (BOM) is the list of exact versions a managed-services platform runs. The BOM of this release is `0.9.1`. It pins what `0.9.0` pins, cluster chart `0.1.14` and platform chart `0.1.3`: only the release line differs. The release also carries the BOMs of `0.8.0`, `0.8.1`, `0.8.2`, `0.9.0-rc.1`, `0.9.0-rc.2` and `0.9.0`, for the platforms those builds installed.

## Highlights

- **A services sync no longer writes on withdrawn node templates.** In `v0.9.0` the sync set `onboot` on every Kubernetes node template the portal had imported, withdrawn ones included. A withdrawn template is now neither read nor written.
- **The plan lists the Proxmox API firewall rule a run writes.** On a platform installed by `0.8.x` the rule does not exist yet. A run writes it, and the plan now names it before you confirm.
- **The stored result of the tenant path test ends with Remove.** A new install no longer shows the verdict of the platform that was removed.
- **Deleting a tenant cluster no longer sends a token delete that must fail.** The portal asked Proxmox to delete a `csi@pve` token that was never made, and Proxmox logged a `500`.
- **PostgreSQL is pinned to a minor release.** A portal upgrade no longer recreates the database container by surprise because a moving image tag moved.

## Upgrade

These steps upgrade from `v0.9.0`. From an older release, follow the [notes of v0.9.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.0) first: their steps and cautions still apply.

1. Upgrade the portal. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.9.1/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.9.1
   ./proxcloud-up.sh upgrade v0.9.1
   ```

   This release changes the PostgreSQL line of `compose.yaml` from `17-alpine` to `17.12-alpine`. Expect this one upgrade to recreate the PostgreSQL container, and Keycloak with it. The volumes stay. Later upgrades restart the database only when a release changes that line.

2. The platform is not changed by step 1. It stays on its BOM and keeps working.

   - **From the BOM `0.9.0`:** the move to `0.9.1` is record only. The plan in step 4 of System → Managed services lists one change, the release, and nothing is synced for it. Type the confirmation the page shows, or leave it for later.
   - **From a `0.8.x` BOM:** the plan is the one the [notes of v0.9.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.0) describe, six changes and no refusal. It now also lists the entry `pve-api-rule` while the cluster firewall rule is missing. Read the cautions there and take the seed backup first.

3. Then let one services sync run. It runs every 15 minutes; on an install without the scheduler start it with `POST /api/v1/admin/job/external-service/sync`. Do this before a planned Proxmox node reboot.

   - **It writes** `onboot: 1` on the Kubernetes node templates that an import of this portal still holds, staged or published, and on the running workers of its tenant clusters. It writes only where the option is missing, with the portal's token.
   - **It skips** a withdrawn import (tag `pc-tu-withdrawn`), a template the portal did not import, a worker that is not running, and everything that already has the option. A second sync writes nothing.
   - An `onboot` that a sync of `v0.9.0` already wrote on a withdrawn template stays. Nothing takes it back.

   See ["After a Proxmox node reboots"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.1/docs/managed-services.md#after-a-proxmox-node-reboots).

4. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| The Helm chart with its CloudNativePG database | The image name changes from `18` to `18.6`. The operator restarts the portal's database once at the `helm upgrade`. |
| A platform installed by `0.8.x` whose Check row `pve-api-rule` warns | The next apply or upgrade run writes the rule: one `ACCEPT` rule for the platform's addresses to the Proxmox API port. Nothing else in the firewall is touched, and the plan now lists it. |
| A site that held back the services sync because of withdrawn node templates | The sync no longer writes on them. Run it now. |
| A platform on the BOM `0.9.0-rc.1` or `0.9.0-rc.2` | As from `0.9.0`: one change, the release, record only. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |

## What changed

### Managed services

- **Plan entry `pve-api-rule`.** While the cluster firewall rule `proxcloud:pve-api:<installation>` is missing or differs from the settings, the plan of an apply or an upgrade lists it, with the rule spelled out. It never blocks. With the rule in place, or when the firewall cannot be read, the plan is as before.
- **Check row `boot-store`.** It says "disks of N other VM ids" and marks an id that no guest holds as a leftover volume. It called such a volume a VM.
- **Tenant path test.** Remove deletes the stored result, and the start of an install deletes one saved after that. A fresh platform answers `404 no_probe` until its own first test.
- **Guide.** The upgrade section names the one upgrade that ran on a production site with tenants.

### Kubernetes

- **`onboot` pass.** The services sync skips a node template tagged `pc-tu-withdrawn`. A cluster made on such a template before the withdraw still clones from it; such a worker gets `onboot` from the sync's worker pass once it runs.
- **Cluster delete.** The release lists the tokens of `csi@pve` and sends the delete only when the cluster's token is among them. A token that exists and cannot be deleted still fails the release.
- **Operator console.** The card "Managed clusters" says how many clusters are behind the provider's chart. The refusal `409 bom_installed` reads as a plain message.
- **Permissions guide.** It says who gets `403` on `GET /cluster/status` and why no privilege is added for it.

### Install and build

- **Docker Compose.** PostgreSQL is `postgres:17.12-alpine`. It was the moving tag `17-alpine`. The tag is a version without a digest, as Traefik and Keycloak are pinned.
- **App chart `0.9.1`.** The CloudNativePG image is `ghcr.io/cloudnative-pg/postgresql:18.6`. It was `18`.
- **BOM `0.9.1`.** The pins of `0.9.0`. No chart of the product, image or download moved.
- **CI.** The `rebrand-gate` job installs nothing, and the Go job fails on a file `gofmt` lists.

## Verified on a lab

Nothing. No fix of this release has run on a lab yet, and nothing was run on the published images of `v0.9.1`. The fixes are covered by tests only.

- **What `v0.9.0` verified** is in the [notes of v0.9.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.0). It is not repeated here, and this release adds nothing to it.
- **One site run, not a lab run.** On 2026-11-19 one production site moved its platform from the BOM `0.8.0` to `0.9.0`, on the published images of `v0.9.0`. The site has one Proxmox node, one tenant cluster of two workers and one database. One run of 68.6 seconds, eleven stages, no retry. No machine was replaced, both tenants were healthy before and after, and a probe that looked 149 times at the tenant cluster's API, the database's port and the portal saw no failure. The tenant cluster stayed on cluster chart `0.1.13`.
- **What that site run found** is fixed here: the run wrote the firewall rule the plan had not listed, the portal upgrade before it recreated PostgreSQL and Keycloak, and the services sync was held back because it would have written on withdrawn node templates. None of the three fixes was run on that site.

## Not verified

- **The plan entry `pve-api-rule`.** Not seen on a platform that has no rule, with the run after it.
- **The `boot-store` row.** Not read on a store that holds a leftover volume.
- **`404 no_probe`.** Not seen after a Remove, or after a new install.
- **A tenant cluster delete.** Not run: a delete with no failing `csi@pve` request in the Proxmox log.
- **The sync on withdrawn node templates.** Not run on a site that has one, and no worker was cloned from one.
- **The PostgreSQL pin.** Not run: a Compose upgrade from `v0.9.0`, a later upgrade that keeps the container ids of PostgreSQL and Keycloak, and the `helm upgrade` with the new image name.
- **The operator console.** No page was opened: the `409 bom_installed` message and the count on "Managed clusters".
- **The button that publishes the node image.** Not pressed on any lab: the button on the ready card that tests and publishes the node image and offers the version. The notes of `v0.9.0` do not list it, and it has not run since.
- **Everything `v0.9.0` lists.** Its "Not verified" list still holds in full: see the [notes of v0.9.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.0). The upgrade with tenants has run on one production site, and on no lab.

## Known issues

Fixed in this release: the `boot-store` row that named a VM that does not exist, the stored result of the tenant path test that outlived Remove, and the failed token delete at a tenant cluster delete. The `403` on `GET /cluster/status` is by design and is now documented in the [permissions guide](https://github.com/mutex-solutions/proxcloud/blob/v0.9.1/docs/proxmox-permissions.md).

- **The root command stops when the platform's token ids are taken.** The platform's two Proxmox tokens have fixed ids, `capmox@pve!capi` and `csi@pve!csi`. On a Proxmox cluster where one of them already exists for something else, the command stops before it changes anything and prints the command that removes the token. It affects a new install on such a site. The only way forward it offers is to remove that token, which breaks whatever else uses it. See ["The root command of an installation"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.1/docs/managed-services.md#the-root-command-of-an-installation).
- **A chart version that changes only its hook does not run the hook.** ArgoCD syncs an Application only when a rendered object differs. No chart of this release is such a version. It affects a later release, which must also change a rendered object. See ["What a release checks about its BOM pairs"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.1/docs/ci-release.md#what-a-release-checks-about-its-bom-pairs).
- **Workers do not join when the node that holds the platform's addresses also translates tenant traffic.** On a `simple` tenant zone, tenant connections to the platform network are dropped on the Proxmox node that both translates tenant traffic and runs the platform's machines. The network of an installed platform is fixed, so `routed` mode helps a new one-node install only. Read the Check row `tenant-path`, run the test, and use one of [the two layouts that work](https://github.com/mutex-solutions/proxcloud/blob/v0.9.1/docs/managed-services.md#the-path-from-tenants-to-the-platform).
- **The platform upgrade is not shown on a lab with tenants.** It ran once on a production site that has them. Take the seed backup first, or leave the platform on its BOM, where it keeps working.
- **The other known issues of `v0.9.0` remain.** The health check's guard, Replace on a node group of one, a standalone volume that loses its name, the `pve-api-rule` row behind a translating router, and seed ISOs of servers created before `v0.8.0`: see the [notes of v0.9.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.0).
