ProxCloud v0.10.1-rc.2 is the second release candidate of `v0.10.1`, published as a prerelease. It corrects what the lab drill of `v0.10.1-rc.1` found: on a platform with one control plane machine, the replacement of the machines stopped after the control plane. It exists so that a lab can run the whole upgrade on the corrected code: nothing of this candidate has run on a lab yet. It is not for production. `v0.10.0` stays the current stable release.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this candidate is `0.10.1-rc.2`. Against `0.10.1-rc.1` it moves one thing: the cluster chart `proxmox-kamaji-cluster` from `0.1.15` to `0.1.16`. Against `0.10.0` it also moves the seed's k3s from `v1.35.10+k3s1` to `v1.36.6+k3s1`, and the platform cluster from Kubernetes `1.35.10` to `1.36.6` with the node image built for it.

## Highlights

- **The drill of rc.1: the seed part passed, with tenants live.** One lab, one tenant cluster and one database under a write loop. The run took 43 min 20 s, of which 41 min were the import of the node image on three nodes. The seed's API was away 43 s. The database and the write loop had no failure.
- **The drill of rc.1: the platform part stopped after the control plane.** Cluster API gave up deleting the old machine's Node object after 10 seconds, its default, inside the 65 seconds in which the API address moves to the new machine. The Node stayed, and the run waited for a node count that could not come true (`nodes_timeout`, and again at every Retry).
- **Cluster chart `0.1.16` gives the Node delete 30 minutes.** It sets `nodeDeletionTimeoutSeconds` to 1800 on the control plane's and every node group's machines. No machine is replaced for it.
- **The run deletes a Node that no machine owns.** A platform that stands in that wait gets out with one Retry.
- **A replacement that has begun continues under this candidate.** A platform whose machines are being replaced toward `0.10.1-rc.1` goes on under the BOM `0.10.1-rc.2` with Retry, with nothing to type.
- **The seed's k3s stage can wait and fail under its own codes.** The job store refused a code with a digit, so the stage looked once a minute and could not record a failed k3s upgrade.
- **Not run on a lab yet.** Nothing in this candidate: see below.

## Upgrade

Use a lab or another non-production site. Production sites should stay on `v0.10.0` and wait for `v0.10.1`.

These steps upgrade from `v0.10.0` or from `v0.10.1-rc.1`. From an older release, read the [notes of v0.10.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.0) first: their steps and cautions still apply.

1. Upgrade the portal. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1-rc.2/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.10.1-rc.2
   ./proxcloud-up.sh upgrade v0.10.1-rc.2
   ```

2. The platform is not changed by step 1. Find your case in this table, then follow its steps.

| If the platform ... | Do ... |
|---|---|
| Is on the BOM `0.10.0` and no upgrade has started | Steps 3 to 6. |
| Stands in the replacement of its machines toward `0.10.1-rc.1` (phase failed, target `0.10.1-rc.1`, a step recorded) | Step 7. Do not delete the leftover Node by hand. |
| Ran "Seed and node image" under `0.10.1-rc.1` and has not started "Platform cluster" | Step 8. |
| Is on the BOM `0.10.1-rc.1` with its upgrade finished | The plan lists three changes and replaces no machine: the release, the tenant chart and the cluster chart `0.1.15` → `0.1.16`. Type `upgrade <installation name> to 0.10.1-rc.2`. Read, not run: no platform has finished on that BOM. |

3. Before you move a platform from `0.10.0`, do these three things.

   - **Back up the seed VM.** Run `vzdump <seed VMID>` on the seed's node. The upgrade is refused (`409 seed_backup_missing`) until the portal sees a backup of the seed VM younger than 24 hours, or you confirm one.
   - **Know how to answer the backup question.** On most stores the portal cannot see the seed's backups, and the Check row `seed-backup` says so. Then check in Proxmox that there is an archive of this seed VM, made after the seed VM was created and younger than 24 hours. Then tick the box "I checked in Proxmox: seed VM … has a backup …" (`"seedBackupTaken": true` by API).
   - **Read the allow-lists for a network with host bits.** Correct a value such as `192.168.0.5/24` through the portal. This is a precaution: a stored value keeps working.

4. Open System → Managed services and read the plan. From the BOM `0.10.0`, with one control plane machine and one machine each in `system`, `kamaji` and `dbaas`, the plan lists 19 changes and refuses nothing:

   | Change | From → to | Class | Stage | Part |
   |---|---|---|---|---|
   | `roll` (there is no way back) | | machines | `cluster` | Platform cluster |
   | `release` | `0.10.0` → `0.10.1-rc.2` | record only | none | |
   | `kubernetes.version` | `1.35.10` → `1.36.6` | machines | `cluster` | Platform cluster |
   | `kubernetes.nodeImage` | `ubuntu-2604-k8s-1.35.10-…` → `ubuntu-2604-k8s-1.36.6-20261116194043-72f0eaa3d0d4` | machines | `cluster` | Platform cluster (the import is in "Seed and node image") |
   | `seed.k3s` | `v1.35.10+k3s1` → `v1.36.6+k3s1` | seed | `seed-k3s` | Seed and node image |
   | `seed-k3s-job` | Job `proxcloud-system/k3s-upgrade-v1-36-6-k3s1` on the seed | site | `seed-k3s` | Seed and node image |
   | `seed-etcd-snapshot` | `/var/lib/rancher/k3s/server/db/snapshots/pre-upgrade-v1.35.10-k3s1-<node>-<time>` | site | `seed-k3s` | Seed and node image |
   | `seed-k3s-config` | `/etc/rancher/k3s/config.yaml.d/10-proxcloud-leader-elect.yaml` | site | `seed-k3s` | Seed and node image |
   | `seed-k3s-binary` | `/usr/local/bin/k3s`, the previous binary kept as `/usr/local/bin/k3s.prev` | site | `seed-k3s` | Seed and node image |
   | `tenantCharts.kubernetes` | `proxmox-kamaji-cluster` `0.1.15` → `0.1.16` | record only | none | |
   | `pc-platform` | `0.1.15` → `0.1.16` | chart | `cluster`, wave 3 | Platform cluster (with the first step of the replacement) |
   | `roll/controlPlane`, `roll/system@<node>`, `roll/kamaji@<node>`, `roll/dbaas@<node>` | `1.35.10` → `1.36.6` | machines | `cluster` | Platform cluster |
   | `roll-vm/controlPlane`, `roll-vm/system@<node>`, `roll-vm/kamaji@<node>`, `roll-vm/dbaas@<node>` | 1 new VM cloned, 1 old VM deleted with its boot disk | site | `cluster` | Platform cluster |

5. Run **Seed and node image**. Type `upgrade <installation name> to 0.10.1-rc.2`. The figures are those of rc.1's drill: one run on one lab, not a promise for a site.

   - **What it does.** It imports the 1.36.6 node image as a template on every Proxmox node the cluster uses (about 2.4 GiB each, one node after another). On the seed it saves an etcd snapshot, writes the k3s config file that turns leader election off in three components, replaces the k3s binary and restarts k3s.
   - **How long.** On the lab 43 min 20 s, of which 41 min were the import on three nodes.
   - **What stops serving.** The seed's API: 43 s on the lab. Meanwhile no machine is repaired, the seed's ArgoCD syncs nothing and no platform run goes on.
   - **What keeps serving.** The platform cluster, every tenant cluster and the databases. On a shared or slow disk the import itself can stall an API for seconds: on the lab the seed's k3s restarted once during an import (39 s), and single looks at the platform API and the tenant API failed in those minutes. Pick a quiet hour.
   - **It replaces no machine.** Stop here if something looks wrong on the seed: the platform cluster is still on 1.35.10.

6. Run **Platform cluster** (the button **Replace the machines**). Until step 5 is done it is blocked with `seed_not_upgraded`. Type `upgrade <installation name> to 0.10.1-rc.2 and replace its machines`. Only the control plane's unit was ever run, on rc.1; no figure exists for the others.

   - **Control plane first.** A second machine is cloned from the 1.36.6 template and joins, then the old one is removed. On the lab the platform cluster's API did not answer for 65 s at the hand-over. On a node whose disk the control plane shares with the clone, the API can be away during the clone too: 2 min 21 s on the lab. The tenant API and the database kept answering through both.
   - **Then `system`, `kamaji` and `dbaas`.** With one `kamaji` machine **every tenant API server is away** while its pod restarts on the new machine. With one `dbaas` machine **every database with one instance on it is down** while its pod and disk move. Not measured.
   - **A node without room.** A group on a node without room for one more machine is replaced delete-first. A control plane node without room refuses the upgrade (`capacity_short`).
   - **Pause.** Pause stops the run between two units, and Resume goes on at the next one. Not run on a lab.
   - **The machine replacement has NO way back.** Once the new control plane machine has joined the platform cluster's etcd, the run restores nothing. A step that fails leaves the machines that still run serving, and Retry goes on at that step.
   - **The seed's k3s has a way back by hand.** The message of `seed_k3s_timeout` gives the command, with the snapshot restore; the [notes of v0.10.1-rc.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1-rc.1) show it. It was not tried on a lab. The backup of the seed VM is the last net.

7. A platform that stands in the replacement toward `0.10.1-rc.1`: press **Retry**. There is nothing to type. With the installed BOM `0.10.0`, the target `0.10.1-rc.1` and step 1 recorded, the plan of this candidate shows one upgrade in progress, to `0.10.1-rc.2`:

   | Plan field | Value |
   |---|---|
   | Target | `0.10.1-rc.2`, in progress, allowed, nothing blocking, no phrase |
   | `carried` | `0.10.1-rc.1` (the target this BOM took the place of) |
   | Part "Seed and node image" | done |
   | Part "Platform cluster" | allowed, no phrase |
   | Changes | The 19 rows of step 4, `pc-platform` `0.1.15` → `0.1.16` among them |

   - **What Retry does.** The run uses the BOM `0.10.1-rc.2` and records it as the target. The step is kept: the units already replaced stay as they are, and the others are replaced with cluster chart `0.1.16`.
   - **The leftover Node.** The run deletes the Node of the old control plane machine by itself: it is not Ready, and no machine owns it. The stage's item `node/<name>` names it. Do not delete it by hand.
   - **This path was not run on a lab.** It is covered by tests against a fake Cluster API only.

8. A platform that ran "Seed and node image" under `0.10.1-rc.1` and has not started "Platform cluster": an apply without a target would go on to `0.10.1-rc.1`, with cluster chart `0.1.15`. Start the move to this candidate instead: the plan offers it next to the unfinished one. Type `upgrade <installation name> to 0.10.1-rc.2 and replace its machines`. Read, not run.

9. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.10.0-rc.1` | As from `0.10.0`: 19 changes, the same two actions. Read, not run. |
| A platform on the BOM `0.9.0`, `0.9.1` or a candidate of `0.9.0` | The plan lists 20 changes: the two tenant charts and the cluster chart `0.1.14` → `0.1.16` next to the move to Kubernetes 1.36.6. Read, not run. |
| A platform on a `0.8.x` BOM | The plan lists 23 changes: also the cluster chart `0.1.13` → `0.1.16` and the three components of platform chart `0.1.2` → `0.1.3`. Read, not run. Move to `0.10.0` first if you can. |
| A platform you move to the BOM `0.10.1-rc.2` | Keep it on a lab. Later builds apply it only while they carry this BOM; `v0.10.1` is planned to. A build without it refuses the platform (`bom_unsupported`). |
| Tenant Kubernetes clusters and databases | They are not upgraded and stay on their version (1.35.10). A new tenant cluster gets cluster chart `0.1.16`; an existing one keeps its chart until its own bump. |
| A site with one Proxmox node | Not run. The control plane's surge machine is cloned on the node the control plane runs on: expect the API away during the clone as well. |
| A site installed with the Ansible installer | Nothing moves. The installer keeps k3s `v1.35.10+k3s1` and Kubernetes `1.35.10`. |
| A new install | Pass `--version v0.10.1-rc.2` to `proxcloud-up.sh install`. The script's default, the chart and the installer still name `v0.10.0`. |

## What changed

Since `v0.10.1-rc.1`: one merged pull request with the corrections (#402), the cluster chart `0.1.16`, and this BOM. What rc.1 changed since `v0.10.0` is in the [notes of v0.10.1-rc.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1-rc.1) and is part of this candidate.

### The replacement of the machines

- **Cluster chart `proxmox-kamaji-cluster` `0.1.16`** (#402). It reads `nodeDeletionTimeoutSeconds` (default 1800) and renders it on the control plane's machines and on every node group's. Cluster API then tries the Node delete again until the platform cluster's API answers. Cluster API puts the value on the machines in place: no machine is replaced for it. The kube-vip lease is unchanged.
- **The run deletes a Node no machine owns** (#402). Between two units and in stage 9, a Node that is not Ready, that Cluster API joined for a machine of this cluster which is gone, and that no Machine or ProxmoxMachine names, is deleted through the platform cluster's API. A Node that a machine owns is never deleted. `nodes_timeout` now names the nodes.
- **A replacement that has begun continues under a later BOM** (#402). While a unit is still to be replaced, a later release whose BOM differs from the unfinished target only in the product's own charts and the release takes the target's place at Retry. A later BOM that changes Kubernetes, the node image or k3s again is refused by name.
- **The Check has a row `nodes`** (#402). It warns, by name, about a node that is not Ready. It never fails the Check.

### The seed

- **Stage `seed-k3s` can wait and record its failure** (#402). The job store now takes a digit in a code (`waiting_seed_k3s`, `seed_k3s_failed`, `seed_k3s_refused`, `seed_k3s_timeout`). The stage looks every 15 seconds as designed and no longer spends a job attempt per look.
- **The etcd snapshot is recorded by its real name** (#402), on the run and in `status.seed.preUpgradeSnapshot`.
- **An import that is tried again says so** (#402). The `images` item shows the try and the last code.

### Fixes

- **Template updates lists no VMID twice** (#402). A `template_missing` row names no VMID another guest holds.
- **The guide carries the drill's figures** (#402), each marked as one lab's sample, and `nodes_timeout` for stage 7.

### Release

- **BOM `0.10.1-rc.2`.** `pc-platform` and `tenantCharts.kubernetes` pin cluster chart `0.1.16` at `sha256:2a58fa81b5a96fd7b23c76b06418af5a477586f151ec8e9eab1bad1536e6f000`. `pc-platform` may replace `0.1.13`, `0.1.14` and `0.1.15`, so every previous BOM reaches it. Nothing else moved against `0.10.1-rc.1`. This build carries the BOMs of `0.8.0`, `0.8.1`, `0.8.2`, `0.9.0-rc.1`, `0.9.0-rc.2`, `0.9.0`, `0.9.1`, `0.10.0-rc.1`, `0.10.0` and `0.10.1-rc.1` as previous BOMs.
- **A candidate moves nothing a final moves.** The app chart, the installer pin and the Compose default stay on `v0.10.0`.

## Verified on a lab

Nothing of this candidate. The list below is what the audit of the drill of `v0.10.1-rc.1` confirmed, on that candidate's images and BOM: one run on one lab (three Proxmox nodes on one shared disk, one control plane machine, one tenant cluster and one database under a write loop).

- **"Seed and node image", the whole part.** The run took 43 min 20 s in seven stages with no retry. The seed node came back at `v1.36.6+k3s1` with the same uid and boot id, containerd 2.3.7. The pre-upgrade etcd snapshot exists as an object (11,743,264 bytes, ready to use); the file itself was not seen.
- **The config file without leader election, by its effect.** The three components' leases were not renewed after the restart. The file and `k3s.prev` were not seen directly.
- **The seed's API gaps.** 43 s in the k3s stage. Once more, unplanned, 39 s during the image import.
- **Serving through the seed part.** Failed looks, one every 2 s: platform API 12 of 1535, tenant API 7 of 1526, database port 0 of 1569.
- **"Platform cluster", the control plane's unit only.** One clone (6 min 5 s), the new member added to etcd, the old member removed, the old VM destroyed. The platform API did not answer for 88 s and 54 s during the clone, 22 s after the join and 65 s at the hand-over. The tenant API's longest gap was 13.4 s. The database port had 0 failed looks of 1558, the write loop no failed insert, and the marker row was unchanged.
- **Cilium on the one 1.36.6 node.** The agent is Ready with no restart.
- **The state the drill left serves.** Control plane at 1.36.6, the three node groups at 1.35.10, the old control plane machine's Node still listed.
- **The findings are real.** The Node left behind (blocker; the 65 s are the chart's own kube-vip lease against a 10 s timeout, not the lab's disk). The seed stage's codes refused by the job store. The clone taking a single control plane away before the join. Five minor ones: the import's load on a shared disk, the hidden import tries, the snapshot's name, the Check with a machineless node, the guide's `nodes_timeout` row.

## Not verified

- **This candidate.** Not run: its images, its tag's workflows, and any move of a platform to the BOM `0.10.1-rc.2`. None of the corrections ran against a real cluster.
- **Units 2 to 4 of the replacement.** `system`, `kamaji` and `dbaas` were never replaced on a real cluster: no gap of theirs is measured, no MetalLB address moved, no volume followed its pod to a new machine.
- **The whole replacement on the corrected code.** Also not run: the Retry that takes a stuck platform on under this BOM, the Node delete by the run, and chart `0.1.16` on a live cluster.
- **Pause and Resume.** Never exercised between two finished units.
- **The seed's way back.** The command with the snapshot restore was not tried.
- **A new tenant cluster at 1.36.6.** None was created at that version anywhere.
- **cert-manager issuing on 1.36.** No certificate was issued after the move, on the seed or on the platform cluster. cert-manager `v1.20.2` and Cilium `1.18.16` stay outside their own support matrix on 1.36.
- **A one-node site.** Not run. The lab has three nodes.
- **A site with SNAT.** Not run.
- **The moves from the other BOMs.** Their plans were read, not run. The drill covers the move from `0.10.0`.
- **Earlier releases.** Everything the [notes of v0.10.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.0) list as not verified still holds.

## Known issues

- **The corrected replacement has never run on a real cluster.** It affects every platform moved to this BOM. Run it on a lab first.
- **The machine replacement cannot be undone.** After the new control plane machine has joined, the only nets are the seed VM's backup and the tenants' own backups.
- **With one control plane machine the platform API is away at the hand-over, and can be away during the clone.** 65 s and 2 min 21 s on the lab. No tenant cluster or database operation runs meanwhile.
- **With one `kamaji` machine every tenant API server is away during its replacement.** With one `dbaas` machine every one-instance database on it is down during its replacement. How long was not measured.
- **The node image import loads the disk.** On a shared or slow disk it can stall the seed's or the platform cluster's etcd for seconds. Three nodes took 41 min on the lab.
- **A platform that only ran the seed part under rc.1 goes on to rc.1's BOM unless you name this one.** See step 8.
- **cert-manager and Cilium are outside their own support matrix on 1.36.** If one fails after the upgrade, this release cannot move its chart.
- **The `seed-backup` row cannot see a backup on most stores.** The upgrade is then started with the box that says a backup was taken. See [the permissions guide](https://github.com/mutex-solutions/proxcloud/blob/v0.10.1-rc.2/docs/proxmox-permissions.md#what-the-fence-hides-from-the-portal-the-seeds-backups).
- **Earlier releases.** The other known issues in the [notes of v0.10.1-rc.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1-rc.1) and of [v0.10.0](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.0) still hold.
