ProxCloud v0.9.0-rc.2 is the second release candidate of `v0.9.0`, published as a prerelease. It is `v0.9.0-rc.1` plus three fixes for what the second lab round found. It is for a lab: to run a fresh install and to drill the platform upgrade on a build that holds the fixes. It is not for production. `v0.8.2` stays the current stable release.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this candidate is `0.9.0-rc.2`. It pins what `0.9.0-rc.1` pins: only the `release` line differs.

## Highlights

- **The platform upgrade ran on a lab.** A platform that `v0.8.0` installed moved to the BOM `0.9.0-rc.1` in one run of 72.8 seconds. No machine was replaced and no pod restarted. The lab had no tenant cluster and no database, so the upgrade is not shown for a site that has them.
- **Tenant workers start with their Proxmox node after an upgrade.** A site upgraded from `0.8.x` kept node templates and workers without `onboot`. The provider sync now sets it.
- **A control plane that does not fit is blocked.** Three control plane machines saved on a node without room are now listed in the plan and refused by the Check, before any run.
- **Clearer upgrade texts.** The plan no longer says that ArgoCD syncs every chart that moves, and a stage's progress names the BOM's wave.
- **Not run on a lab yet.** None of the three fixes, and nothing on this candidate's own images: see below.

## Upgrade

Use a lab or another non-production site. Production sites should wait for `v0.9.0`.

1. On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0-rc.2/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.9.0-rc.2
   ./proxcloud-up.sh upgrade v0.9.0-rc.2
   ```

2. The platform is not changed by step 1: it stays on its BOM. To move it, open System → Managed services, read the plan in step 4 and confirm the upgrade. See ["Upgrade between BOMs"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0-rc.2/docs/managed-services.md#upgrade-between-boms).

3. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.9.0-rc.1` | Nothing is needed: this build applies it as it is. To move it, confirm the upgrade in step 4. The plan lists one change, the release, and nothing is synced for it. Not run on a lab. |
| A platform on a `0.8.x` BOM | The plan lists six changes and refuses nothing, as it did to `0.9.0-rc.1`. Before the upgrade, check that tenant clusters and databases are healthy and take the seed's backup, as the guide says. |
| A platform you move to the BOM `0.9.0-rc.2` | Keep it on a lab. Later builds apply it only while they carry this BOM; `v0.9.0` is planned to, and moving to its BOM is one more upgrade run. A build without it refuses the platform (`bom_unsupported`). |
| Tenant Kubernetes clusters made before this upgrade | Wait for one provider sync (every 15 minutes) before a planned Proxmox node reboot: it sets `onboot` on the node templates this portal imported and on running workers. It does not cover a template the portal did not import, or a worker that is stopped: see ["After a Proxmox node reboots"](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0-rc.2/docs/managed-services.md#after-a-proxmox-node-reboots). |
| A script that sends the installed BOM as `targetBom` | The answer is now `409 bom_installed`. It was `400 invalid_confirmation`. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |
| A new install | Pass `--version v0.9.0-rc.2` to `proxcloud-up.sh install`. The script's default, the chart and the installer still name `v0.8.2`. |

## What changed

Since `v0.9.0-rc.1`. Everything else is as in the [notes of v0.9.0-rc.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.9.0-rc.1).

### Kubernetes

- **`onboot` on old node templates and workers.** `onboot` was written on a Kubernetes node image only at its import. A node template imported before `v0.9.0` had none, and neither had its workers, so they stayed stopped after a node reboot. The provider sync now sets it where it is missing, on the node templates this portal imported and on the running workers of its tenant clusters. It needs no new Proxmox privilege.
- **Join log without key art.** The join log of a worker that did not join no longer ends with SSH host key art.

### Managed services

- **Control plane growth is checked.** On an installed platform, a larger control plane count is now a change in the plan (`controlPlane.replicas`). When the new machines do not fit, the Check row `capacity` fails, the plan carries the reason in `blocking`, and an apply stops at its first stage. What already runs still only warns.
- **Upgrade plan texts.** A chart that moves is synced by ArgoCD only where the new version renders an object differently, and its hook runs only then. The plan and the guide now say so. After an upgrade, ArgoCD's history can still name the old version as the last sync: that is the upgrade having landed.
- **Wave numbers.** A stage that applies waves shows `step 3 of 4, wave 2`, with the wave number the plan uses.
- **`409 bom_installed`.** An apply whose `targetBom` is the BOM the platform is already on gets this answer, in place of a text about `confirm`.

### Release

- **BOM `0.9.0-rc.2`.** The same pins as `0.9.0-rc.1`: cluster chart `0.1.14`, platform chart `0.1.3`. Neither chart changed. This build carries the BOMs of `0.8.0`, `0.8.1`, `0.8.2` and `0.9.0-rc.1` as previous BOMs.

## Verified on a lab

The second lab round, on 2026-11-19, on one lab Proxmox VE cluster, with the published images of `v0.9.0-rc.1` over a platform that `v0.8.0` installed. It ran before the three fixes of this candidate. Nothing was run on this candidate's own images.

- **The upgrade from `0.8.0` to `0.9.0-rc.1`, on a lab without tenants.** One run, no retry, 72.8 seconds. The plan showed six changes and nothing blocking. The lab had no tenant cluster and no database.
- **Nothing rolled.** The same four machines, nodes and boot ids, the same QEMU processes, and no Proxmox task. No pod restarted: 47 on the platform cluster, 16 on the seed. The platform API answered at each of 238 looks, one every 2 seconds.
- **What ArgoCD did.** It synced one Application of fourteen, `platform`. The three other chart moves were compared and found in sync, and no clusterctl hook ran. A second apply took 5 seconds and changed nothing.
- **Refusals.** Seven requests with a wrong confirmation or a wrong target were refused, and none started a run.
- **Chart 0.1.14 on a new tenant cluster.** A worker was Ready 9 minutes after the create. A node group of one gets no health check, by design; a group of two got one, with its guard.
- **Replace.** On the last Ready worker it asked for a confirmation, then made a new machine whose node was Ready 7 minutes 21 seconds later. The group had no node for about 6.7 minutes.
- **The health check, all workers failed.** On a cluster whose two workers could not join, it replaced nothing, as its guard says. A replacement by the health check was not seen.
- **Worker firewall, one worker.** From a second tenant machine, the kubelet, SSH and port 4240 were closed afterwards, and NodePort and LoadBalancer stayed open. The node stayed Ready. Two of about 6000 one-second requests failed in 52 minutes, none at the change.
- **Provider settings check and join error.** The refusals and their texts, and `kubeadm`'s own error in the join log, with no token in it.
- **Tenant path test.** A full run on a `simple` zone gave the verdict `failed`, the predicted one for the node that holds the platform's addresses, and cleaned up. `passed` was not seen.
- **Three control plane machines.** The save was accepted on a node without room and the plan showed no change. This candidate fixes that. Nothing was applied.

## Not verified

- **This candidate.** Not run: its images, its three fixes, the tag's workflows, and the upgrade to the BOM `0.9.0-rc.2` from `0.9.0-rc.1` or from a `0.8.x` BOM.
- **The upgrade with tenants.** Not run on a platform that has a tenant cluster or a database: the wait for tenants in stage 9, a tenant that is unhealthy (`tenants_unhealthy`), the `platform` chart's sync beside live tenant control planes, and an existing cluster staying on chart `0.1.13`.
- **A failed upgrade.** Not run: a failed stage, Retry, a restore, and the refusal of a chart that would replace a machine (`unexpected_rollout`). The seed's backup was not taken before the lab upgrade.
- **The upgrade from other starts.** Not run: the portal's own step from `v0.8.2` (the lab's portal came from a build of `main`), and a platform on the BOM of `0.8.1` or `0.8.2`.
- **The console.** The upgrade was run at the API. Step 4 of the console was not opened.
- **Worker repair.** Not seen: a replacement by the health check, Replace of a machine that has no node, and `onboot` on a freshly imported node template and its clone.
- **Worker firewall.** Not run: two workers, a new or replaced worker, and `workerFirewall: true` on the provider.
- **Network modes.** Not seen: the path test's verdict `passed`, `routed` mode, and a VLAN tag.
- **A fresh install from a candidate.** Not run: a preset, the one root command on a node, three control plane machines, and the button that publishes the node image and offers the version.
- **Earlier releases.** Everything `v0.8.0`, `v0.8.1`, `v0.8.2` and `v0.9.0-rc.1` say is not verified still holds, except what is listed as verified here.

## Known issues

- **A health check replaces nothing when every worker of a group fails.** That is its guard. The machines stay, show "not joined" with "needs attention", and are counted in the tenant's quota. It affects a tenant whose workers cannot reach the platform. Repair the cause, then use Replace or delete the cluster.
- **Replace on a node group of one leaves the group without a node.** The old machine goes first: on the lab the group had no node for about 6.7 minutes. It affects a tenant with one worker. Raise the group's count by one first when the workload cannot wait.
- **A chart version that changes only its hook does not run the hook.** ArgoCD syncs an Application only when a rendered object differs. No chart of this candidate is such a version. It affects a later release, which must also change a rendered object.
- **A standalone volume can lose its name at create.** A volume created without a server can answer `200` with no `id` when Proxmox is slow, and is then named after its disk at the next provider sync. It affects a tenant who creates such a volume. Nothing is lost but the name; not fixed.
- **Workers do not join on some site layouts.** Tenant connections to the platform network are dropped on a site where one Proxmox node translates tenant traffic and also runs the platform's machines. The network of an installed platform is fixed, so `routed` mode helps a new one-node install only. Read the Check row `tenant-path` and use one of [the two layouts that work](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0-rc.2/docs/managed-services.md#the-path-from-tenants-to-the-platform).
- **The `pve-api-rule` row can read `ok` while the rule matches nothing.** This happens on a site whose router translates the platform network on the way to the Proxmox node. It affects installs on such a site. Add a rule for the translated address: see [the guide](https://github.com/mutex-solutions/proxcloud/blob/v0.9.0-rc.2/docs/managed-services.md#when-a-router-translates-the-platform-network).
- **Seed ISOs of servers created before `v0.8.0` are never swept.** When such a server is deleted, its seed ISO stays on the seed store and holds the server's user data. It affects a site with such servers. Clean it up by hand with the commands in the [release notes of v0.8.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.8.2).
