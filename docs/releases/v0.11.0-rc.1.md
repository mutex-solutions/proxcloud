ProxCloud v0.11.0-rc.1 is the first release candidate of `v0.11.0`, published as a prerelease. It brings load balancers that run on a pair of appliances, a load balancer controller for managed Kubernetes clusters, an opt-in gateway listener for Docker Compose, and two billing fixes. It exists so that a lab can run the drill of these: none of them has run on a lab on this code yet. It is not for production. `v0.10.2` stays the current stable release.

The BOM (bill of materials) is the list of exact versions a managed-services platform runs. The BOM of this candidate is `0.11.0-rc.1`. Against `0.10.2` it moves one thing: the cluster chart for new tenant clusters, `proxmox-kamaji-cluster` `0.1.16` → `0.1.17`. k3s, the Kubernetes version, the node image, the providers, the third-party charts and the platform cluster's own chart stay the same.

## Highlights

- **Load balancers on two appliances.** A new load balancer runs on two VMs by default: one carries the traffic, the other takes over when it fails. Existing balancers keep their single VM.
- **What HA means here.** The two VMs go to two nodes when the site can place them so. On a one-node site, or on a tenant network in a `simple` zone, both run on one node: the pair survives the failure of one appliance, not the loss of the node. The page says so.
- **A load balancer controller for managed Kubernetes.** A Service of type LoadBalancer gets a public address on a pair of the product's appliances. New clusters get it where the site can serve it. Existing clusters keep MetalLB, and the operator can add the controller to one in class-only mode.
- **A gateway listener for Docker Compose.** Opt-in, with `--cluster-gateway <address>`. It needs a new route: from the platform network to the portal host on port 8444.
- **What it costs.** A pair is two servers with their disks, plus one public address per address of the balancer (VIP). Nothing new to price: these bill as servers, volumes and floating IPs.
- **Two billing fixes.** An address owned by a load balancer is no longer taken for an orphan, which would have stopped the project's address billing. A pair's traffic is counted once.
- **More on every load balancer.** HTTP health checks, PROXY protocol v2, and allowed source ranges per listener.
- **A light platform upgrade.** From the BOM `0.10.2` the plan has two rows, both record only: no machine is replaced, nothing is synced, no seed backup is asked for.
- **Failover measured on the spike only.** The spike before the code, on the lab: a dead master lost 3.1 to 3.5 s, a planned switch under 1 s. Not measured on this candidate.

## Upgrade

Use a lab or another non-production site. Production sites should stay on `v0.10.2` and wait for `v0.11.0`. These steps upgrade from `v0.10.2`. From an older release, read the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) first: their steps and cautions still apply.

1. **Check the platform's BOM first.** The move is planned from the BOMs `0.10.1`, `0.10.2` and their candidates. A platform on an older BOM (`0.8.0` to `0.10.0` and their candidates, all on Kubernetes 1.35.10) is refused by this build. Move it to `0.10.1` first with the `v0.10.1` build, both parts, as the [notes of v0.10.1](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.1) describe.

2. **Upgrade the portal.** On the Docker Compose host, check out the tag and run the upgrade. The script takes its backup first. `compose.yaml` did not change since `v0.10.2`. See ["Upgrade" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0-rc.1/deploy/compose/README.md#upgrade).

   ```sh
   git fetch --tags && git checkout v0.11.0-rc.1
   ./proxcloud-up.sh upgrade v0.11.0-rc.1
   ```

   - **From now on a new load balancer is a pair.** Each one costs two servers, their disks and one address. A tenant can still ask for one VM (`ha: false`).
   - **The appliances need their packages.** A stock image gets `haproxy`, `socat` and `keepalived` from apt. A site with no egress bakes them into `config.lbImage`.
   - **A public network that is an SDN vnet is refused for a pair.** Use a plain bridge.

3. **Optional on Compose: turn on the gateway listener.** Only for the load balancer controller of managed clusters. Re-run `install` on the same version with the address of this host that the platform cluster's nodes reach:

   ```sh
   ./proxcloud-up.sh install --cluster-gateway <address>
   ```

   - **Add the route.** The platform cluster's nodes, on the platform network, must reach the portal host on `<address>:8444`. Without it no controller reaches the gateway, and its cluster page says it has not reported. Nothing else breaks.
   - **Keep the volume `gateway`.** It holds the listener's key and self-signed certificate (made on the API's first start). A new certificate means a new gateway Secret for every cluster. Database backups do not hold it.
   - **Block volumes stay off on Compose.** No gateway token is registered there, with or without the listener.
   - See ["Optional features" in the Compose guide](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0-rc.1/deploy/compose/README.md#optional-features).

4. **Read the plan.** Open System → Managed services and read the plan in step 4. From the BOM `0.10.2` (or `0.10.2-rc.1`) it lists two changes and refuses nothing:

   | Change | From → to | Class | Stage | Wave |
   |---|---|---|---|---|
   | `release` | `0.10.2` → `0.11.0-rc.1` | record only | none | |
   | `tenantCharts.kubernetes` | `proxmox-kamaji-cluster` `0.1.16` → `0.1.17` | record only | none | |

5. **Run the upgrade.** Type `upgrade <installation name> to 0.11.0-rc.1`. There is one action, with no parts.

   - **What it does.** It records the new release and writes chart `0.1.17` on the Kubernetes provider. Clusters created after it get the new chart.
   - **What it does not do.** It replaces no machine, syncs nothing and writes nothing on Proxmox. The platform cluster stays on chart `0.1.16`. No tenant cluster changes chart, and none loses MetalLB.
   - Its duration was not measured.

6. **Let new clusters get the controller.** On the Kubernetes provider, set `config.cluster.loadBalancer`: a public network of the workers' Proxmox provider (with a gateway, on a plain bridge) and the flavor of the appliances. The form calls them **Load balancer public network** and **Load balancer flavor id**. A new cluster then gets the controller in default mode when every gate holds:

   - the portal has a gateway URL and the controller image (Compose: `--cluster-gateway`; the installer chart: `api.csiGateway`);
   - the provider pins chart `0.1.17` or later (step 5);
   - the workers are the project's own, not shared;
   - the project may use that public network.

   In default mode a Service without a class gets a public address, and MetalLB serves only class `proxcloud.io/internal`. NGINX Gateway Fabric then takes one public address per Gateway. When a gate does not hold, the cluster is made as before, with MetalLB alone, and the API log says which gate.

7. **Optional: add the controller to an existing cluster.** An existing cluster keeps MetalLB as its default. The operator's **Load balancer** dialog (provider → clusters) runs **Enable load balancer controller**, in class-only mode: only Services of class `proxcloud.io/lb` get the product's balancer, and no MetalLB address moves. It moves the cluster to the provider's chart, so run step 5 first. Moving a Service to the product's balancer means deleting it and creating it again, with a new address. See ["How a cluster lands on Proxmox"](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0-rc.1/docs/managed-k8s.md#9-how-a-cluster-lands-on-proxmox).

   ```text
   POST /api/v1/admin/service/{kubernetesProviderId}/k8s-clusters/{clusterId}/load-balancer
   ```

8. Follow each row of this table that matches your site.

| If you run ... | Do ... |
|---|---|
| A platform on the BOM `0.10.1` or `0.10.1-rc.2` | The plan has four changes: the two above and cert-manager `v1.20.2` → `v1.21.3` on the seed and on the platform cluster. Back up the cert-manager resources first, as the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) say. Read, not run. |
| A platform on the BOM `0.10.1-rc.1` with its upgrade finished | Five changes: those four and the platform cluster's chart `0.1.15` → `0.1.16`. No machine is replaced. Read, not run. |
| A platform that stands in the replacement of its machines toward `0.10.1` or one of its candidates | Press **Retry** first: it goes on to that BOM, which this build carries. Then upgrade as above. |
| A platform on an older BOM | Refused (step 1). |
| A platform you move to the BOM `0.11.0-rc.1` | Keep it on a lab. Later builds apply it only while they carry this BOM; `v0.11.0` is planned to. A build without it refuses the platform (`bom_unsupported`). |
| Load balancers made before this release | Nothing changes: one VM, the same config and firewall rules. A pair is a new balancer, with a new address. |
| Tenant Kubernetes clusters made before this release | Nothing changes: they keep their chart and MetalLB until step 7. |
| A site with no public network for cluster load balancers | Leave `config.cluster.loadBalancer` empty. Every cluster keeps MetalLB alone. |
| A site installed with the Ansible installer | The tag's app chart sets the controller image where `api.csiGateway` is set. The installer still pins `v0.10.2`. Not drilled. |
| A new install | Pass `--version v0.11.0-rc.1` to `proxcloud-up.sh install`. The script's default, the chart and the installer still name `v0.10.2`. |
| A platform installed from a `dev-<sha>` build of `main` | It is still refused (`bom_unsupported`). Remove it and install again. |

## What changed

Since `v0.10.2`: four merged pull requests.

### Load balancers

- **A pair of appliances** (#415). keepalived (VRRPv3, unicast over the project network) moves the address between two VMs that run the same HAProxy config. Both start as backup and neither takes the address back (`nopreempt`). A stopped HAProxy hands the address to the peer. The standby gets every config change first. See ["High availability: a pair of appliances"](https://github.com/mutex-solutions/proxcloud/blob/v0.11.0-rc.1/docs/cloud-integration.md#high-availability-a-pair-of-appliances).
- **The firewall the pair needs.** The product writes a `vrrp` rule from the peer on each appliance, and adds each address to both appliances' filter sets entry by entry. The spike showed both are needed: without the rule both appliances hold the address, without the filter entries the address does not answer.
- **Status and repair.** `ACTIVE`, `DEGRADED` (one appliance, or both holding the address, with the reason) or `DOWN`. **Replace appliances** rebuilds both from the current image, the standby first, with one planned switch. It is the way to new packages.
- **Placement.** The second VM goes to another node when it can (a soft spread group), and to the first one's node on a `simple` zone, whose traffic stays on its node.
- **Health checks, PROXY v2 and source ranges** (#415). Per pool an HTTP check on a path and port, and `proxyProtocol`. Per listener `sourceRanges`, written as the source of the listener's firewall rule. For single appliances and pairs.
- **A failed build leaves no VM behind.** The next try destroys an appliance the failed build could not remove.

### Managed Kubernetes

- **The gateway takes a cluster's load balancer state** (#416). A cluster's controller calls `PUT /lb/v1/state` with its own credential, stored as a hash only. The portal checks each Service (TCP and IPv4 only), keeps only the cluster's own workers as members, and builds the balancer in the background: one pair per cluster, one public address per Service. A cluster's release revokes the credential first.
- **The load balancer controller** (#417, cluster chart `0.1.17`). One per cluster, next to its control plane on the platform cluster. Every 10 s it sends the cluster's Services and nodes, writes each address in the Service's status, and reports refusals (UDP, no node port, source ranges, quota) as Events. It is a second binary of the `proxcloud-api` image, with no image of its own. Its NetworkPolicy lets it reach DNS, its namespace's control planes and the gateway only.
- **Default mode for new clusters, class-only for existing ones** (#417). See Upgrade, steps 6 and 7. NGINX Gateway Fabric's Service class is never changed.
- **The consoles** (#418). The tenant's cluster page says which Services get a public address and what the pair and each address cost, and shows the balancer. The operator's provider form edits `config.cluster.loadBalancer`, and the clusters card shows each cluster's mode with a **Load balancer** dialog. On the load balancer pages a cluster's balancer is read-only.
- **New clusters get chart `0.1.17`** (#418). The BOM pins it for tenant clusters; the platform cluster stays on `0.1.16`.

### Docker Compose

- **`--cluster-gateway <address>`** (#417). The API listens on 8444, published on `<address>:8444` only, with an ECDSA key and a self-signed certificate it makes on its first start, in a volume of its own. Off by default; `--no-cluster-gateway` turns it off. It takes `v0.11.0-rc.1` and later.

### Billing

- **A load balancer's address is not an orphan** (#415). Before, such a row (no VM lists it) would have stopped the project's floating IP reconcile: the address was never billed, and no other address change of the project reached its rows.
- **A pair's traffic is counted once** (#415). One counter per appliance and balancer on the appliance's public NIC, never one per address.
- **What a pair costs.** Two `SERVER` rows and their `VOLUME` rows (hidden from Servers, listed on the balancer's page) and one `FLOATING_IP` row per address. No new billing type and no new quota key. A cluster's balancer bills from its first Service until the cluster is deleted; each Service's address counts against `floatingIps`.

### Release

- **BOM `0.11.0-rc.1`.** The pins of `0.10.2` but the tenant cluster chart `0.1.17`. No chart of the product changed since its tag. This build carries the BOMs of `0.8.0` to `0.10.2` (fourteen) as previous BOMs.
- **A candidate moves nothing a final moves.** The app chart, the installer's ProxCloud pin and the Compose default stay on `v0.10.2`.

## Verified on a lab

Only the v0.11.0 load balancer spike, not this candidate. On 2026-11-21, before any of this code was written, two tenant servers on the lab (portal `v0.10.2-rc.1`) were set up by hand as a pair: keepalived and HAProxy over SSH, the `vrrp` rule and the address's filter entries written by hand on those two VMs and removed after. Both appliances were on one node, on a tenant VLAN network; the client was a pod inside that network, sending 10 requests per second. Three runs of each:

| Fault | Requests lost for |
|---|---|
| Master stopped through the product (an ACPI shutdown: a planned switch) | 0.7 to 0.8 s |
| Master hard-reset through the product (a dead master) | 3.1 to 3.5 s |
| keepalived stopped on the master | 0.7 to 0.9 s |
| HAProxy stopped on the master and left down | 2.0 to 2.6 s |
| HAProxy killed on the master | 0.6 s, no switch: systemd restarted it |

- **No take-back.** The returning appliance stayed backup every time.
- **Reloads lost nothing.** Adding an address with a keepalived reload, and three HAProxy reloads, lost no request.
- **A split heals.** With the `vrrp` rule missing at start both held the address; once the rule was on both, one yielded 2.1 to 5.2 s later.
- **What the code took from it.** The `vrrp` rule and the filter entries the product writes; one address always in keepalived's `virtual_ipaddress` (keepalived refuses a config without one).

## Not verified

- **This candidate's code, all of it.** Not run on a lab: the pair as the product builds it (create, status, apply, Replace appliances, delete), the rule and filter entries it writes, the gateway, the controller, chart `0.1.17` on a tenant cluster, the enable action, the Compose gateway listener and the consoles. The lab drill comes next.
- **A pair on a public network.** The spike's address was on a tenant network; the lab has no public network.
- **Two nodes and node loss.** VRRP between two nodes, the loss of a node, and open connections across a switch.
- **The billing fixes on a site.** Covered by tests only.
- **The upgrade.** No move to the BOM `0.11.0-rc.1` has run, from any previous BOM.
- **The installer path.** The controller image set by the app chart was not run.
- **This candidate.** Its images and its tag's workflows do not exist before the tag.
- **Earlier releases.** Everything the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) list as not verified still holds.

## Known issues

- **Never run on a lab.** Run the drill on a lab first.
- **One node is not node HA.** Where both appliances run on one node, the loss of the node takes the address down. Where the appliance image is on one node only, both appliances land on it.
- **A switch cuts open connections.** There is no connection state sync between the appliances.
- **Every controller call starts a full converge.** It reads the appliances through Proxmox's guest agent, every 10 s for each cluster. The load on a site with many clusters was not measured.
- **A large state is refused whole.** The gateway takes at most 64 KiB per call. A cluster with many Services (around 45 or more, with several ports or long source ranges) may pass that before the 50-Service limit; then no Service of the cluster is updated.
- **A gateway URL that is a host name** leaves the controller's egress port open to any address. Use an IPv4 address.
- **Enable during a cluster's delete** can mint the cluster's credential again. Operator only; do not enable a cluster that is being deleted.
- **TCP and IPv4 only.** UDP and IPv6 Services are refused, with an Event.
- **No grace for an address.** A Service deleted and created again gets a new address.
- **Default mode bills each Gateway.** NGINX Gateway Fabric takes one public address per Gateway.
- **Cluster appliances skip the server quota.** Only the addresses count against the quota (`floatingIps`).
- **Cilium is still outside its own support matrix on 1.36.** This candidate does not move it.
- **Earlier releases.** The other known issues in the [notes of v0.10.2](https://github.com/mutex-solutions/proxcloud/releases/tag/v0.10.2) still hold.
