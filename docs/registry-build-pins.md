# Registry reference pins — BUILD/template participation (P2-A)

## Implemented boundary / not complete GC

Only custom BUILD runtime-BASE acquisition and producer-DEST/template binding participation is wired; durable provenance for every retained `Builds[].From` is not yet integrated. Current retained From/Image references conservatively HOLD a parent binding's cleanup, but that DB observation is not race-free provenance transfer. API startup explicitly ensures the existing PRIMARY pin/intent tables plus a one-shot build-dispatch marker and wires `SetSandboxBuildPins`. No native/E2B sandbox create/resume/fork/snapshot/provider catalog writers or legacy adoption are covered by this change. BOTH scheduled/global and project-teardown real manifest-delete entrypoints remain unconditionally on operator HOLD. No rollout/coverage flag or GC endpoint is added; partial participation does not authorize deletion.

## Build protocol

1. A waiting owner build row claims PREPARING once, with immutable operation UUID, project identity and expected spec nonce. Duplicate callers cannot prepare/dispatch the same build again. Steps, registry credentials, env, CR payloads and signed context URLs are not stored in pin bookkeeping.
2. BASE selection is only a candidate. Standalone `BeginPins` commits owned `t/<project>/<template>` BASE alias/digest and generated DEST tag together before rendering/use or the existing project/start transaction. Builtin library and external BASE are explicitly outside internal deletable scope, not claimed protected. A changed/foreign internal BASE is refused.
3. Namespace → parent/current template row locks reselect the exact parent reference/build/runtime settings fingerprint and attach receipts to the same owner operation. PENDING pins protect independent-commit gaps. Exact-operation lookup recovers receipts after a lost return but never reacquires or redispatches. PREPARING/PINNED crashes remain conservatively held for operator investigation; there is no timeout takeover.
4. Durable `registry_build_dispatch` authorization is issued once per operation, freezes receipt identity/epochs and BASE+DEST, and is never deleted/reissued. A unique opaque envelope shares its use bit across shallow copies. The owner CASes PINNED → DISPATCHING before the existing project/rotation TX; production `sandbox.New` requires its low-level StartBuild envelope. The envelope is consumed in-memory, so no hidden nested commit or database call occurs inside the existing TX.
5. Authorized pins cannot be released as “known no effect” or have an active BASE alias collapsed to a digest. Busy/rotation refusal can cancel only the sole unused opaque envelope before a DB known-no-effect marker CAS; the retained operation PK prevents remint. A consumed/lost/ambiguous envelope is UNKNOWN and nonexpiring, never a retry permit.
6. Pods/ConfigMaps carry operation/nonce/BASE/DEST annotations. An independent exact pod UID+nonce+reference observation attaches UID without changing the pending alias. Same-pod optimistic observation conflicts accept only the exact current receipt, not a foreign generation. BASE stays protected through positive Succeeded/Failed observation; absence/deadline/cancellation is not termination proof.
7. Positive terminal observation is monotonic. The owner commits terminal result/digest + TERMINAL_OBSERVED before per-pin handoff. Exact BASE receipts release after terminal; successful DEST binds to the durable template/build generation after PRIMARY owner reread. Checkpoint recovery accepts only exact completed BASE/DEST transitions; it does not dispatch, invent a digest or clear UNKNOWN. Persisted terminal evidence resumes handoff even after the old pod disappeared. SDK status remains building until handoff finishes.
8. Stale error handlers cannot mark current known-finished refs UNKNOWN after failing the owner CAS. A core terminal marker cannot be downgraded by a delayed same-envelope Running observation. If only phase was durable but no owner digest was committed and the pod is gone, conservative HOLD remains; this is not fabricated READY evidence.
9. Active/unknown operations cannot be trimmed/deleted. Removed ready build generations become tombstones until exact binding release succeeds; retained historical ready builds remain pinned even after tag removal. Explicit tag edits are not restored by generic stale merges. Compact build-ID/generation tombstones survive full receipt cleanup without TTL, so even a stale pre-prepare snapshot with no registry operation cannot recreate an old build ID. Current retained From/Image refs conservatively retain parent DEST bindings and their owner tombstones until those known refs disappear; this is not complete durable provenance pin coverage. Project/template deletion may return an operator hold rather than destroy an unresolved owner record.

## Tests and known limits

Local unit/race tests cover READY/tag merge intent, active-build trim preservation, existing OCI output and cold-readiness behavior. Local real-PG/fake-K8s/loopback-S3 tests cover one accepted dispatch across parallel handlers, independently committed pins before the existing project TX, busy/rotation known-no-effect release, ambiguous apply no resend, exact READY DEST transfer, tag removal preserving retained builds, template removal release, and owned-parent TWO-pin persisted-checkpoint recovery through the existing handler before handoff/after DEST/after BASE with the old pod removed (not an OS-process restart test). Public SDK/console projections and usable-template selection all remain building/unusable until handoff finishes; legacy records keep their prior readiness behavior. Core tests cover durable one-shot authorization across stores, copied-proof consume/cancel, active alias conversion refusal, terminal UID/nonce release, monotonic stale Running observation, UNKNOWN retention and all P1 reference/prune regressions.

This is cooperative BUILD safety, not complete writer coverage or permission to run real GC. PREPARING/PINNED uncertain crashes, missing terminal digest, unknown apply, unadopted legacy records and nonparticipating writers remain HOLD conditions. No lease retry, clear-UNKNOWN endpoint, live registry/Kubernetes action, SMTP, billing-policy mutation or production-GC acceptance is introduced. The remaining work is separately bounded writer participation/adoption, then separately approved exact-own-project GC.
